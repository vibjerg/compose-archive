# 01 — AI-native composition protocols and runtimes (as of 2026-10-07)

Track: what composition looks like today in the AI ecosystem, and whether any of it can be the
substrate for a user-level "patch" of product tools (writing tool, knowledge base, swarm,
research tool, ...). Shared lens: `sonic/docs/product/patch-bay.md` — modules with typed jacks,
`canConnect`, the patch as plain data, parked modules that keep state, feedback legal at one
step of delay, edits that keep state.

Every dated claim carries a URL. Claims I could only find in secondary sources are marked
*(secondary)*; claims I could not verify are listed at the end.

---

## 0. The headline: the landscape moved a lot in 2026

Anything written from 2025 knowledge gets MCP wrong. The **MCP 2026-07-28 specification**
([blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/),
[changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)) changed the
protocol's shape:

- **Stateless core.** `initialize`/`initialized` and `Mcp-Session-Id` are gone (SEP-2575,
  SEP-2567). Every request carries protocol version, client capabilities and client info in
  `_meta`. New `server/discover` RPC. "Servers that need cross-call state use explicit,
  server-minted handles passed as ordinary tool arguments."
- **Multi Round-Trip Requests (MRTR, SEP-2322).** Server-initiated requests (`roots/list`,
  `sampling/createMessage`, `elicitation/create`) are replaced: the server returns
  `resultType: "input_required"` with `inputRequests`; the client retries the original call
  with `inputResponses`. Every result now has `resultType` (`complete` | `input_required`, plus
  `task` under the tasks extension).
- **Roots, Sampling and Logging are deprecated** (SEP-2577, twelve-month minimum window).
  Suggested migration: pass directories via tool params/resource URIs instead of Roots;
  "integrate directly with LLM provider APIs instead of Sampling"; OpenTelemetry instead of
  Logging.
- **Tasks moved out of core into the `io.modelcontextprotocol/tasks` extension** (SEP-2663,
  [SEP page](https://modelcontextprotocol.io/seps/2663-tasks-extension)): a `tools/call` may
  return a task handle (`resultType: "task"`); `tasks/get` (poll), `tasks/update` (client
  input mid-flight), `tasks/cancel`; `tasks/list` removed; server decides per request.
- **Subscriptions:** `resources/subscribe` and the GET stream replaced by one opt-in
  `subscriptions/listen` stream (list-changed and resource-change notifications).
- **Formal extensions framework** ([overview](https://modelcontextprotocol.io/docs/extensions/overview)):
  identifiers are `{vendor-prefix}/{name}`, third parties use reverse-DNS
  (`com.example/my-extension`), negotiated per request in `clientCapabilities.extensions` and
  in `server/discover`. Official ones: Tasks, MCP Apps (`io.modelcontextprotocol/ui`),
  auth extensions (client credentials, Enterprise-Managed Authorization), **Skills over MCP**
  (`ext-skills`), plus `experimental-ext-*` incubation (e.g. interceptors).
- **Cacheable lists** (`ttlMs`, `cacheScope`, SEP-2549), header routing (`Mcp-Method`,
  `Mcp-Name`, SEP-2243), OTel `traceparent`/`tracestate`/`baggage` conventions in `_meta`
  (SEP-414), JSON Schema 2020-12 for `inputSchema`/`outputSchema` and any JSON in
  `structuredContent` (SEP-2106).
- **Auth hardening:** RFC 9207 issuer validation, credentials bound to issuer, Dynamic Client
  Registration deprecated in favour of Client ID Metadata Documents (CIMD).

Other 2026 movements: A2A reached v1.0 and is hosted by the Linux Foundation; Claude Code
gained agent teams, plugin dependencies and `userConfig`; Agent Skills (SKILL.md) became a
cross-vendor format; OpenAI merged its app directory into a plugin directory and is shutting
down Agent Builder; Claude Managed Agents and OpenAI sandbox agents made "a hosted agent with a
workspace" a product primitive; Windows ships an OS-level MCP registry and agent workspace.

## 1. Per-system survey

Same fields for each: **unit** of composition · **what flows** · **state** ·
**identity/permission** · **substrate verdict** for a patch of product-level tools.

### 1.1 Model Context Protocol (spec 2026-07-28)

- **Unit:** a *server* exposing tools, resources (URI-addressed, `resources/read`,
  templates), prompts; optionally extensions (UI, tasks, skills). A *client* lives inside a
  *host* (Claude, ChatGPT, VS Code, goose...). Composition is host-centric: one host, many
  servers, the model picks.
- **What flows:** JSON-RPC requests/results. Tool results are content blocks plus
  `structuredContent` validated against `outputSchema`; resources are URI + MIME + content.
  MRTR interim results (`input_required`), task handles, notifications on
  `subscriptions/listen`. MCP Apps: tools point at `ui://` HTML resources rendered in a
  sandboxed iframe that speaks MCP JSON-RPC back to the host
  ([SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp),
  [MCP Apps blog 2026-01-26](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)).
- **State:** deliberately *not* the protocol's job anymore. Protocol is stateless; state lives
  in server-minted handles passed as arguments, or in task handles. Resource subscriptions are
  the only push channel.
- **Identity/permission:** OAuth 2.1 per server (resource server), CIMD for client identity,
  `clientInfo`/`serverInfo` per message; enterprise extension for centralized auth. Permission
  granularity is *per server connection* (plus host-side per-tool approval UX); there is no
  notion of "tool A may pass data to tool B".
- **Registry:** [registry.modelcontextprotocol.io](https://registry.modelcontextprotocol.io),
  preview since 2025-09-08 ([blog](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)),
  API frozen at v0.1 on 2025-10-24; GA/v1 not found as of last source
  ([about](https://modelcontextprotocol.io/registry/about)). It is a metadata index of
  servers (packages/remotes), sub-registries can mirror it.
- **Governance:** donated to the Agentic AI Foundation (Linux Foundation) Dec 2025 with goose
  and AGENTS.md ([LF/AAIF coverage](https://www.enterpriseaiworld.com/Articles/News/News/The-Linux-Foundation-Announces-the-Formation-of-the-Agentic-AI-Foundation-172815.aspx)).
- **Verdict:** the best available *module boundary*. Typed in/out schemas, URI-addressed
  resources, async tasks, human-input as a first-class result, UI as a resource, a sanctioned
  vendor-extension mechanism. But the *cable* is the model's runtime decision inside one host;
  there is no wiring object, no inter-server data flow, no shared artifact identity.

### 1.2 A2A — Agent2Agent (v1.0)

- **Status:** v1.0.0 in early 2026, described by the LF as the "first stable specification";
  >150 orgs, integrated in Google Cloud, Azure, AWS; SDKs in Python, JS, Java, Go, .NET
  ([LF press release, 2026-04-09](https://www.linuxfoundation.org/press/a2a-protocol-surpasses-150-organizations-lands-in-major-cloud-platforms-and-sees-enterprise-production-use-in-first-year)).
  Hosted by the Linux Foundation directly (not one of AAIF's founding projects). Signed Agent
  Cards in v1.0 and an extension mechanism in 1.0.1 *(secondary:
  [glukhov.org](https://www.glukhov.org/ai-systems/comparisons/a2a-protocol-2026-adoption/))*.
- **Unit:** an *agent* behind an HTTP endpoint, described by an **Agent Card** (identity,
  skills, endpoint, security schemes) ([spec](https://a2a-protocol.org/latest/specification/)).
  Opaque: you do not see its tools.
- **What flows:** **Messages** (role + **Parts**: text, file ref, structured data) and **Tasks**
  with lifecycle `SUBMITTED → WORKING → INPUT_REQUIRED / AUTH_REQUIRED → COMPLETED / FAILED /
  CANCELED / REJECTED`; outputs are **Artifacts** made of Parts. `contextId` groups related
  tasks. Polling, streaming (`SendStreamingMessage`, `SubscribeToTask`) or push webhooks.
- **State:** server-owned task with history and artifacts; context id for continuity.
- **Identity/permission:** declared security schemes (OAuth/OIDC/API keys/mTLS), extended
  Agent Card behind auth, signed cards.
- **Verdict:** the right *shape* for "hand a job to swarm and get artifacts back,
  maybe asking a human in between". Its Artifact is the nearest thing to a shared artifact
  model in any protocol, but it is scoped to one task on one server, has no content address,
  no lineage, no cross-agent reference. Peer-to-peer delegation, not a patch.

### 1.3 Claude Agent SDK, Claude Code, Managed Agents

- **Agent SDK** ([overview](https://code.claude.com/docs/en/agent-sdk/overview)): Claude
  Code's agent loop as a TS/Python library: built-in tools, hooks, subagents, MCP,
  permissions, sessions (resume/fork), skills/commands/memory from `.claude/`, plugins by path.
- **Claude Code extension points:** skills (SKILL.md, progressive disclosure), subagents
  (report to parent only), **agent teams** (lead + teammates with a shared task list, direct
  messaging; launched 2026-02-05 *(secondary:
  [towardsai](https://pub.towardsai.net/claude-code-extensions-explained-skills-mcp-hooks-subagents-agent-teams-plugins-9294907e84ff))*),
  hooks (deterministic shell/exec at lifecycle events: PreToolUse, PostToolUse...), MCP
  servers, LSP servers, monitors, workflows, output styles.
- **Plugins** ([manifest reference](https://code.claude.com/docs/en/plugins-reference)): a
  plugin is a namespaced bundle (`plugin:component`) with `dependencies` (name@marketplace,
  version), `userConfig` (typed, `sensitive` values to keychain, surfaced in `/config`),
  `channels` (message bridges bound to an MCP server), `${CLAUDE_PLUGIN_DATA}` persistent
  per-plugin dir, marketplaces. Same plugins run in **Cowork** (knowledge-work plugins, Jan–Feb
  2026, *(secondary: [claudecowork.im](https://claudecowork.im/blog/claude-cowork-new-plugins-feb-2026))*),
  minus `bin/`.
- **Agent Skills** became an open format at agentskills.io (Dec 2025), adopted by Codex,
  Gemini CLI, Copilot, Cursor et al. *(secondary:
  [noqta.tn](https://noqta.tn/en/blog/agent-skills-skill-md-universal-ai-coding-standard-2026))*;
  and Skills are now readable over MCP (`ext-skills`, see 1.1).
- **Managed Agents** (launched 2026-04, [docs](https://platform.claude.com/docs/en/managed-agents/overview)):
  Agent (model, prompt, tools, MCP servers, skills) + Environment (cloud or self-hosted
  sandbox template) + Session (long-running, server-side history and sandbox state) +
  Events.
- **State:** session transcripts + filesystem/working directory; per-plugin data dir.
- **Identity/permission:** permission modes and allow/deny rules per tool; hooks as policy;
  API-key identity; the user is the principal, plugins inherit the session's rights.
- **Verdict:** the richest *packaging* model (plugin = skills+agents+hooks+MCP+config with
  dependencies) and the natural home for swarm's agents. But plugins compose by *co-residence
  in one agent's context*, not by wiring: everything installed is in the same pot and the model
  routes. Dependencies are "must be enabled", not "output of X feeds input of Y".

### 1.4 OpenAI: Agents SDK, Apps SDK / plugins, AgentKit, Frontier

- **Agents SDK** ([docs](https://openai.github.io/openai-agents-python/)): Agents, Handoffs,
  Guardrails, Sessions, Tracing, MCP tools, Realtime agents, and (April 2026) **Sandbox
  Agents** with "manifest-defined files" and resumable sandbox sessions plus a model-native
  harness ([TechCrunch 2026-04-15](https://techcrunch.com/2026/04/15/openai-updates-its-agents-sdk-to-help-enterprises-build-safer-more-capable-agents/)).
  Unit = agent; handoff = transfer of the conversation to another agent.
- **Apps SDK** is MCP-based; ChatGPT reached full MCP Apps compatibility 2026-02-22, plugin
  distribution expanded to Codex 2026-03-25, CIMD client IDs 2026-08-21
  ([plugins changelog](https://developers.openai.com/plugins/changelog)). App directory merged
  into a plugin directory 2026-07-09 *(secondary:
  [awesome-chatgpt-apps](https://github.com/rdmgator12/awesome-chatgpt-apps))*.
- **AgentKit / Agent Builder** — the only major-vendor *visual* agent graph — is being shut
  down: notice 2026-06-03, Evals read-only 2026-10-31, both gone 2026-11-30; migration to the
  Agents SDK or Workspace Agents in ChatGPT *(secondary:
  [therouter.ai](https://therouter.ai/news/openai-evals-agent-builder-prompts-deprecation-november-2026/),
  [therundown](https://www.therundown.ai/tools/agent-builder); OpenAI's own page returned 403)*.
- **Frontier** (Feb 2026): enterprise agent platform with a "semantic layer for shared
  business context" and per-agent identity *(secondary:
  [reworked](https://www.reworked.co/digital-workplace/openai-expands-enterprise-push-with-frontier-ai-agent-platform/))*.
- **Verdict:** converges on MCP for the module boundary and on "agent + sandbox workspace +
  session" for runtime. The retreat from Agent Builder is a data point: a vendor-owned visual
  wiring canvas for *developers* did not stick; natural-language "workspace agents" won. That
  argues the user-visible patch must be about *product tools and artifacts*, not prompt
  nodes.

### 1.5 LangGraph (1.x) / LangSmith Deployment

- **Status:** 1.0 Oct 2025, no breaking changes; 1.1 typed streaming; LangGraph Platform
  renamed LangSmith Deployment ([LangChain blog](https://www.langchain.com/blog/langchain-langgraph-1dot0)).
- **Unit:** a node (function) in a `StateGraph`; subgraphs compose.
- **What flows:** a shared typed state object; each channel has a **reducer** that merges
  concurrent writes ([graph API](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph)).
  Execution is Pregel/BSP **super-steps**: nodes in a step read the state of the previous step,
  so cycles are legal by construction.
- **State:** checkpointer snapshots every super-step keyed by `thread_id`; `interrupt()`
  pauses indefinitely for human input; time travel / fork from any checkpoint
  ([durable execution](https://7x.mintlify.app/oss/javascript/langgraph/durable-execution),
  [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts),
  [time travel](https://docs.langchain.com/oss/python/langgraph/use-time-travel)).
- **Identity/permission:** none at graph level; the deployment layer does auth.
- **Verdict:** the closest *execution semantics* to the patch bay (see §3), but the graph is
  developer code, single-process-scoped state, one owner. A good model to imitate for
  scheduling and feedback; not a user-level patch.

### 1.6 Durable execution engines (Temporal, Restate, Inngest, DBOS)

- **Temporal:** workflows + activities with replay; OpenAI Agents SDK integration GA
  2026-03-23 — `TemporalRunner`, `activity_as_tool` make every model/tool call an activity
  ([Temporal blog](https://temporal.io/blog/announcing-openai-agents-sdk-integration),
  [cookbook](https://docs.temporal.io/ai-cookbook/openai-agents-sdk-python)).
- **Restate:** durable handlers, journaled side effects, **Virtual Objects** = single
  instance per key with transactional state and a queue — "an agent per session id";
  integrations with OpenAI Agents SDK (2026-01-15), Google ADK, Vercel AI SDK
  ([Restate AI docs](https://docs.restate.dev/ai/index),
  [OpenAI SDK post](https://restate.dev/blog/durable-orchestration-for-ai-agents-with-restate-and-openai-sdk)).
- **Inngest:** event-triggered functions, `step.run` memoized checkpoints, AgentKit networks,
  `useAgent` streaming parts to the UI that survive refresh
  ([useAgent](https://agentkit.inngest.com/reference/use-agent)).
- **DBOS:** a library; workflow state in Postgres; Pydantic AI integration
  ([DBOS docs](https://docs.dbos.dev/integrations/pydantic-ai)).
- **Unit:** workflow/function/handler; **flows:** events, step results; **state:** journal or
  DB, keyed by workflow/object id; **identity:** service-level only.
- **Verdict:** the right *runtime* for modules that wait days for a human, survive deploys
  and stay parked with state (Restate virtual objects and durable sleep are literally "parked
  module keeps its state"). Not a composition model: wiring is code, and code versioning
  (Temporal patching/versioning) is the only story for "the patch changed while running".
  Nothing here gives "edit the patch, keep the reverb tail".

### 1.7 Dagger

- **Unit:** typed **Dagger Functions** in modules (any language), callable via GraphQL; core
  types `Container`, `Directory`, `File`, `Secret`, `Service`. Content-addressed and cached
  (per-function cache control added March 2026, *(secondary: [blog index](https://dagger.io/blog/))*).
- **LLM primitive:** an `LLM` gets an **Env** that binds typed *inputs* (a Directory, a
  Container, a module, a string) and named typed *outputs* it must produce; tools are the
  Functions attached to env objects; final env state is the result. MCP both ways: expose
  modules as MCP servers, attach MCP servers to an LLM
  ([LLM docs](https://docs.dagger.io/features/llm/), [blog](https://dagger.io/blog/llm/)).
- **State:** immutable values + cache; no long-lived state.
- **Verdict:** the best prior art for **an LLM step with typed jacks** and for
  content-addressed artifacts with reproducible lineage (the DAG of function calls *is*
  provenance). Scoped to build/CI-like work, developer-authored pipelines, no human-in-the-loop
  or long-lived state.

### 1.8 Editor/OS/workspace layers ("agent OS")

- **Agent Client Protocol (ACP, Zed):** JSON-RPC over stdio between an *editor* and a *coding
  agent*; Zed + JetBrains, 25+ agents/editors by March 2026, Zed 1.0 on 2026-04-29
  ([Zed progress report](https://zed.dev/blog/acp-progress-report)). Note the name clash:
  "ACP" also names IBM/BeeAI's *Agent Communication Protocol*, a REST agent-to-agent protocol;
  its reported merger into A2A is unverified here.
- **Windows agentic features:** MCP servers registered as "agent connectors" in the Windows
  **On-Device Registry (ODR)**; **agent workspace** where agents run as a separate low-privilege
  account with scoped folder/app access
  ([Windows dev blog, Ignite 2025](https://blogs.windows.com/windowsdeveloper/2025/11/18/ignite-2025-furthering-windows-as-the-premier-platform-for-developers-governed-by-security/),
  [MS support](https://support.microsoft.com/en-us/windows/ai/ai-features/experimental-agentic-features)).
- **Enterprise control planes:** Microsoft Agent 365 GA 2026-05-01 (registry and governance of
  agents across vendors), Google Gemini Enterprise Agent Platform, OpenAI Frontier, AWS
  AgentCore Gateway (supports the 2026-07-28 MCP spec,
  [AWS blog](https://aws.amazon.com/blogs/machine-learning/how-agentcore-gateway-supports-the-mcp-2026-07-28-spec/))
  *(Agent 365/Gemini details secondary:
  [winbuzzer](https://winbuzzer.com/2026/05/02/microsoft-agent-365-general-availability-local-ai-agents-xcxwbn/))*.
- **goose** (AAIF): local-first agent with MCP extensions and "recipes".
- **Verdict:** these are *inventories and sandboxes*: who exists, who may run, where. None of
  them models how one tool's output becomes another's input, and none shows the user a wiring.

## 3. Gaps: what none of them provide

1. **No user-visible, versioned patch.** In every system the composition is either the model's
   runtime choice (MCP, A2A, plugins, handoffs) — invisible, non-deterministic, never saved —
   or developer code (LangGraph, Temporal, Dagger). Nobody stores "research → knowledge base →
   writing tool, with swarm reviewing" as plain data the user sees, edits, undoes, shares. The
   one vendor visual graph (Agent Builder) is being retired.
2. **No `canConnect`.** MCP now has JSON Schema 2020-12 `inputSchema`/`outputSchema`, A2A has
   typed Parts, Dagger has typed values, but nothing checks *at wiring time* that tool A's
   output kind may feed tool B's input. Compatibility is discovered by the model at call time.
3. **No cross-tool artifact identity.** MCP resources are owned and addressed by their server
   (and the server may vanish); A2A artifacts live inside one task on one agent; Claude/OpenAI
   sessions produce files in a sandbox. Nothing gives "this brief" a stable, content-addressed
   identity that the writing tool, the KB and swarm all reference.
4. **No provenance/lineage across tools.** OTel `traceparent` in MCP `_meta` gives run traces
   (which call happened), not artifact lineage ("this paragraph came from research run R,
   source S, approved by person P, revised by swarm round 4"). Only Dagger's call DAG
   approximates lineage, and only inside one pipeline.
5. **No per-cable capability grant.** Permission is per server (OAuth), per tool (host
   approval), per session (permission modes) or per OS account (Windows agent workspace).
   None expresses "the KB may be *read* by the writing tool in this patch but not by swarm" —
   data-flow-level authority. *(Corroborating, not authoritative: arXiv
   [2606.31498](https://arxiv.org/pdf/2606.31498), "Governance Gaps in Agent Interoperability
   Protocols: What MCP, A2A, and ACP Cannot Express" — title only checked.)*
6. **No "edits keep state".** Durable engines keep state across crashes, LangGraph across
   interrupts, Restate per key — but changing the composition while running is a code deploy
   with versioning, not a diff of a patch that keeps surviving modules' state.
7. **No parked-module semantics.** Nothing says "this module is installed and configured but
   not reached by any cable, so it costs nothing and keeps its state". Plugins are enabled or
   disabled globally; everything enabled crowds one context window.
8. **Model access moved out of the protocol.** With Sampling deprecated, a module that needs
   an LLM must bring its own provider credentials — there is no standard "the platform lends
   you a model under the user's budget".

## 4. What is the cable/jack/patch here

Mapping the patch-bay vocabulary onto the landscape:

- **Module** ≈ an MCP server (or a plugin bundling one, or an A2A agent seen from outside).
  Good fit: a module already doesn't know or care what is on either side of it.
- **Jack** ≈ a tool's `inputSchema`/`outputSchema`, a resource template's URI+MIME, an A2A
  Part type, a Dagger Env input/output. These are *types*, but no system lifts them into named
  **jack kinds** with a `canConnect` rule. Candidate kinds for product tools: `document`
  (markdown + metadata), `source-set` (citations), `knowledge` (KB query/scope), `brief`/`spec`,
  `feature`/`task` (swarm), `review`/`verdict`, `event` (trigger), `human` (needs a person).
  Like audio/control, some kinds should be deliberately interchangeable (a document can be a
  brief), others strict (a verdict only joins a gate).
- **Cable** — this is where the landscape has *nothing*. Today the "cable" is an LLM deciding
  to call tool B with something it got from tool A. It is invisible, unsaved and
  re-decided every run. In a kernel the cable must be explicit data: `{from: module.jack, to:
  module.jack, kind, grant}`. It doubles as the **capability grant** (gap 5): if there is no
  cable, data does not flow, whatever the model wants.
- **Modulation cable into a param** ≈ configuration flowing from one tool into another's
  settings (a KB's "house style" document setting the writing tool's tone `userConfig`;
  swarm's feature status gating publication). Claude plugin `userConfig` is the closest
  existing "param" surface.
- **Patch** ≈ none exists as data. Nearest: a LangGraph graph (code), a Dagger pipeline (code),
  a plugin's `dependencies` list (not a wiring). The kernel's patch must be plain,
  diffable, versioned, user-visible data — the thing the landscape lacks most.
- **Feedback at one step of delay** ≈ LangGraph's super-step semantics (a node reads the
  previous step's state, so cycles are legal) and swarm's own rounds. For product tools the
  "quantum" is a *revision* or *round*: the critic's verdict feeds the next draft, not the
  current one. Legal, bounded, visible.
- **Several cables into one input are summed** ≈ LangGraph reducers. Product tools need
  per-kind merge rules (source-sets union; documents do *not* sum — they need a mixer module).
- **Parked module** ≈ Restate virtual object / durable sleep: identity + state retained, zero
  cost. No product layer exposes it.
- **Needs-a-human** ≈ MCP `input_required` + tasks extension and A2A `INPUT_REQUIRED` /
  `AUTH_REQUIRED` have converged on the same shape. The kernel's "module is waiting for a
  person" state should map 1:1 onto both.

## 5. Implications for the kernel

**Build on MCP — as the module boundary and transport, not as the composition model.**

1. **Module = MCP server (2026-07-28, stateless).** Every tool (writing, KB, research, swarm)
   exposes its capabilities as MCP tools/resources, with `outputSchema`, tasks for long work,
   MRTR for human input, MCP Apps for its card UI. This buys every host for free (Claude,
   ChatGPT, VS Code, goose, Windows ODR) and lets *external* agents drive any module. Stateless
   core + server-minted handles fits modules whose state lives behind ids.
2. **Jack metadata in a vendor MCP extension**, e.g. `<reverse-dns>/jacks`: per tool/resource,
   declare jack names, kinds, direction, merge rule, whether a cable may move a param. The
   extensions framework explicitly sanctions third-party reverse-DNS extensions with graceful
   degradation, so modules stay plain MCP servers for hosts that ignore it. Same for an
   artifact/provenance extension (below).
3. **The kernel owns what MCP does not:**
   - **the patch as plain data** (modules, cables, params; versioned, diffable, undo,
     presets = starting patches), and a runtime that diffs patches and keeps surviving
     modules' state;
   - **jack kinds and `canConnect`**, checked when a cable is drawn, using the extension
     metadata plus JSON Schema compatibility;
   - **artifacts as first-class, content-addressed objects** with a lineage record (produced by
     module M in run R from inputs I, approved by P). Modules receive and return artifact
     *references*; MCP resources become one way to read them, not their identity;
   - **cables as capability grants**: a module only sees what is cabled into it; the LLM
     inside a module operates within that, never outside it;
   - **scheduling semantics** borrowed from LangGraph (step/round-based, feedback legal at
     one round of delay) and from the patch bay (modules not reaching an output are parked).
4. **Runtime under modules, not in the kernel's model:** durable execution (Restate/DBOS-style
   journaled steps keyed by module id) for long, human-waiting work — or MCP tasks backed by
   it. Keep the kernel engine-agnostic; it needs "durable handle + status + input_required",
   which both MCP tasks and A2A tasks already give.
5. **Model access is a kernel service.** Sampling is deprecated; modules should not each hold
   provider keys. The kernel lends models (budget, identity, audit) — the equivalent of the
   patch bay's shared pitch detector: one service, many consumers.
6. **A2A at the edge only:** expose a whole patch (or swarm) as an A2A agent for cross-org
   delegation, and wrap foreign A2A agents as modules. A2A's Artifact/Part model is a good
   reference for the kernel's artifact envelope.
7. **Packaging via Claude-style plugins / Agent Skills:** a module's agent prompts, skills and
   hooks ship as a plugin; skills can also be served over MCP (`ext-skills`). Plugin
   `dependencies` ≠ cables; do not confuse install-time deps with the patch.
8. **Why not MCP as *the* model:** its composition point is the host's model, which is exactly
   the invisible, unsaved, permission-flat cable the platform exists to replace. Using MCP as
   the model would make "the patch" a prompt.
