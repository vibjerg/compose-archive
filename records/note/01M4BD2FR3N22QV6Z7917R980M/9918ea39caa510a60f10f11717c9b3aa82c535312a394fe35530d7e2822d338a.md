# 01 — What flows on the cable: the shared data/artifact model

Track 1 of the compose research (see `STATE.md`). The shared lens is Sonic's patch bay
(`~/www/sonic/docs/product/patch-bay.md`): jacks have a **kind** (`audio`, `control`, `note`).
`canConnect` decides legality. A patch is plain data. A module that reaches no sink is parked.
A feedback cable is legal and reads the previous quantum. The question here is what plays the
role of "a 128-sample block" when the modules are a writing tool, a knowledge base, swarm and a
research tool.

Researched 2026-10-07. Fast-moving claims carry an as-of date. Anything marked
*(background, unverified)* comes from general knowledge and was not re-checked on the web
this session.

---

## 1. The question, sharpened

Unix composes because every program agrees on one thing: a byte stream, usually lines of text.
Sonic composes because every module agrees on one thing: a mono block of 128 floats, whose
*meaning* is given by the jack kind. Both choices make the cable **dumb and universal**. All
the meaning lives in the modules, plus a thin legality check.

Knowledge-work tools have never agreed on a cable. Every past attempt picked one of four
answers:

| Answer | Examples | What the cable carries |
|---|---|---|
| **Files** | Unix, Obsidian, git | named blobs, often text, in a directory the user owns |
| **Database / graph** | Notion, Tana, Anytype, Logseq DB, RDF stores | typed entities and relations in one store, usually behind one app |
| **Log / facts** | Kafka, Datomic, event sourcing, Automerge's change history | an append-only sequence of immutable changes or facts |
| **Embedded components** | OpenDoc, OLE, Embark, Patchwork | documents containing live parts owned by other "tools" |

Each answer is reviewed below. A synthesis follows that settles on **immutable, content-addressed
records with a small typed envelope, flowing as references along an append-only log**. Text
bodies are allowed, and LLM coercion is an explicit module, never kernel magic.

## 2. Prior art

### 2.1 Local-first and Ink & Switch

**Local-first software.** Data lives on the user's device and syncs peer-to-peer or through
dumb relays. Collaboration comes from CRDTs, not a server of record. **Automerge** is the lab's
JSON-like CRDT. *Automerge Repo 2.0* shipped in May 2025 and *Automerge 3.0* in July 2025:
"cuts down memory usage by more than 10x while preserving backwards compatibility". By August
2026 the line was at 3.4.1 ([automerge.org/blog](https://automerge.org/blog/)). Automerge stores
**every change**, so a document is really a log with a materialized view. Its "heads" (hashes of
the latest changes) name an exact version, much as a git commit does.

**Patchwork** is "version control for everything": branches, drafts, diffs and history for any
document type, all built on Automerge
([Patchwork notebook](https://www.inkandswitch.com/patchwork/notebook/),
[history and diffs with Automerge](https://inkandswitch.com/patchwork/notebook/08)). Two points
matter for us.

- **Tools are documents too.** The 2025 malleable-software essay says Patchwork stores "both
  user data and software code in Automerge documents". A tool someone wrote "could be shared
  with a link, just like any other document", and tools sync "with no need to rebuild or
  redeploy Patchwork itself" ([essay](https://www.inkandswitch.com/essay/malleable-software/)).
  The patch, the modules and the data share one substrate.
- **2026: a local-first task framework.** In Alex Warth's notes (April 2026), a *task* is a
  unit of work with code to run, an optional input and a history of runs, kept in an Automerge
  document. Task queues and a router hand tasks to each user's workers, and tasks keep running
  offline. This is paraphrased from search summaries; the page itself was not quoted. It is used for aggregating edit histories and computing embeddings
  ([tasks-01](https://www.inkandswitch.com/patchwork/notebook/tasks-01/),
  [tasks-02](https://www.inkandswitch.com/patchwork/notebook/tasks-02/), April 2026). This is
  very close to a swarm round expressed as data: input, code or agent, run history, all in a
  document.

Orion Reed's *Breadboard* and *Space-frame* prototypes reportedly compose tools that transform each
other's data when placed side by side: a spatial patch bay over shared documents. This comes
from a search summary of the Ink & Switch newsletter and was not checked against the page.

**The malleable software essay (2025)** is by Litt, Horowitz, van Hardenberg and Matthews
([essay](https://www.inkandswitch.com/essay/malleable-software/)). Its data claim is that
"when data is instead shared among applications, it empowers end users to compose tools in more
flexible ways". It cites the filesystem, where "you can edit the same file in different tools
that focus on different subtasks", and Airtable-style multiple views of one store. It names
apps that bundle a single workflow "avocado slicers". On AI it says "AI code generation alone
does not address all the barriers to malleability", so the substrate matters more than the code
generator. That is our premise exactly: LLMs make modules cheap to write, but only a shared
cable makes them composable.

**Embark** (Sonnentag, Litt, Obenauer) is an outline document enriched gradually with
**mentions** (structured entities inline in text), **formulas** (computations over the outline)
and **views** (maps and calendars bound to subtrees) ([Embark](https://www.inkandswitch.com/embark/)).
Its lesson is that *"freedom to annotate is valuable"*. People want prose and structure in one
place. Structure should be **added to text where it pays**, not demanded up front.

**Cambria** (2020, research prototype) uses bidirectional **lenses** (rename, hoist/plunge,
wrap/head, convert value, add/remove field) to translate a document between schema versions *on
read*. Independently developed apps can then share live data without agreeing on one schema
([Cambria](https://www.inkandswitch.com/project/cambria/)). It is not a widely adopted library.
I found no evidence of either active development or deprecation. The idea outlived the code.
Its known limits *(background, from the Cambria paper)*: lossy conversions need defaults, and
lenses compose badly across structural changes such as splitting one field into two records.

**Keyhive** is local-first access control: capability-based write control plus group key
agreement for read control, open-sourced in March 2025
([Keyhive notebook](https://www.inkandswitch.com/keyhive/notebook/)). It matters because, once
data is shared between modules and people, "who may write this kind of record" becomes a
property of the substrate, not of each app.

### 2.2 Content-addressed stores: git and IPLD

**git** *(background, unverified)*: blobs, trees and commits are named by their hash. A commit
is an immutable value whose identity *is* its content and history. Branches are mutable names
pointing at immutable values. Swarm already lives on this: every round ends in a core-made
snapshot commit (`snapshotSha`), and approval merges *exactly* that sha
(`swarm/docs/product/simple-model.md`, D-014/D-032).

**IPLD** generalizes git's model. The data model is null, bool, int, float, string, bytes,
list, map and **link**, where a link is a CID, a self-describing content hash. **DAG-CBOR**
gives a deterministic encoding, so equal data has an equal address
([DAG-CBOR spec](https://ipld.io/specs/codecs/dag-cbor/spec/)). Atproto repos are built on it.

Content addressing gives free deduplication, tamper evidence, cache keys and, most importantly
here, **provenance that cannot be forged after the fact**. "This claim was derived from
*that* source" is a link to a hash, not to a mutable URL that may have changed.

### 2.3 Logs and immutable facts: Kafka and Datomic

**Kafka / event sourcing** *(background, unverified)*: the source of truth is an append-only,
ordered log. Every view (table, index, cache) is a fold over it and can be rebuilt. Consumers
read at their own pace from their own offset. That is a cable with memory, and it decouples
producer from consumer in time.

**Datomic** stores a database as a set of immutable atomic facts called datoms, each a 5-tuple of entity,
attribute, value, transaction and op (add or retract). It has no tables, only a universal
schema of user-defined attributes. Every datom knows its transaction, and a database value is
a point-in-time immutable value, so you can query *as of* any time
([Datomic data model](https://docs.datomic.com/whatis/data-model.html)). Two lessons follow.

1. **Attributes, not tables, are the unit of schema.** Independently built modules can each add
   attributes to the same entity without a shared table design. This is the same move as
   Tana's fields, Notion's per-block properties and atproto's sidecar records.
2. **Time and transaction are part of every fact.** Provenance (which transaction, hence which
   run, agent and input) is built in, not bolted on.

### 2.4 RDF and linked data: why it mostly failed in practice

RDF is the purest attempt at a universal cable. Everything is a subject-predicate-object
triple, named by URIs, with shared ontologies for meaning. **W3C PROV-O** (a Recommendation
since 2013) is the best surviving piece. Its Entity, Activity and Agent, with `wasGeneratedBy`,
`used`, `wasDerivedFrom`, `wasAttributedTo` and `actedOnBehalfOf`, are exactly the provenance
vocabulary we need ([PROV-O Recommendation](https://www.w3.org/TR/prov-o/)).

Why the larger vision mostly failed:

- **Upfront, global agreement.** Ontologies must be designed before data flows, and they
  describe a world that keeps moving. Upkeep usually falls on one person with another job
  ([semantic web failed on upkeep](https://www.thisandthat.chat/blog/semantic-web-failed-on-upkeep/)).
- **Cost without payoff.** The formats were complex and error-prone, and they had no business
  model. Publishers had no incentive, and the consuming infrastructure never materialized
  (["The Semantic Web: Two decades on", Semantic Web journal](https://journals.sagepub.com/doi/10.3233/SW-190387),
  [Fournier-Viger](https://data-mining.philippe-fournier-viger.com/the-semantic-web-and-why-it-failed/)).
- **Triples drop the context that makes a claim usable.** A September 2026 paper argues the
  standards "formalised truth while omitting three things: the conditions under which a claim
  holds, the operations its terms permit, and any account of what a base covers". In the
  author's account, the field ceded question-answering to language models
  ([Zappa, arXiv:2609.14121](https://arxiv.org/abs/2609.14121)).

**The lesson for us** is not "no types". It is: **no global ontology, no upfront agreement,
and never a bare assertion**. A claim must carry its source, its conditions or scope, and who
or what produced it. The parts of RDF that survived (schema.org, JSON-LD in web pages, PROV)
are small, pragmatic and tied to a payoff.

### 2.5 Block and supertag tools: Notion, Tana, Anytype

- **Notion**: every block has an `id`, a `type`, `properties`, `content` (ordered child ids)
  and a `parent`. "Changing the type of a block doesn't change the block's properties or
  content—it only changes the type attribute"
  ([Notion data model](https://www.notion.com/blog/data-model-behind-notion)). Type here is a
  **rendering hint over durable properties**, so data survives reinterpretation.
- **Tana**: everything is a node, even fields, views and commands. A **supertag** turns a node
  into a typed object with a field template, and every node with that tag forms a queryable
  collection ([Tana: nodes, fields, supertags](https://tana.inc/articles/intro-to-nodes-fields-and-supertags)).
  Types are **added to existing nodes** after the fact, and a node can carry several. This is
  Embark's gradual enrichment, made systematic.
- **Anytype**: every object has a type, and "relations" are both attributes and links. It is
  local-first, with end-to-end encrypted P2P sync (any-sync)
  ([Anytype relations](https://doc.anytype.io/anytype-docs/basics/relations)).

All three are excellent *inside one app* and closed *between apps*. The types live in the app's
store, and a module from outside cannot plug in except through an export or an API. They show
the right **shape** (id, type tags, open properties, links) but the wrong **ownership**
(one vendor's database).

### 2.6 Files plus plugins: Obsidian, Roam and Logseq

- **Obsidian**: a vault is a folder of Markdown files with YAML frontmatter "properties".
  Plugins operate on the files. **Bases** (core plugin, v1.9, May 2025) adds database views,
  but all the data in a base is backed by the local Markdown files and their YAML properties,
  and the view definition is itself a `.base` YAML file
  ([1.9.0 changelog](https://obsidian.md/changelog/2025-05-21-desktop-v1.9.0)). That is
  structure added *over* files, not instead of them, and the view is itself plain data.
- **Roam** *(background, unverified)*: a block graph in a hosted database, with block
  references and Datalog queries. Powerful, but it has no files and the user's data sits in
  one vendor's store.
- **Logseq went the other way.** The "DB version" stores graphs in SQLite, not Markdown, to get
  **typed property values, full Datalog queries and real-time sync**. The file-based app was
  split off as "Logseq OG". It was in beta as of late 2025
  ([install notes, Oct 2025](https://preslav.me/2025/10/13/how-to-install-logseq-db-version-on-your-computer-sqlite/),
  [Logseq forum](https://discuss.logseq.com/t/questions-about-the-upcoming-database-version/27108)).
  Its status may have moved since.

**Counter-evidence, taken seriously.** Obsidian kept files and grew structure on top. Logseq
concluded that files could not carry typed properties, fast queries and sync, and moved to a
database. Both are right about their own problem. Files win on **ownership, tool diversity
(git, grep, editors, LLMs) and longevity**. A database wins on **types, queries and concurrent
edits**. The design below tries to get both: an append-only store of immutable records, which
is file-like and diffable, plus derived indexes, which are database-like and rebuildable.

### 2.7 Atproto: typed records in user-owned repos

Atproto (Bluesky) is the closest existing answer to "independently developed modules sharing
typed data that the user owns" *(repo structure: background, consistent with docs)*:

- Each user has a **signed repo**, a Merkle tree on IPLD/DAG-CBOR, under their DID. Records are
  addressed `at://<did>/<collection NSID>/<rkey>`.
- Every record has a `$type` naming a **Lexicon**, a JSON schema identified by a reverse-DNS
  NSID such as `app.bsky.feed.post` ([Lexicon guide](https://atproto.com/guides/lexicon)). Anyone
  who owns a domain can define a new record type, and lexicons are themselves published as
  records (`com.atproto.lexicon.schema`).
- **Evolution rules are strict and additive.** New fields must be optional. Fields cannot be
  renamed or change type. "Loosening constraints breaks old software validation; tightening
  them breaks new software validation", so a breaking change means a **new NSID** (`…V2`).
  Use **open unions** "in almost all situations". Avoid closed enums in favour of `knownValues`.
  Other developers extend someone else's records with **sidecar records** that point at the
  original by strong reference
  ([Lexicon style guide](https://atproto.com/guides/lexinomicon)).

Atproto settles three questions at once. **Ownership**: the repo is the user's. **Typing**: a
decentralized namespace, with no global ontology. **Evolution**: additive only, plus a new name
for anything breaking. What it lacks is provenance *between* records ("derived from"). Strong
refs (URI plus CID) give you the raw material, but no convention.

### 2.8 Compound documents: OpenDoc and OLE

OpenDoc (Apple and partners) and OLE (Microsoft) let a document contain live "parts" edited
in place by different components. OpenDoc was cancelled in March 1997. It was too radical a change
for users and developers and overly complex for what it did, and the concept was oversold, since word processors already embedded pictures and charts
([Wikipedia: OpenDoc](https://en.wikipedia.org/wiki/OpenDoc),
[Gilbane: Jobs, OpenDoc and Fluid](https://gilbane.com/2020/05/steve-jobs-opendoc-and-fluid/)).
OLE survived as a clipboard-and-embed mechanism, not as an ecosystem. Microsoft's Fluid/Loop
components are the latest try.

**The lesson:** composing at the level of **live UI parts inside one document** couples
modules too tightly. They must share a process, a rendering contract and an in-place editing
protocol. Composing at the level of **data** (Unix pipes, the filesystem, atproto records)
survives. Patchwork's "tools as documents" works because the tool and its data are both just
data; the embedding is a view, not the contract. **The cable must carry data, never live
widgets.**

## 3. Trade-offs

### 3.1 Files vs database vs log

| | Files | Database | Log of immutable records |
|---|---|---|---|
| Ownership and longevity | best: any tool reads it in 20 years | vendor or app-bound | good, if the encoding is open |
| Typed queries | poor (Logseq left for this) | best | via derived indexes |
| Concurrent edits | poor (conflicts) | good, centralized | good (CRDT or append-only) |
| History and provenance | via git, coarse | usually lost | native (Datomic, Automerge) |
| Composability across independent tools | high (filesystem) | low (one schema owner) | high (each module reads and writes records) |
| Fit for LLM agents | excellent (text, grep, diff) | needs a tool or API layer | good if records render as text |

**Recommendation:** the **log of immutable, content-addressed records is the source of truth**.
Files and databases are **projections**: a Markdown export for humans and editors, an index for
queries. This is Datomic's and Kafka's stance, made local and user-owned like atproto. Swarm
already has the shape. `Round[]` is append-only, the hand-back is persisted "the moment the run
exits", and the snapshot is a hash. Only the feature-level JSON is a mutable materialization.

### 3.2 Typed schemas vs untyped text, after LLMs

LLMs make untyped text **more composable than ever**. Any module can read a paragraph and
extract a task list, a claim or a decision. Does that make types obsolete? No, for three
reasons:

1. **The coercion is lossy, costly and non-deterministic.** In Sonic, audio→control is free,
   exact and instant, so the kernel allows it implicitly. Text→task through an LLM costs money
   and seconds, can hallucinate, and gives a different answer each time. A coercion with those
   properties must be **visible in the patch**, as an *adapter module* with a cost, a model id
   and provenance, never an implicit cast in `canConnect`.
2. **Authority must not come from coercion.** An accepted decision, an approval or a merge
   are swarm's `approve`, D-005/D-016 decisions and `snapshotSha`. They must be strict typed
   records written by an authorized actor. In swarm the core writes `problem`, never the
   agent, and the orchestrator owns transitions (D-017). An LLM reading "we agreed to X" in a
   chat transcript must produce at most a *proposed* decision, never an accepted one. That is
   Sonic's `note` kind: a strict kind that only connects to its own kind.
3. **Machines need guarantees, humans need prose.** Swarm's `Handback` is a good model. It is a
   strict discriminated union (`result | question`) whose *fields* are mostly short text
   (`built`, `why`, `risks`). Type the **envelope and the routing-relevant fields**, and leave
   the bodies in text.

So the answer shifts but does not flip. Before LLMs, the dilemma was "type everything (RDF,
which failed) or nothing (files, which don't compose)". With LLMs it becomes: **type thin,
text thick, coerce explicitly.** Embark, Tana and Notion all reached the same pattern from the
UI side: text first, types added where they pay.

### 3.3 Provenance

Every record needs to answer, cheaply and unforgeably: *which module, which version, which run,
which agent or person, from which inputs, at what time, at what cost.* PROV-O gives the
vocabulary (`wasGeneratedBy` an activity, which `used` inputs and `wasAssociatedWith` an agent).
Content addressing gives the integrity: inputs are cited by hash. The Datomic lesson is that
**the store stamps it, not the author**. If modules write their own provenance, they will
forget, lie or drift. If the kernel stamps every record on write with the producing run, the
chain is complete by construction. Swarm already does this for rounds (`basis`, `sessionId`,
`costUsd`, `snapshotSha`). The generalization is to make it the kernel's job for every record.

Provenance also answers the Semantic Web's missing piece: a claim is never bare. It carries its
source links and the run that asserted it, and an optional `scope` or `conditions` text.

### 3.4 Versioning and schema evolution across independent modules

Three known strategies:

- **Additive-only plus a new name for breaking changes** (atproto). Simple, proven at scale,
  and it needs no runtime machinery.
- **Lenses on read** (Cambria). Powerful, but research-grade, and lossy in hard cases.
- **Migrate the store** (classic databases). Impossible when data is spread across modules
  and users that nobody controls.

**Recommendation:** adopt atproto's rules as kernel law for record types. Namespaced type ids,
additive evolution, open unions, `knownValues` over enums, and V2 as a new id. Allow lenses as
**ordinary adapter modules** in the patch (`TaskV1 → TaskV2`), not as kernel machinery. Sidecar
records (a record that annotates another by hash) let module B extend module A's data without
A's permission or schema change.

### 3.5 Ownership

Atproto, local-first and Obsidian agree: **the user's store is the user's**, readable without
the app and portable between hosts. Keyhive shows that access control can live in the data
layer. For a single-owner tool platform, the minimum is: one store per user or project, on
disk, in an open encoding, with a git-friendly text projection. Multi-party sharing and
capabilities can come later, without changing the record model, because records are already
immutable and content-addressed.

## 4. Where the Sonic analogy holds and where it breaks

| Sonic | Knowledge work | Holds? |
|---|---|---|
| A 128-sample block per quantum | a **reference to an immutable record version**, plus a change event saying "a new one exists" | holds if the cable carries refs, not payload copies |
| Jack kinds plus `canConnect` | a small set of record **kinds**, with type ids inside a kind | holds |
| audio ↔ control are interchangeable | text ↔ structure only through an LLM: costly and lossy | **breaks**: make it an explicit adapter module |
| `note` connects only to `note` | authoritative records (accepted decision, approval) connect only from authorized producers | holds, and is stricter |
| Several cables into one input are summed | several inputs form a **set or collection** (union of records), not a sum | adapted |
| Feedback reads the previous quantum (2.7 ms) | a loop reads the **previous version** of a record, by hash | holds |
| Loops decay and cost nothing extra | each pass costs money, and nothing fades | **breaks**: every loop needs a **bound** (swarm's rounds, review iterations, spend caps) and should return to a human sink |
| A module runs only if it reaches the speakers | a module runs only if it reaches a **sink**: a human inbox, a publish step, a merge | holds: parking is valuable, since it means no spend without a consumer |
| Edits keep state (diff the patch, keep surviving modules) | re-cabling keeps module state and record history | holds, and is easier because records are immutable |
| Block-rate time | event time: modules wake on new records, not on a clock | adapted: the clock becomes the log offset |

**Value or event on the cable?** Both, layered. The **log** carries events: "record R of
kind K was appended by run X". The **cable** delivers to the consumer the *current set of
references* that match its input. A consumer reads values by hash and can always ask for the
previous version. This is Kafka's offset model, combined with git's or IPLD's immutable values
and Automerge's heads.

## What is the cable/jack/patch here

**Cable** = a typed subscription from one module's output to another's input. It delivers
**references (content hashes) to immutable records**, together with the event that a new
record appeared. Payloads are fetched by hash from the shared store, never copied down the
cable. A feedback cable delivers the *previous* version.

**Jack** = a port declaring a **kind** (below) and optionally narrowing it to type ids
(`swarm.handback`, `kb.note`) and cardinality (one or a stream).

**Patch** = plain data, itself a record in the store (like Patchwork's tools-as-documents and
Obsidian's `.base` file): modules (type, version, id, config) plus cables. Versioned and
diffable like everything else. Parked modules are those with no path to a sink.

### Candidate jack kinds

These are not settled. Each is defined by three tests:
- **Coercible?** Can another kind be cabled into it through an adapter?
- **Authority?** Does a record of this kind commit anyone to anything?
- **Value or event?** Is it a thing to read, or a happening to react to?

| Kind | What it carries | Coercible? | Authority? | Value / event | Swarm today |
|---|---|---|---|---|---|
| `doc` | prose or Markdown with optional typed properties: notes, drafts, specs, sources' text | yes, the "audio" of the system, and the universal input | no | value | the feature `idea`, a `reply`, `simple-model.md` |
| `claim` | a statement with **required provenance**: source refs, producing run, optional scope or conditions, confidence. Research findings, review findings, critiques | **into** it only through an adapter (doc→claims extraction), which is stamped | no: claims are evidence, not commitments | value | reviewer's `openFindings`, `risks`, `checks.tests` |
| `decision` | a choice with rationale, rejected alternatives, status (proposed / accepted / superseded) and relation (follows / conflicts / supersedes) | **strict**, like `note`: a proposed decision may come from an adapter; *accepted* only from an authorized human action | **yes** | value with revisions | D-005/D-016/D-026 register, `Handback.decisions`, the pinned `basis` |
| `task` | a unit of requested work: intent, acceptance criteria, budget, dependencies; its runs and outcome appended | proposed tasks yes, through an adapter; *admitted* tasks are strict | yes (spends money) | value whose state is a fold over events | a `Feature` and its `Round[]`; Patchwork's 2026 task framework |
| `artifact` | an opaque, content-addressed build output: a commit sha, a file tree, a dataset, a rendered page, a preview URL | no (bytes) | no | value | `snapshotSha`, the preview |
| `signal` | an event or control: "approved", "dropped", "budget reached", "question asked", a request for a human, a clock tick | no (strict per type) | approvals yes | **event** | `approve`, `reply`, `drop`, `problem`, hand-back `question` |

`doc` and `claim` are the closest thing to Sonic's audio/control pair, with one difference:
the rule is **asymmetric**. Any structured record can be heard as a `doc`, because rendering it
to text is cheap, deterministic and nearly lossless; this is the analogue of "a control signal
can be heard". Going the other way (`doc` → `claim`, `task` or `decision`) means an LLM
extraction, so it needs an adapter module. `decision` and `signal` are the `note`-like strict kinds, because they carry
authority. `task` is the kind that makes something run. `artifact` is the escape hatch for
bytes, as Unix files are.

**`canConnect`, proposed:**
- **Same kind connects directly.** A jack's type narrowing (`swarm.handback`) must match, or the
  type is open.
- **Any kind into a `doc` input connects directly.** The kernel renders the record to text
  deterministically.
- **`doc` into any structured input needs an adapter**, as does any other lossy or costly
  conversion: an LLM extraction or a lens across schema versions. The adapter is a visible
  module with a cost and provenance.
- **`artifact` connects only to `artifact`** or to a `doc` input, through its textual
  description.
- **Authoritative records are restricted by producer, not by cable.** An accepted `decision`
  or an approval `signal` is accepted only from a producer the patch grants that authority,
  ultimately a human action. An adapter can only emit `proposed`.

The six may collapse to four or five. `signal` might be just the event log itself. `claim`
might be a `doc` with required provenance fields. Iteration 2 should test them against three
real compositions.

## Implications for the kernel

**The kernel owns:**

1. **One record envelope**, small and fixed:
   - `id` (content hash) and `kind` (from the set above)
   - `type` (a namespaced id such as `swarm.handback`, open-ended)
   - `body`, opaque to the kernel
   - `links`: typed references to other records by hash (`derivedFrom`, `about`,
     `supersedes`, `answers`)
   - `producedBy`: module type and version, patch node id, run id, agent or person, cost
   - `at`, the time
2. **An append-only, content-addressed store plus an event log**, local and user-owned. It has
   an open encoding (JSON or DAG-CBOR) and a text projection that is git- and grep-friendly.
   Mutable state ("the current task status") is always a **derived view** (a fold), never the
   source of truth.
3. **Provenance stamped on write by the kernel**, not supplied by modules. A module cannot
   write a record without the kernel attaching the run and its input hashes.
4. **`canConnect` by kind**, plus optional type narrowing. Two rules:
   - Lossy or costly coercion (text into structure, or a lens across schema versions) is
     *never implicit*. It is an adapter module, with its own cost and provenance. Only the
     deterministic rendering of any record into a `doc` input is direct, so the rule is
     asymmetric, unlike Sonic's audio ↔ control.
   - Authoritative kinds (`decision` accepted, approval `signal`) can only be produced by
     modules the patch grants that authority, ultimately a human action. This generalizes
     swarm's "core writes `problem`, person approves".
5. **Scheduling by reachability and bounds.** A module runs only if it has a path to a sink
   (parking). Every cycle in the patch must carry a bound (iterations, spend, or a human
   checkpoint) before the patch is legal. This is the knowledge-work replacement for "one
   quantum of delay" making feedback safe.
6. **Evolution law in the atproto style**: namespaced type ids, additive-only changes, open
   unions, a new id for breaking changes. The kernel checks only the envelope and, if a module
   declares one, a JSON-schema for its body type.

**The kernel does not own:**
- body schemas (modules publish them as records)
- rendering and UI (views are modules, as in Notion's type-as-render-hint, Embark's views and
  Obsidian Bases)
- lenses (adapter modules)
- LLM calls (adapter or agent modules)
- sync and sharing (a later layer; immutable content-addressed records make it addable without
  changing the model)

**Consequences for swarm as a module.** Swarm would consume `task` and `decision` (the basis)
and `signal` (reply, approve, drop). It would produce `claim` (findings), `decision`
(proposed), `artifact` (snapshot, preview) and `signal` (result or question hand-back). Its
`Feature` JSON becomes a fold over its records, and its decision register becomes the shared
`decision` kind that a writing tool or knowledge base can also read. That is the first
cross-module composition to try.

**Open risks to carry into iteration 2:**
- whether `claim` deserves its own kind, given the RDF lesson that over-structuring kills
  adoption
- the cost of content-addressing large or binary artifacts (store a hash and a path, not
  the bytes)
- how a human edits an "immutable" doc ergonomically (an Automerge document per doc, with
  each committed version hashed, as Patchwork does)
- whether the store is one per user or one per project
