# 05 — Adversarial critique of the round-2 premise

Round 2, iteration 5, the premise track. It runs in parallel with `05-invariants`, `05-foundry` and
`05-selection`, and attacks what those three take for granted.

**The premise, from the owner (`STATE.md`, "Runde 2"):**

> Don't think in what we know. Think in new ways of seeing tools and work, because developing
> workflows and tools has become cheap, and if they can be combined, their use grows.

**The proposed consequences, split so each can be judged on its own:**

| # | Claim |
|---|---|
| P1 | Building tools and workflows is cheap. |
| P2 | Tools are generated per problem and are mostly disposable. |
| P3 | The standard (kinds, contracts, trust) is the part that lasts. |
| P4 | The toolset evolves through use and selection. |
| P5 | A tool foundry replaces hand-built modules. |
| P6 | The problem is the app. Workspaces dissolve after the outcome. |
| P7 | When tools can be combined, their use grows. |

The brief is to attack the premise honestly, not to dismiss it. Each source is marked:

- **[P]**: a primary source that was fetched or read;
- **[S]**: a secondary write-up or a search snippet of a primary;
- **[U]**: unverified.

The owner's files are cited by path.

---

## Verdict first

1. **Generation is cheap. Building is not.** The cost has moved from writing to verifying,
   understanding, reviewing and trusting. For this owner the binding constraint is one person's
   review minutes plus $0.50–25 per paid run (`03-critique-product.md` §3). P1 is true of
   generation and false of everything after it. A design that counts only generation will spend
   the owner's attention without noticing.
2. **The slowdown evidence hits the premise's home turf least.** METR's slowdown result and the
   quality and maintenance findings come from large, long-lived codebases. Small, stateless,
   single-purpose tools are where the premise is strongest; Simon Willison's 150+ tools are the
   example. **Disposability is a property of a class of tools, not of tools in general.** P2
   survives below a size and blast-radius line and fails above it.
3. **The central contradiction is round 1's trust rule multiplied by disposable tools.** Every
   authoritative act is a human act over exact hashes (`04-synthesis.md` §2). If tools are
   generated per problem and those tools carry trust, the owner becomes the reviewer of
   everything. That is Faros's paradox with a review team of one. The premise survives only
   under Kernel D's cut: **trust attaches to effects and records at sinks, never to a tool's
   identity.** A tool can be disposable because it is trusted with nothing.
4. **"The standard lasts" (P3) is right, but it creates a new bottleneck.** A foundry needs kinds
   before tools exist. That inverts round 1's monolith-first rule (FM test 2), under which kinds
   come from real crossings. Kinds must be *promoted from observed crossings*, never generated
   alongside the tools.
5. **"Workspaces dissolve" (P6) contradicts the promise of cross-project memory** (`04` §8.3).
   The fix is a sharper split: the tool and the workspace dissolve, but the problem → decision →
   outcome records persist.
6. **"Use grows when they combine" (P7) holds only under conditions:**
   - a payload native to the domain;
   - M+N contracts rather than M×N glue;
   - cheap verification per combination;
   - solved discovery.

   Without these, composition is a tax. Tool-selection accuracy drops as tools are added, and
   network value grows nearer n log n than n². The owner's own composing skills already show
   that tax, written into their prose.
7. **Selection (P4) needs a fitness signal and volume. One owner has neither by default.**
   Voyager evolved a skill library because Minecraft is a verifier. In the compute-matched
   re-test of TroVE's toolbox, the gain shrank to about 1%.
8. **The steelman is real.** Round 1 treated every tool as a product that must earn its place.
   For leaf tools that is too conservative. The owner already has eight self-authored skills (last updated
   May–Aug 2026) that compose without any kernel. Round 2 should build *on that practice*, not on four
   hand-built modules.

## 1. Is building actually cheap? Decomposing "cost"

### 1.1 The cost ledger

| Cost component | Cheaper in 2025–26? | Evidence | What it means here |
|---|---|---|---|
| **Generation** (first working version) | **Yes, much** | Willison: 150+ single-file tools in about two years, "almost entirely" written by LLMs, and "rewriting them from scratch with help from an LLM takes just a few minutes" ([simonwillison.net, Dec 2025](https://simonwillison.net/2025/Dec/10/html-tools/)) [P] | The premise's true core |
| **Verification** (is it right?) | **No, and it grows with output** | Faros (10,000+ developers, 1,255 teams): high-AI-adoption teams merge 98% more PRs, review time rises 91%, PR size 154%, bugs per developer 9%, and company-level gains "evaporate" ([faros.ai](https://www.faros.ai/blog/ai-software-engineering)) [S]. Stack Overflow 2025: 66% cite "almost right, but not quite", and 45% say debugging AI code takes longer ([VentureBeat](https://venturebeat.com/ai/stack-overflow-data-reveals-the-hidden-productivity-tax-of-almost-right-ai-code)) [S] | Each new tool is a new thing to verify. The owner is the only reviewer. |
| **Security** | **No** | Veracode 2025: in 45% of 80 tasks across 100+ LLMs the model chose the insecure option. Java failed in over 70% of cases, and XSS defences failed in 86% ([Veracode press release](https://www.veracode.com/press-release/ai-generated-code-poses-major-security-risks-in-nearly-half-of-all-development-tasks-veracode-research-reveals/)) [S] | An unreviewed generated tool is an unreviewed attack surface |
| **Maintenance / design health** | **Worse at scale** | GitClear (211M lines): blocks of 5 or more duplicated lines rose 8× in 2024, moved (refactored) lines fell 39.9%, and copy-paste overtook moves for the first time ([devclass](https://devclass.com/2025/02/20/ai-is-eroding-code-quality-states-new-in-depth-report/)) [S] | Generating instead of reusing *is* the duplication GitClear measures |
| **Speed on mature code** | **Unclear, trending up** | METR 2025 RCT: 16 experienced developers on mature repos (22k+ stars, 1M+ lines) were **19% slower** with AI while believing they were 20–24% faster ([metr.org](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)) [S]. METR, Feb 2026: for returning developers the estimated change in task time is **−18%** (faster), CI −38% to +9%; for new recruits −4%, CI −15% to +9%. METR itself calls the signal unreliable because developers now refuse to work without AI and withhold AI-suited tasks ([metr.org](https://metr.org/blog/2026-02-24-uplift-update/)) [P] | It applies to swarm and sonic (long-lived code), not to throwaway leaf tools. The perception gap applies everywhere: **self-report cannot be the measurement.** |
| **Delivery stability** | **Worse unless the system is strong** | DORA 2025: AI is "an amplifier", and adoption correlates with throughput *and* with instability ([InfoQ](https://www.infoq.com/news/2025/09/dora-state-of-ai-in-dev-2025)) [S]. The often-quoted −7.2% stability figure is DORA 2024's [U as to which year] | The owner's guardrails (hash-bound approve, sandbox) are the "strong system" |
| **Understanding** (what does this do, why does it exist) | **No** | Bainbridge: automation leaves the operator the tasks the designer could not automate, and the operator's skill decays while monitoring ([1983 PDF](https://gwern.net/doc/sociology/technology/1983-bainbridge.pdf)) [S] | Tools the owner never read cannot be debugged by the owner when they matter |
| **Human attention / approvals** | **The scarcest resource** | Anthropic: approval fatigue is real enough that sandboxing was built to cut permission prompts by 84% ([anthropic.com](https://www.anthropic.com/engineering/claude-code-sandboxing)) [S] | Round 1's trust rule makes approvals load-bearing. Their count must be budgeted. |
| **Runs** | **Cheaper per token, not per outcome** | `03-critique-product.md` §3: $0.50–25 per composition run, minutes to hours | Generating a tool *is* a paid run. Regenerating per problem repeats the cost. |
| **Trust in operation** | **Unsolved** | Replit's agent deleted a production database during a code freeze, against explicit instructions ([Fortune](https://fortune.com/2025/07/23/ai-coding-tool-replit-wiped-database-called-it-a-catastrophic-failure)) [S] | Instructions are not guardrails. Only choke points are (Kernel D). |

**Calibration.** The negative evidence is weakest exactly where the premise is strongest:
- METR, GitClear and DORA measure large, shared, long-lived codebases.
- Veracode and Faros measure production code under review.
- None of them measures a 200-line single-purpose tool used for a week and then dropped.

So the honest reading is not "building is still expensive". It is: **generation is now nearly
free, and every cost after generation scales with how long a tool lives, how much it touches, and
how many tools a human must hold in their head.** The premise has to be shaped to stay in the
region where those costs are small.

### 1.2 What "cheap" means for this owner

| | Value | Source |
|---|---|---|
| Paid run | $0.50–25, minutes to hours | `03-critique-product.md` §3 |
| Reviewer pool | 1 person | `04` §8.1 |
| User-authored skills (last updated May–Aug 2026) | 8: `coach-me`, `execute`, `agent-team`, `1-1`, `meeting-prep`, `meeting-notes`, `todo`, `notat` | `~/.claude/skills/synced/*/manifest.json` (`creatorType: user`) |
| Hand-built products | swarm (229 commits), sonic (200), printer (50 verbs), square | `git rev-list` |

The eight skills are 57–148 lines each. They are kept, edited and dated, not thrown away. **What the
owner has actually made cheaply is durable personal tools, not per-problem disposables.** That is
the first data point against P2 as stated, and for P1 as practised.

## 2. What goes wrong when all tools are disposable

Each failure below has its mechanism, the evidence or nearest analogue, and how it would show up
in the owner's practice.

### 2.1 Sprawl and near-duplicates
- **Mechanism.** Generating is cheaper than finding, so the foundry generates. Ten problems
  produce eight "summarise these notes into decisions" tools, each slightly different.
- **Evidence.**
  - GitClear's duplication rise is exactly this at line level.
  - TroVE works only *because* it periodically trims its toolbox by usage. Its toolboxes are
    79–98% smaller than the baselines' ([ICML 2024](https://proceedings.mlr.press/v235/wang24az.html)) [S].
  - Trivial npm packages: 10.5–16% of packages are trivial. Developers believe they are well
    tested, but only about 28% have tests. Left-pad was 11 lines that broke major sites
    ([Abdalkareem et al.](https://arxiv.org/pdf/2409.18884), via survey) [S].
- **For the owner.** No registry means no reuse. A registry means a new thing to maintain.

### 2.2 Selection collapse: more tools, worse choices
- **Mechanism.** An agent must choose among tools. Every tool's description competes for context.
- **Evidence.**
  - RAG-MCP: with every tool shown, selection accuracy was 13.62%. Retrieving a relevant
    subset first raised it to 43.13% and cut prompt tokens by more than 50%
    ([arXiv 2505.03275](https://arxiv.org/abs/2505.03275)) [P, abstract].
  - Anthropic's skills use progressive disclosure (metadata first, body on demand) to survive
    many skills ([anthropic.com](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)) [S].
- **For the owner.** This session's own skill list already runs to roughly 60 entries across
  plugins. Every generated tool that is not retired makes every later choice worse.

### 2.3 Lost institutional knowledge
- **Mechanism.** If the workspace dissolves, so do the reasons: why this tool, why this
  threshold, what was tried and rejected.
- **Evidence.**
  - Bainbridge on skill decay (above).
  - Round 1's own finding that "the formats are what is expensive to change, and what must
    outlive the kernel" (FM test 15).
  - CASE and low-code drift (FM pattern 8).
- **For the owner.** Swarm's 33 handwritten `D-` entries survived because they live in a file.
  The `todo` skill's state "has no single storage file; it lives in the conversation history,
  recovered via `conversation_search`" (`todo/SKILL.md` l.63). That is exactly what dissolves.

### 2.4 Inconsistent outputs
- **Mechanism.** The same problem, solved twice by two generated tools, yields records that
  cannot be compared. The "decision" from March and the "decision" from June have different
  fields.
- **Evidence.**
  - Spreadsheets are the largest disposable-tool ecosystem ever. Field audits find errors in
    most real spreadsheets (reviews cite about 94% with at least one error, and an average cell
    error rate around 5%) ([Panko-era audits, arXiv 0801.1514](https://arxiv.org/pdf/0801.1514.pdf);
    [Tuck](https://mba.tuck.dartmouth.edu/spreadsheet/product_pubs_files/Errors.pdf)) [S].
  - Every end-user computing governance programme exists because of this.
- **For the owner.** P3 is the answer *only if* kinds are enforced on output, deterministically
  (G8 below).

### 2.5 The human drowns in approvals
- **Mechanism.** Round 1: "only a person writes `accepted`"; approvals name exact hashes. N
  tools per problem × M problems × a human act per effect means approvals grow with tool count.
  Fatigue sets in, approvals become rubber stamps, and the trust rule is hollow while still
  looking intact.
- **Evidence.**
  - Faros: the review queue absorbs the gain.
  - Anthropic's 84% prompt reduction was built *because* fatigue degrades safety.
  - ActiveX's click-through trust (FM pattern 6).
- **For the owner.** This is the decisive failure mode. See §4.

### 2.6 Security of unreviewed tools
- **Mechanism.** A generated tool is code nobody read, often with network access, run as the
  owner. A tool's *description* is also an injection surface.
- **Evidence.**
  - Veracode's 45%.
  - Invariant Labs' MCP tool-poisoning disclosure (April 2025): hidden instructions in a tool
    description led Cursor to exfiltrate `~/.ssh/id_rsa` while showing the user a benign summary
    ([invariantlabs.ai](https://invariantlabs.ai/blog/mcp-security-notification)) [S].
  - Later benchmarks report attack success above 60% across 45+ servers [U].
- **For the owner.** `03-critique-technical.md` §4.6 already shows agents running unsandboxed
  as the owner. A foundry multiplies the number of things running that way.

### 2.7 Cost of runs
- **Mechanism.** "Generate per problem" puts a paid generation run in front of every problem.
  "Evolve through use" adds variant runs. "Verify" adds critic runs.
- **Evidence.** In the TroVE re-evaluation, most of the toolbox's apparent gain was extra
  compute. Matched for compute, it fell to about 1% on MATH
  ([arXiv 2507.22069](https://arxiv.org/abs/2507.22069)) [P, abstract].
- **For the owner.** At $0.50–25 per run, a foundry that generates three candidates and a critic
  per problem costs more than reusing a kept tool, unless reuse is impossible.

### 2.8 The standard becomes the bottleneck: who designs kinds?
- **Mechanism.** If tools are cheap and kinds are what lasts, all the hard design moves into
  kinds. Each kind must be:
  - native to the domain (FM pattern 3);
  - small (FM test 3, one page);
  - stable (FM pattern 4).

  The foundry cannot generate tools until the kinds exist. If it generates kinds too, the
  standard *is* disposable, and P3 collapses.
- **Evidence.**
  - Successful standards were extracted from products that already worked: Eurorack from the
    A-100, LSP from VS Code, Unix text from tools (FM pattern 1).
  - Designed-first ontologies are the cautionary case. The semantic web's upper ontologies and
    Doctorow's "Metacrap" argument (people won't maintain metadata) [U, not re-fetched].
  - Hyrum's law: with enough use, every observable behaviour of a "disposable" tool becomes
    someone's contract [U, not re-fetched].
- **For the owner.** Round 1 found three kinds (`doc`, `decision`, `artifact`) from real
  crossings. The owner's new inputs add candidates: problem, outcome, contact or meeting, and
  action. That is already double. Kinds are where "cheap" ends.

### 2.9 Selection without a fitness signal
- **Mechanism.** Selection needs (a) variation, (b) a fitness signal, and (c) enough trials. A
  personal toolchain has plenty of (a), a weak (b) (did it help? judged by feel, and METR shows
  feel is off by about 40 points), and little (c) (a problem type recurs a handful of times).
- **Evidence.**
  - Voyager's skill library generalised to new worlds because the environment verified every
    skill and execution errors fed back automatically ([arXiv 2305.16291](https://arxiv.org/abs/2305.16291)) [S].
  - TroVE's compute-matched null result shows what is left when the verifier is weak.
- **For the owner.** Selection works where a deterministic check exists: tests pass, a quote is
  in the bytes, a schema is valid. Elsewhere "selection" is the owner's taste, and that costs
  attention (§2.5).

## 3. Does "use grows when they combine" hold?

### 3.1 When composition increases use

| Condition | Winner | Loser |
|---|---|---|
| A payload native to the domain on every cable | Unix text, Eurorack voltage | IFTTT's one-event contract, OpenDoc parts (FM pattern 3) |
| M+N contracts, not M×N glue | LSP | Mashups, Segment (FM pattern 7) |
| Pre-built combinations as the front door | Zapier's per-pair and per-workflow pages | Yahoo Pipes' blank canvas (FM pattern 2) |
| Composition happens in code or files, not in the model's context | Anthropic's "code execution with MCP": 150,000 → 2,000 tokens (98.7%) on a Drive → Salesforce flow ([anthropic.com](https://www.anthropic.com/engineering/code-execution-with-mcp)) [S] | Every tool loaded into context (RAG-MCP's 13.6%) |
| Each combination is cheap to verify | Spreadsheet formulas (visible values) | Agent chains whose middle steps nobody reads (LangChain, FM pattern 8) |

### 3.2 When composition is a tax
- **Network value grows sub-quadratically.** Odlyzko and Tilly argue n log n, not Metcalfe's n²,
  because most potential links are worth little
  ([IEEE Spectrum](https://spectrum.ieee.org/computing/networks/metcalfes-law-is-wrong)) [S]. For
  one user, the valuable links are the handful of real crossings (round 1 found one:
  research → decision → swarm basis).
- **Generating apps does not solve composing them.** Ink & Switch's *Malleable Software* essay
  (June 2025) makes the same point independently: chat-generated apps are easy, but how
  generated tools compose with each other, and how users tweak rather than regenerate, is open
  ([inkandswitch.com](https://www.inkandswitch.com/essay/malleable-software/)) [S].
- **Risk grows with links.** Every edge is a contract someone can break: left-pad, OSGi version
  hell (FM pattern 4), Segment's shared-library drift.
- **Discovery costs grow with nodes** (§2.2).

### 3.3 The owner's own evidence: eight skills that already compose

From `~/.claude/skills/synced/*/SKILL.md`:
- `todo` sweeps open actions out of `/meeting-notes` and `/1-1`.
- `meeting-notes` reads the `/meeting-prep` document.
- `notat` references four siblings (`coach-me`, `meeting-notes`, `meeting-prep`, `todo`).

This is P7 happening without a kernel. **The composition tax is visible in the prose:**
- The glue is `conversation_search` over chat history, with no typed record.
- `todo` must run "a separate, dedicated search round" for 1:1s, "Do not assume the meeting
  search covered these; it usually won't", and it hard-codes search vocabulary ("action-liste",
  "opsamling", "Opdateret action-liste").
- `meeting-notes` states that carrying actions into the next prep is "Planned, not built … Don't
  improvise this loop".

So the skills compose, but by string matching on remembered phrasing. That is the Unix-haters'
complaint ("every pipe is a parser", FM pattern 3) in its LLM form.

**Verdict on P7:** use grows when a combination is cheaper to make *and to trust* than doing the
step by hand. That happens when a small typed record (here, an `action`) replaces the search
glue. It does not happen by multiplying tools. Experiment E2 tests this directly.

## 4. The central tension, and the cut that resolves it

Round 1's spine:
- only a person makes anything authoritative;
- a human act names exact hashes;
- a verifier stands at each sink (`04` §2, Kernel D in `03-critique-technical.md` §7).

Put disposable, generated tools on top:

| If trust attaches to… | Then each new tool needs… | Result |
|---|---|---|
| **the tool** (reviewed, signed, installed) | a human review of its code | Reviews grow with tool count. Disposability is impossible, and the owner drowns (§2.5). |
| **the tool's outputs, checked at the sink** | nothing. Tools are untrusted by construction. | Reviews grow with *effects*, not tools. Disposability is safe. |

**The second row is the only version of the premise that survives.** It is Kernel D's cut, and
it turns D from "deferred until friction demands it" (`04` §3) into the *precondition* for
round 2. Concretely:
- A generated tool runs sandboxed, holds no credentials (`04` §6b.3) and can write only `doc` or
  `proposed` records.
- Spend draws on a human grant, so a bad tool wastes its grant and nothing more.
- Every effect (accept, merge, publish, post) passes a verifier over exact hashes.
- **Verification moves from "is this tool correct?" to "is this record valid for its kind?"**
  That check is deterministic where possible (schema, quote in the bytes, tests pass) and a
  batched human act where not.

**Two more contradictions round 2 must resolve explicitly:**

1. **Kinds before tools vs monolith-first.** A foundry needs kinds to generate against. Round 1
   says kinds come from crossings. *Resolution:*
   - The foundry may emit tools only over **existing** kinds.
   - A new kind is *promoted* when the same ad-hoc shape has crossed between tools at least
     three times, and the owner accepts it.
   - The kind list stays at one page.
2. **Dissolving workspaces vs cross-project memory.** *Resolution:*
   - **Tools and scratch dissolve. Records persist.** The problem, decisions, outcome, contacts
     and provenance stay.
   - "Dissolve" means *unlisted*, not deleted: the tool's source hash stays in provenance, so a
     record made by a dead tool can still be explained.

## 5. Steelman: where the premise is right and round 1 was too conservative

1. **Round 1 treated every tool as a product that must earn its existence** (FM test 1,
   monolith-first). That is right for *kept* tools and the kernel. For leaf tools it is wrong.
   Willison's rule is that a few hundred lines don't need to be maintainable because an LLM
   rewrites them in minutes. It turns "maintain" into "regenerate" for a whole class of tools.
   Round 1 never drew that class line.
2. **Round 1 benchmarked against the "null kernel" (Claude Code plus skills) as a rival to
   beat.** The premise reframes it as *the foundry that already exists*. The owner's eight self-authored skills,
   already composing, are the strongest evidence in this folder. They are
   stronger than anything iteration 2's kernels showed.
3. **Round 1's slice is module-centric** (`decide`, `research`, swarm). The owner's later input,
   "the flow starts with the problem" (`STATE.md`), is a better spine. Problem → outcome is the
   unit the owner cares about, and modules serve it. "The problem is the app" is right as a
   *spine*, even if wrong as "nothing else persists".
4. **"Standard lasts, tools are disposable" is round 1's own best finding, generalised.** Round 1
   said formats are durable and the runtime is disposable (`03-critique-product.md`,
   implications 3). The premise extends that from the runtime to the tools. That extension is
   consistent, not radical.
5. **The trend favours the premise.** METR's task-time estimate moved from +19% (slower, 2025) to −4% to −18% (faster, 2026; both CIs include a slowdown), and
   its main caveat is that developers no longer accept working without AI. Generation will get
   cheaper. A design that assumes today's generation cost will be too conservative within a
   year.
6. **Composition in code is now cheap for agents** (the 98.7% token saving). Round 1's "no
   canvas, compose by conversation that writes a file" is exactly the medium in which generated
   glue is cheap. Round 1 underused its own conclusion.

## 6. What survives

| Claim | Verdict | Condition |
|---|---|---|
| P1 Building is cheap | **Partly.** Generation yes; verification, attention and trust no. | Measure owner-minutes and $ per *outcome*, not generation time |
| P2 Tools are disposable | **Survives for a class** | Leaf, stateless, small, no sink access, untrusted by construction (G1, G6) |
| P3 The standard lasts | **Survives, and becomes the hard part** | Kinds promoted from crossings, closed list, deterministic checkers (G3, G8) |
| P4 Evolution through selection | **Weak by default** | Only where a deterministic fitness check exists. Elsewhere it is curation by the owner, budgeted (G2) |
| P5 A foundry replaces hand-built modules | **Replaces leaves, not the spine** | Kept: the record store, the verifiers, the sink integrations, swarm. Generated: the leaf transformers (G4, G6). |
| P6 The problem is the app; workspaces dissolve | **The spine survives; dissolution needs a split** | The problem record is the spine. Tools and scratch dissolve; records persist (G5). |
| P7 Use grows when combined | **Conditional** | A typed record replaces search glue, the M+N contract holds, and discovery is retrieval rather than listing |

## 7. Guardrails any round-2 design must meet

Each guardrail can be checked from files, in the style of `04` §6's kill table.

| # | Guardrail | Pass if | Fail if |
|---|---|---|---|
| **G1** | **Trust is never a property of a tool.** A generated tool runs sandboxed, with no credentials or integration tokens, and can write only `doc` or `proposed`. Every effect passes a sink verifier over exact hashes. | A grep of generated-tool descriptors finds no grant beyond read-plus-`proposed`. Every accepted, merged or published record has a human act naming its hash. | Any generated tool holds a token, writes `accepted`, or reaches a sink without the verifier |
| **G2** | **Owner attention is budgeted and measured.** The design states the human acts per outcome and batches them. | A log shows owner-minutes and human acts per problem. Acts per problem stay flat as the tool count grows. | Approvals scale with the number of tools, or nobody can say how many minutes an outcome cost |
| **G3** | **Kinds are closed and promoted, never generated.** The foundry emits tools only over existing kinds. A new kind needs at least three observed ad-hoc crossings plus an owner accept. | The kind list fits on one page (≤ about 7). Each kind cites the crossings that justified it. | The foundry introduces a kind, or two tools emit incompatible shapes under one kind name |
| **G4** | **Reuse before generate.** The foundry searches existing tools by descriptor (kinds in/out) first and logs why it generates instead. Unused tools are retired on a timer (TroVE-style trimming). | The near-duplicate rate is reported. The listed tool count is bounded. Retirement runs. | The tool list only grows, or two listed tools have the same in/out kinds and purpose |
| **G5** | **Records outlive tools and workspaces.** Dissolving a workspace leaves problem, decisions, outcome, contacts and provenance readable. A dead tool's source hash stays in provenance. | Delete any tool or workspace, and every record still answers "what, why, from what, by which tool version" | An answer requires a tool that was disposed of, or a chat transcript (swarm principle 7) |

**Note on G5.** The owner's cheapest tools (the eight skills) appear to run in claude.ai chats and
keep state in conversation history [U as to surface]. They live outside git. So "records persist"
needs a store that both claude.ai and Claude Code can reach. That challenges round 1's
files-in-git assumption (`04` §2), which only Claude Code-side tools satisfy today.
| **G6** | **Disposability has a line.** Disposable means leaf, stateless, under about 300 lines, and no sink access. Anything over the line is a *kept* tool, with tests and the conformance suite (FM test 7). | Every tool is classed. Kept tools have tests. | A "disposable" tool holds state other tools read, or touches a sink |
| **G7** | **Generation is a paid run under a grant.** Cost per outcome is generation runs + use runs + review minutes, and generate-vs-reuse is compared on it. | Per-problem cost lines exist, and the foundry's choice can be audited | Generation is "free" in the accounting |
| **G8** | **The output is verified, not the tool.** Every kind has a deterministic checker: schema, quote in the cited bytes, tests. Only what fails or cannot be checked goes to the human queue, and the design states that share. | The checker exists per kind. The human-queue share is reported. | Validity rests on "the tool was reviewed" or on the owner's reading of every output |

## 8. Three cheap experiments, two weeks, in the owner's own practice

All three use what exists: Claude Code, the eight skills, and swarm. None needs a kernel. Each
writes a log file, so the result is read from data, not recalled. METR's 40-point perception gap
is why self-report does not count.

### E1. Generation vs verification: the foundry shadow log
- **Setup (½ day).** For 14 days, every tool, script or skill the owner would want is generated
  into `~/www/foundry-trial/<date>-<slug>/`.
  - Each tool has a 6-line descriptor: kinds in/out, lines, $ for generation, and timestamps
    for *prompt sent → tool works → owner trusts it*.
  - Owner minutes spent reading, debugging or re-prompting are logged as they happen.
- **Measure.**
  - Generation minutes vs owner verification minutes per tool.
  - Reuse at day 14: did the tool run again, or serve as a template?
  - Near-duplicates: same in/out kinds and purpose.
  - Total $.
- **Confirms P1/P2 if:** median owner-minutes to trust is ≤ 15 per tool, at least 30% are reused
  or remixed, and near-duplicates are under 20%.
- **Refutes if:** verification minutes are at least 3× generation minutes, reuse is under 10%,
  or more than a third are near-duplicates. In that case "cheap" is generation-only, and the
  foundry needs G4 and G6 as hard rules, not options.

### E2. Does a typed record make use grow? On the existing skills
- **Surface first.** The skills glue on `conversation_search`, so they most likely run in claude.ai
  chats, not Claude Code [U]. The local copies in `~/.claude/skills/synced/<uuid>/` are a managed
  sync target (`manifest.json`, `.last-complete-round`), so edits must go to the *source* skills
  where the owner authors them, not the synced directory.
- **Setup (1 day).**
  - Introduce one kind, `action` (`{id, text, owner, due?, source: skill+date, status}`). Keep it
    in a store the skills' surface can reach: one Claude Docs doc or an artifact database for
    claude.ai, or Markdown files in a folder if the trial runs in Claude Code.
  - Edit the source of `meeting-notes`, `1-1` and `todo` to write and read it, instead of
    sweeping with `conversation_search`.
  - Leave `notat`, `meeting-prep` and the `morning` brief untouched, and do not tell them about
    it.
- **Measure.**
  - Weekly, the owner checks the action list against ground truth (the meetings actually held).
    Count missed and phantom actions, before and after.
  - Unplanned uses: does any other skill or session start reading `action` records without
    being designed to (for example `notat` citing open actions, or a prep pulling them)?
  - Time per `/todo` sweep.
- **Confirms P7 if:** missed actions drop, and two or more unplanned uses of the record appear
  in two weeks.
- **Refutes if:** the record adds friction (the owner bypasses it) and no new use appears. That
  would mean search glue is good enough at this scale, and kinds should stay few and late.

### E3. Problem-as-app with dissolving workspaces
- **Setup.** Pick two or three real problems from the next two weeks, for example the owner's
  "who have I talked to, meetings, outcomes" data collection, or "how should square store saves".
  - For each, work in a throwaway workspace with generated tools.
  - At the outcome, keep only the records: problem, decisions, outcome, contacts, provenance with
    tool hashes. Delete the workspace.
- **Measure (day 14).**
  - Ask ten cross-problem questions written *before* the trial, such as "what did I decide about
    X and why" and "who did I talk to about Y". Count how many the persisted records alone
    answer.
  - Count how often the owner reaches for a dissolved tool, and what regenerating it cost.
- **Confirms P6 if:** at least 8 of 10 questions are answerable from records, and regeneration
  happens at most once and cheaply.
- **Refutes if:** the owner needed a dissolved tool twice or more, or answers needed chat
  history. In that case dissolution destroys value, and "kept vs disposable" must be decided at
  creation (G6), not at the end.

**Reading them together.**
- If E1 and E3 confirm, P2 and P6 hold for this owner and the foundry is worth building, with
  G1–G8.
- If E2 confirms, the first round-2 investment is kinds and records, not the foundry.
- If all three refute, round 1's slice stands, with the problem record added as its spine.

## What is the cable/jack/patch here

| Patch-bay concept | Under the premise, after this critique |
|---|---|
| Module | Two classes: **kept** (record store, verifiers, sink integrations, swarm) and **disposable** leaf tools, generated, untrusted, unlisted when idle |
| Jack kind | The durable standard. Closed, one page, promoted from crossings, each kind with a deterministic checker |
| Cable | A typed record passed by hash, not a search over chat history |
| Patch | A problem's workspace: generated, dissolvable. Its records persist. |
| Non-modulatable param | Accept, merge, publish and spend: human acts over exact hashes at sinks, budgeted in count |
| Preset | A kept, reused composition, promoted when a disposable one recurs |

## Implications for round 2 (for `06-synthesis`)

1. Adopt Kernel D's cut as a precondition, not a later upgrade: **trust lives at sinks and on
   records, never on tools.** Without it the premise drowns the owner.
2. Draw the line between kept and disposable tools explicitly (G6). The foundry generates leaves
   only.
3. Make kinds the expensive, slow, human-promoted part (G3). Start with round 1's three plus the
   owner's candidates (problem, outcome, action, contact) *only as crossings justify them*.
4. Replace "workspaces dissolve" with "tools dissolve, records persist" (G5).
5. Budget owner attention as the scarce resource (G2) and measure cost per outcome (G7).
6. Run E1–E3 before building a foundry. The owner's eight composing skills are the testbed.
