# 05 — Invariants: what holds when tools are nearly free

Round 2, iteration 5, track "invariants". This track asks what stays fixed when the
premise changes. It does not design how tools get made (05-foundry) or which ones survive
(05-selection). It names the invariants those mechanisms will rely on.

**The premise, from the owner:** developing workflows and tools has become cheap, and if
they can be combined, their use grows. The flow starts with the problem. Capture happens in
many places. Who you talked to, meetings and outcomes must be collected. Integrations are
edge modules.

**The claim of this document in one sentence:** when tools are cheap, *durability moves
from tools to records*. The standard must therefore define what makes a record trustworthy,
meaningful and judgeable without its tool, and nothing else. Every other part of round 1's
design either becomes cheaper, becomes a tool, or disappears.

Claims are written to be contestable. Each scarcity claim has a falsifier. Sources are at the
end of the relevant section, and unverified ones are flagged.

---

## 1. What exactly got cheap

"Tools are cheap" is too loose to reason from. What got cheap is narrower:

| Got cheap (≈ minutes, ≈ $0–5) | Did *not* get cheap |
|---|---|
| Writing the code of a small tool: CLI, single-file HTML page, skill, MCP wrapper | Knowing whether that code is right |
| Glue: an adapter from format A to format B | Knowing whether the adapter preserved meaning |
| UI: a view over some records | Deciding what the records should mean |
| Drafts, summaries, extractions, proposals | A human deciding which proposal binds |
| Re-running a workflow | Getting the *same* result twice (models are nondeterministic) |
| A first version | A version someone has used for a month and trusts |

Evidence that this is the actual shape and not wishful thinking:

- Simon Willison reports building 150+ single-file "HTML tools" in two years, "almost all of
  them written by LLMs" ([Useful patterns for building HTML tools, Dec 2025](https://simonwillison.net/2025/Dec/10/html-tools/)).
  The patterns he names are telling: single file, no build step, state in URL or
  `localStorage`, copy/paste as the I/O. These are tools whose *interface* is the clipboard,
  because there is no shared substrate to read from.
- Anthropic's Agent Skills (Oct 2025) make a tool a folder of instructions plus optional
  scripts, loaded on relevance, and ship a `skill-creator` skill that writes new ones
  ([Anthropic engineering: Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).
  A tool is now a text file an agent writes.
- "Imagine with Claude" (Sep–Oct 2025) generated the behaviour of an interface on the fly,
  with no code prewritten. *Sourced only from secondary write-ups*
  ([DataCamp tutorial](https://datacamp.com/tutorial/imagine-with-claude)); unverified
  against Anthropic's own page.
- The cost that did not fall: Sonar's State of Code survey (1,100+ developers, published Jan
  2026) reports 96% do not believe AI-generated code is functionally correct, and only 48%
  always check it before committing ([The Register, 9 Jan 2026](https://www.theregister.com/2026/01/09/devs_ai_code/)).
  Karan Sharma's piece on home-cooked software names the same residue: the last 20%, the
  verification burden, and "systems you don't fundamentally understand"
  ([mrkaran.dev, Oct 2025](https://mrkaran.dev/posts/ai-home-cooked-software/)).
- Ink & Switch's malleable software essay is the most careful statement of the limit:
  "AI code generation alone does not address all the barriers to malleability", and
  "Bringing AI coding tools into today's software ecosystem is like bringing a talented sous
  chef to a food court." The missing piece they name is *shared data*: "when each
  application manages its own data, introducing a new tool into a workflow incurs more
  friction" ([Malleable Software, Litt et al., Jun 2025](https://www.inkandswitch.com/essay/malleable-software/)).
- The idea is older than LLMs. Clay Shirky's "Situated Software" (2004) described software
  "designed in and for a particular social situation", for "dozens of users"
  ([gwern mirror](https://www.gwern.net/doc/technology/2004-03-30-shirky-situatedsoftware.html)).
  Robin Sloan's "An app can be a home-cooked meal" (2020) is the canonical example
  ([robinsloan.com/notes/home-cooked-app](https://www.robinsloan.com/notes/home-cooked-app/)). What changed in 2025 is that
  the cook no longer needs to be a programmer.
- The "disposable software" genre (e.g. [HackerNoon: SaaS is dead](https://hackernoon.com/saas-is-dead-why-software-is-becoming-disposable),
  [ChatBotKit: thoughts on disposable software](https://chatbotkit.com/reflections/thoughts-on-disposable-software),
  [Deepak Gupta: just-in-time software](https://guptadeepak.com/future-tech/just-in-time-software/))
  is opinion, not evidence. One line in the genre is worth keeping because it is the thesis of
  this document: temporary modules that close after serving their function and leave behind
  only the data their users choose to keep (*a search-engine summary of the genre, not
  attributable to any one of these pages; unverified*).

**The consequence the premise implies but does not state:** if tools are cheap and
nondeterministic, *re-running a tool is not a way to recover what it produced*. Round 1
treated projections as regenerable (true, they are deterministic). Under this premise most
tool output is not regenerable. What a model concluded on Tuesday from a meeting transcript
cannot be re-derived on Friday. So it has to be kept as a record, with the tool that made it
named.

> **Invariant 0: regenerability decides durability.** Anything that can be regenerated
> deterministically is cache (projections, views, the tools themselves, given their source).
> Anything that cannot be regenerated is a record: observations of the world, human acts,
> external fetches, and every model output that something later relied on.

## 2. The scarcity ledger

Each line: what is scarce, why, and what would prove the claim wrong.

### 2.1 Scarce

**S1. Human judgment, counted in acts per day.** Proposals scale with compute. The number of
times a day the owner can read a diff and mean "yes" does not. It is roughly fixed, maybe
20–50 meaningful acts a day for one person alongside a real job (*estimate, not measured*).
Every cheap tool that emits proposals competes for this budget.
*Falsifier:* if, after a month of use, the owner's accept/reject acts per day stay well below
what they would comfortably do, judgment is not the bottleneck and the design should spend
less on making acts cheap.

**S2. Verified trust in outputs, which is not the same as trust in tools.** Split it:
- *Trust in a tool's code* is cheap to obtain by regenerating, and expensive to obtain by
  reviewing. Under the premise nobody reviews most tools. So the standard must not depend on
  any tool being correct.
- *Trust in a record* comes from its provenance (who or what made it, from which inputs) and,
  for binding records, from a human act over its exact bytes. That does not get cheaper, and
  it is the only kind of trust the standard can enforce.
*Falsifier:* if generated tools reach a quality where unreviewed output is reliably correct
for the owner's work (say, outcomes judged "met" don't degrade when review is skipped),
trust in tools becomes cheap and the record-level machinery is overhead.

**S3. Shared meaning.** Ten tools can write a field called `status`. Whether they mean the
same thing is not something a tool can generate; it is an agreement. Cheap tools *multiply*
the places where meaning can drift. Shared, stable names are scarce in exact proportion to
how many tools there are.
*Falsifier:* if LLM readers reliably reconcile divergent field meanings at read time (so a
reader never acts on the wrong reading of `status`), typed names matter less than round 1
thought. The data-model research (01-data-model §3.2, "type thin, text thick") already bets
the other way for routing fields.

**S4. Accumulated context about the world.** Who said what in a meeting, what was tried, what
happened. This cannot be generated, only captured, and only at the time. It is the one asset
that compounds: a tool made today is worth more if three months of records exist for it to
read. Ink & Switch's "shared data substrate" point is this point.
*Falsifier:* if the owner, given a fresh problem, gets equal value from a tool with no history
as from one with history, accumulated context is not the asset.

**S5. Problem clarity.** When building is cheap, the limiting step is saying what is wrong and
what "solved" would look like. A sharp problem with criteria lets a cheap tool be judged; a
vague one makes every tool look plausible. This is the owner's "flow starts with the problem",
restated as a scarcity.
*Falsifier:* if outcomes are equally good when problems are stated in one line without
criteria, criteria are ceremony.

**S6. Money, moved from build time to run time.** Round 1's $0.50–25 per swarm round still
holds. Cheap to *build* is not cheap to *run*: a tool that calls a model on every capture
costs money every day it lives. Cost does not disappear; it moves to where nobody looks.
*Falsifier:* if run costs for the owner's tools stay under, say, $20/month total with no
caps, cost is not scarce and budget fields are noise.

**S7. Access to the world: credentials and the right to act.** A token for GitHub, mail or
Slack is not cheap, because what it can do is not reversible. Under the premise many more
tools will want one.
*Falsifier:* none plausible for outbound effects. This one is structural.

### 2.2 Abundant

**A1. Tool code, UI and glue.** Including adapters between formats (round 1's M×N problem).
**A2. Text: drafts, summaries, extractions, proposals.** Abundant to the point of being
noise. The standard should make it cheap to *ignore* them, not cheap to make them.
**A3. Variants.** Five versions of a tool that do almost the same thing. Abundance here is a
cost, not a benefit (§3, N1).
**A4. Workflows.** A composition is a paragraph an agent turns into a script. Round 1's "patch
as plain data" is still right, but the patch is now cheap to throw away as well.

### 2.3 What this ledger implies

The scarce things are all properties of *records and acts*: trust (provenance, acts),
meaning (names), context (history), clarity (problems with criteria), judgment (acts), and
access (grants). None of them is a property of a tool. That is the argument for the rest of
the document: **the standard is about records and acts; tools are free to be anything that
reads and writes them correctly.**

## 3. Round-1 failure modes under the premise

Round 1's ten patterns (01-failure-modes) were derived from a world where a module costs
months. Rechecked:

| # | Pattern | Under cheap tools | Why |
|---|---|---|---|
| 1 | Platform before product | **Holds, moved.** | No single tool needs to be a killer product, because a tool costs an afternoon. But the *substrate* must be useful alone: capture plus a problem view, with no other tool. If the record store is only useful once composed, it is Wave again. |
| 2 | Blank canvas | **Inverts, then reappears.** | An agent turns a sentence into a composition, so wiring is no longer a tax. The tax moves to the *blank problem*: stating what is wrong and what "done" means (S5). The front door is a problem template, not a preset patch. |
| 3 | LCD interface | **Holds.** | "Type thin, text thick, coerce explicitly" is unchanged. LLMs make text richer to read, not safer to act on. |
| 4 | Version skew | **Gets worse and changes shape.** | Not library versions but *semantic* skew: near-duplicate tools writing the same names with different meanings (N4). Namespaced types and additive evolution matter more, not less. |
| 5 | Unbounded power freezes the host | **Inverts.** | There is no host to freeze. A tool that touches everything is thrown away and regenerated. What freezes now is the *format*: every record ever written is a client of it. |
| 6 | Security bolted on | **Gets much worse.** | Unreviewed generated code running as the owner, with the owner's credentials. Review cannot be the defence (S2). Sandbox plus explicit grants is the only defence that scales with tool count. |
| 7 | Glue explosion (M×N) | **Inverts.** | Glue is free. But each generated adapter is a coercion that can be wrong, so it must stamp provenance. M×N is no longer a build cost; it is a trust cost. |
| 8 | Opaque boundaries | **Gets worse, moves.** | Nobody read the code, so "inspect the module" is gone as a debugging strategy. Inspection must happen at the records: what went in (by hash), what came out, which tool by source hash. |
| 9 | Owner dependency | **Inverts for tools, holds for models.** | You own every tool; you depend on a model vendor for all of them. A deprecated model breaks every tool at once, and outputs cannot be regenerated identically after it. Another reason records must be kept, not recomputed. |
| 10 | Unprotected edges in the standard | **Holds, harder.** | Tool authors are now agents doing the plausible thing at speed. The must-do-right things (envelope, provenance, never self-accept) must be enforced by a validator, not by documentation. |

**New failure modes** that round 1 could not see because tools were expensive:

- **N1. Tool sprawl and near-duplicates.** Twelve capture tools, four meeting-note
  formatters, each almost right. The owner cannot remember which one wrote what. Mitigation
  in the standard: provenance names the tool by source hash, and the tool is itself a record
  `about` a problem, so sprawl is queryable. Selection is 05-selection's job.
- **N2. Plausible, unverifiable output.** Records that look right, cite nothing and drive
  decisions. Mitigation: provenance with input hashes is mandatory on every machine-written
  record, and nothing machine-written binds anything.
- **N3. Context fragmentation.** Capture in many places means records scattered across many
  tools, each holding its own little store (Willison's `localStorage` pattern is exactly
  this). Mitigation: one store, and a tool that keeps private state is a tool whose output
  does not count. Round 1 already flagged long-lived private state as a hidden channel (04 §9).
- **N4. Semantic drift.** The same name, different meanings, across tool generations. This is
  the cheap-tool form of version skew. Mitigation: types are namespaced and their definitions
  are records; a new meaning gets a new name, never a reused one.
- **N5. Orphaned records.** The tool that wrote a record is gone, and the record's body only
  made sense to that tool. Mitigation: every record must render to readable text without its
  tool. Round 1's test 15 ("outlives the kernel") becomes "outlives *every* tool", and it
  becomes the main test.
- **N6. Goalpost drift.** Success criteria get edited after the fact so the outcome looks
  like success. Cheap rewriting makes this effortless and invisible. Mitigation: an outcome
  pins the exact revision of the criteria it was judged against.
- **N7. Personal data about third parties.** "Who did I talk to, what did they say" is
  personal data about people who never agreed to be in a tool. The research is written
  for a Danish owner (STATE.md and the syntheses are in Danish), so GDPR applies: a lawful basis, minimisation, the ability to find and delete
  everything about one person. Cheap capture tools will over-collect by default. This is a
  real constraint on the standard, not a footnote: a person must be a single identifier that
  every record about them can be found by.
- **N8. Attention flooding.** Proposal volume exceeds judgment (S1). The failure is
  rubber-stamping: acts that name hashes nobody read. Round 1's interactive confirmation per
  accept protects against accidents but invites fatigue at volume.
- **N9. Forgotten automations.** A tool built in an afternoon keeps running and spending.
  Mitigation: anything that spends needs a grant with a bound and an expiry.
- **N10. Non-reproducibility mistaken for reproducibility.** "We can just re-run it" is false
  for model output. A design that recomputes instead of keeping will silently change history.

**Round 1's 16 tests, reweighted.** More important: 9 (capability), 11 (plain data), 12
(probe), 13 (escape hatch), 15 (outlives the kernel, now "outlives every tool"), 16 (budget).
Less important: 1 (single module), 2 (monolith first: a boundary is cheap to redraw *between
tools*, still expensive *in formats*), 6 (M+N, glue is free), 14 (front door, an agent builds
it on request). Unchanged: 3 (one-page spec), 4 (native payload), 7 (conformance), 10 (skew).
New tests to add: **N5 orphan test** (delete the tool; is every record it wrote still
readable and attributable?) and **N6 goalpost test** (edit the criteria; does the old outcome
still point at what it was judged against?).

## 4. The voltage standard

Eurorack works with 1,000+ makers because a maker needs one page: jack size, voltage range,
1 V/oct, power header. Under this premise the makers are agents writing a tool in an
afternoon with no other context. So the requirements are:

1. **It fits on one page an agent can read in one go**, and
2. **it is checked by an executable validator**, because agents will not follow prose
   reliably (pattern 10), and
3. **it never depends on a tool being correct** (S2), only on records being honest about
   where they came from and on humans acting over exact bytes.

### 4.1 The envelope

Every record, whatever tool wrote it:

| Field | Required | What it is | Why it is invariant |
|---|---|---|---|
| `id` | yes | ULID per subject, stable across revisions | Round 1. Identity outlives tools. |
| `rev` | computed | sha256 of the canonical bytes | Round 1. What acts and links pin. |
| `kind` | yes | one of the closed set in §4.2 | The only thing every tool must understand. |
| `type` | yes | namespaced, e.g. `note.meeting`, `kb.source` | Open-ended, additive. A new meaning gets a new name (N4). |
| `about` | no, many-valued | problem ids this bears on | The spine, see §4.3. |
| `links` | no | typed refs by `rev`: `derivedFrom`, `supersedes`, `answers`, `judges` | Round 1. |
| `people` | no | person ids this record is about or involves | §4.4. The GDPR handle (N7). |
| `by` | yes | `human:<id>` or `tool:<sha256 of tool source>` plus model id if any | Provenance must resolve after the tool is gone (N5). A name is not enough. |
| `inputs` | yes if `by` is a tool | `rev`s of the records the tool read | N2. No silent context. |
| `origin` | yes if fetched or captured from outside | `{system, externalId, url, fetchedAt, sha256}` | Round 1 §6b, unchanged. |
| `cost` | if spent | tokens, $ | S6. |
| `at` | yes | time | |

The body is Markdown or JSON, and **must render as readable text without any tool**. If the
body is JSON, the record carries a short human summary. This is the orphan rule (N5).

The store stamps `rev`, `at` and, where it can, `by` and `inputs`. Round 1's Datomic lesson
holds: the author will forget. Where the store cannot stamp (a tool running outside it), the
validator refuses records without them.

### 4.2 Kinds: what rules attach to

The test for a kind is round 1's three questions (coercible? authority? value or event?) plus
one more: **does the standard need to apply a rule to it?** If not, it is a `type` inside
`note`.

| Kind | Rule that attaches | Comment |
|---|---|---|
| `note` | none; the universal input | Round 1's `doc`, renamed because "doc" suggests a long document and most captures are three lines. Meetings, contacts, research, drafts, transcripts are all types here. |
| `problem` | its **criteria** are binding only through an act; it is what `about` points at | §4.3. |
| `outcome` | must pin the `problem` rev (and so its criteria) it judges; its **verdict** binds only through an act | The feedback record round 1 never had. |
| `decision` | binds only through an act | Round 1, unchanged. |
| `act` | only `by: human:*`; names exact `rev`s; closed verb set | Round 1's "human action", promoted to a kind because every rule above points at it. |
| `artifact` | bytes by reference only | Round 1, unchanged. |

Six kinds. The interesting thing is that **authority no longer lives in kinds; it lives in
acts.** Round 1 had to make `decision` strict and argued about whether `task` and `signal`
were strict kinds. Here every strict thing is the same shape: a record that is `proposed`
until an `act` names its `rev`. A problem's criteria, an outcome's verdict, a decision, a
spend grant, an outbound send. One mechanism, one validator rule.

The closed verb set for acts: `adopt` (a problem and its criteria), `accept`/`reject` (a
decision), `judge` (an outcome's verdict), `grant` (spend, credentials, or running unattended,
always with a bound and an expiry), `send` (an outbound effect: post, merge, publish).
Default-deny for everything else.

Batch acts are legal: one act may name many `rev`s. That is the answer to N8, with a cost:
the act records exactly which revs it named, so a later reader can see that 40 proposals
were accepted in one second, which is itself a signal (05-selection may want it).

### 4.3 Is "problem" a kind, a type, or the envelope's root?

Three candidates, tested against the owner's other requirements:

**Root (every record must have exactly one `about`).** Fails three ways:
- Capture happens before a problem exists. The owner's note from a hallway conversation is
  written before anyone knows which problem it bears on. A mandatory root makes capture
  either refuse or guess.
- One note bears on several problems. A meeting covers three topics.
- Problems nest and fork. "Square's saves are fragile" splits into storage and migration.
  A single root forces a tree where reality is a graph.

**Type inside `note`.** Fails on authority. The outcome is judged against the problem's
success criteria. If criteria are just text in a note, anyone (any tool) can rewrite them and
the outcome quietly passes (N6). Criteria are binding, so they need the act rule.

**Kind, with `about` as a many-valued, late-bindable link.** Passes:
- `about` is optional at write time. A record with no `about` is legal and shows up as
  *unfiled*. Filing is an attention task, and an agent may *propose* `about` links.
- `about` can be added after the fact by a sidecar record (a `note` of type
  `link.about` that names the target `rev` and the problem). This lets capture tools stay
  dumb and lets the link have its own provenance: "the triage tool thought this was about P".
- The spine is a property of *navigation* ("show me everything about P"), not of *writing*.

**So: `problem` is a kind, `about` is the spine, and the spine is assembled, not imposed.**

**Name collision to fix now.** Swarm already uses `problem` for something else: in
`src/loop/engine.ts` and `src/loop/page.ts` a feature can be in `kind: 'problem'`, a
blocker/error state waiting for a human ("Empty to continue, or what to do"), and round 1
listed it as a `signal` (01-data-model §4). Meanwhile swarm's classic board already has the
owner's sense: `featureLifecycle.ts` says accept "is the human saying it solved the problem",
and "every evaluation names the delivery it judged … the spec revision", which is an outcome
pinned to a revision. **Recommendation:** the standard keeps `problem` for the spine; swarm's
loop renames its blocker state to `blocked` or `stuck`. Note also that the classic board,
which holds the only existing outcome-like code, is on D-033's deletion path.

### 4.4 Person, meeting, task: needed?

Through round 1's three tests plus "does a rule attach?":

- **Person: not a kind; an identifier.** A person is not a statement someone makes; they are
  the subject of many. What the standard needs is a *stable person id* that every tool uses,
  so "who did I talk to about P" is a join and not a search. Contact details are a `note` of
  type `person`, keyed by that id. Identity resolution (is "Mette" in the calendar the same
  as "mette@…" in mail?) is scarce work (S3) and its result is a proposal like any other. The
  `people` field in the envelope is justified by N7: deleting or exporting everything about
  one person must be one query.
- **Meeting: a type of `note`**, `note.meeting`, with `at`, `people`, `about`. No rule
  attaches to it that does not attach to any note. The owner's "data about meetings" is
  satisfied by the envelope fields, not by a kind. A calendar integration writes these with
  `origin`.
- **Task: not a kind.** Round 1 (01-data-model) made `task` a kind because it spends money.
  Under one-mechanism authority, what spends money is the `grant` act, and the task is a
  `note` (or a swarm feature) that a grant names. Swarm's features keep their own lifecycle;
  the standard only needs to know that spending required a grant over that rev.

So the owner's data-collection list (people, meetings, outcomes) costs the standard one
kind (`outcome`) and one envelope field (`people`). Everything else is types.

### 4.5 The tool contract

A tool is itself a record: a `note` of type `tool` (or an `artifact` holding its source),
with:

- `reads`: which kinds/types it consumes,
- `writes`: which kinds/types it produces (never `act`; acts go through the presence-gated
  path, §4.6),
- `needs`: grants it requires (network, credential, budget, unattended),
- `about`: the problem it was made for.

The `by` field in every record it writes is the sha256 of its source, so provenance resolves
to the tool record even after the tool is deleted from disk. That is all. How the tool is
built, run and scheduled is not the standard's business (05-foundry).

### 4.6 The trust rule, restated

Round 1's rule, generalised:

> Nothing a tool writes binds anyone. A record binds only when a human `act` names its exact
> `rev`. Every effect outside the store (send, merge, spend, run unattended) needs such an
> act or a bounded `grant` that names the tool's source hash.

The rule is unchanged in spirit, and it is the reason cheap tools are safe to make: a wrong
tool can waste money inside its grant and produce noise. It cannot commit the owner to
anything.

**But only if acts cannot be forged, and under this premise a self-asserted `by` field is
forgeable.** `by: human:<id>` is a string any tool can write. Round 1 accepted that gap openly:
04 §6 says the TTY confirmation protects against accidents, not against an agent that goes
around it, and 04 §8.5 deferred a presence key (Touch ID per act) until something ran
unattended. That deferral assumed few, known processes running as the owner. Cheap,
unreviewed tools running as the owner remove the assumption (pattern 6, S2). So:

- **An `act` counts only if it carries proof of human presence** (a signature from a key
  that needs a physical touch, or equivalent) that the validator checks against the named
  `rev`s. Without it, the record is not an act, whatever its `by` says.
- **Tool provenance (`by: tool:…`, `inputs`) is evidence, not proof**, unless the store or a
  launcher stamps it. That is acceptable: provenance is for understanding and selection,
  and nothing binds on it.
- **Acts are written only through the presence-gated path.** The CLI that performs `accept` is
  itself a tool; what matters is that no tool can produce a valid act without the touch.

**Open cost: grants keyed to a source hash.** If a grant names the tool's source hash, every
regeneration of the tool needs a new grant. That is intended (new code means new consent),
but it feeds the attention flood (N8). Whether grants should name a hash, a tool `id` with
a re-grant on change, or a capability class is left to 05-foundry and 05-selection.

## 5. New framings: kept, changed, or rejected

Each framing either changes a line in §4 or is rejected with a reason.

**Tools as hypotheses. Kept.** A tool is a guess that "this would help with P". Because the
tool is a record `about` P (§4.5) and outcomes judge P, the system can ask which tools touched
the records that led to a "met" verdict. *Changes:* the tool contract's `about` field, and
`by` as a source hash. The selection mechanics belong to 05-selection.

**The problem as the app. Kept, as a view.** The "app" for a problem is whatever renders
`about: P`: a timeline of notes, the people involved, open decisions, the outcome. Different
tools render it differently, and none of them owns it. *Changes:* no "project" or "workspace"
concept in the standard; `about` is enough.

**Workspaces that dissolve. Kept for data, rejected for access.** A workspace as a data
container disappears into the query `about: P`. But a boundary is still needed for *who may
read what* and *which grants apply*, especially with third-party personal data (N7). *Changes:*
access scope is a property of the store and grants, not a field records must carry.
Contestable: if sharing ever matters, a scope field may come back.

**Schemas negotiated by agents. Rejected at run time, kept at design time.** Two agents
agreeing on a schema mid-run produce a meaning no human ever saw, which is N4 at machine
speed. But agents *proposing* a type definition is fine and cheap. *Changes:* a type
definition is a `note` of type `type.def`; using a new type is free, but a type becomes
*shared* (other tools may rely on its fields) only when the owner accepts its definition. A
type definition is a decision.

**Records as the only durable thing. Kept, with a sharpening.** It follows from Invariant 0.
The sharpening: tool *source* is also durable, as an `artifact`, because without it
provenance points at nothing. Tools are disposable as running things, not as history.

**Own framing 1: regenerability decides durability.** (Invariant 0, §1.) It also settles a
round-1 question: projections are cache and never read back (round 1 was right), and model
outputs are records, never cache (round 1 did not say this).

**Own framing 2: judgment is the budget, not money.** The meaningful throughput limit is
acts per day (S1). A tool's real cost is not its tokens but the acts it demands per outcome.
*Changes:* acts are records, so this is measurable from day one. No new field is needed.

**Own framing 3: capture is an inbound sink.** Round 1 made outbound effects sinks with
verifiers (04 §6b). Capture is the mirror: the point where the world enters. It is where
`origin`, `people` and provenance are stamped, and where the third-party data rule (N7)
applies. Many capture tools are fine. They must all stamp the same envelope.

**Own framing 4: the outcome closes the loop that round 1 measured by hand.** Round 1's kill
criteria were read from a friction log written by the owner. With `outcome` as a kind, "did
this help?" is a record judged against criteria, so the system can evaluate its own tools
with the same mechanism it uses for everything else.

**Considered and rejected: "the tool is the record".** I.e. drop the distinction and let
records carry behaviour (OpenDoc's parts, Smalltalk). Rejected for the reason round 1 gave
(01-failure-modes, Smalltalk image, CASE drift): behaviour embedded in data cannot be read
without running it, which fails the orphan test.

## 6. Implications for the standard

The concrete minimal list. This is the one page an agent writing a tool must read.

1. **A record is a file with an envelope and a body that reads as text without any tool.**
2. **Envelope:** `id` (ULID), `rev` (sha256, stamped), `kind`, `type` (namespaced), `about[]`
   (optional), `links[]` (by `rev`), `people[]` (optional), `by` (`human:<id>` or
   `tool:<source sha256>` + model), `inputs[]` (required when `by` is a tool), `origin` (when
   from outside), `cost` (when spent), `at`.
3. **Six kinds:** `note`, `problem`, `outcome`, `decision`, `act`, `artifact`. Everything else
   (meeting, person details, task, source, transcript, tool, type definition) is a `type`.
4. **One authority mechanism:** an `act`, only by a human, proven by a presence signature the
   validator checks (a self-asserted `by` is not enough), naming exact `rev`s, with verbs
   `adopt`, `accept`/`reject`, `judge`, `grant` (bounded, expiring), `send`. Default deny.
   Batch acts allowed and recorded as such.
5. **Problems carry criteria; outcomes pin the problem rev they judge.** Criteria and verdicts
   bind only via acts.
6. **`about` is many-valued, optional at write time, and addable later by a sidecar record.**
   Unfiled records are legal and visible.
7. **People are ids.** Every record involving a person carries the id, so find-and-delete for
   one person is one query.
8. **Types evolve additively.** A new meaning gets a new name. A type becomes shared when its
   definition record is accepted.
9. **Tools are records** (`type: tool`) with `reads`, `writes`, `needs`, `about`, and source
   kept as an `artifact`. Acts are written only through the presence-gated path (item 4).
10. **Nothing a tool writes binds anything; every outside effect needs an act or a bounded
    grant.**
11. **A validator enforces 1–10** and is the conformance test (round 1 test 7). A record that
    fails it is not in the store.
12. **Two new tests join round 1's sixteen:** the orphan test (delete the tool; every record it
    wrote is still readable and attributable) and the goalpost test (edit criteria; old
    outcomes still point at what they judged).

What is deliberately *not* in it: scheduling, the patch format, UI, search, workspaces,
sync, a runtime, how tools are made, which tools survive.

## 7. What round-1 synthesis got wrong under this premise

Kept separate from what still holds.

**Wrong under the premise:**

1. **The spine was `decision`.** 04 §6 made the typed decision "the meeting place". Under the
   owner's flow, decisions are the middle of the chain. The spine is problem → … → outcome,
   and decisions are one of the things that are `about` a problem.
2. **There was no outcome record.** Round 1 judged its own slice by a hand-written friction
   log and kill criteria (04 §6). The feedback loop lived outside the system. Swarm's classic
   board already had the shape (an evaluation pinned to the spec revision it judged) and the
   synthesis did not lift it.
3. **The unit was the CLI.** 04 built `decide` and `research` as products, four weeks of build.
   Under the premise the unit is the record plus its contract, and tools are cache. Building
   five throwaway tools against the envelope in week one says more than two durable CLIs.
4. **"Draw boundaries from real crossings" assumed redrawing is expensive.** It is still right
   for *formats*: they are the only expensive thing to change. It is wrong for *tools*, which
   can be redrawn every week. 04 half-saw this ("formaterne er det, der er dyrt at ændre
   bagefter", §7) but still sequenced the work tool by tool.
5. **The writing tool came last.** 04 §7: "Intet skriveværktøj endnu." Under the owner's input,
   writing is capture, and capture happens everywhere. There is no single writing tool to
   postpone. There is one envelope that every capture surface must stamp, and that comes
   first.
6. **Provenance named modules, not sources.** 01-data-model's `producedBy` is "module type and
   version". With tools regenerated weekly, a name and version point at nothing. Use the
   source hash.
7. **Authority was spread across kinds.** Round 1 argued per kind about strictness (`decision`
   strict, `task` maybe, `signal` maybe). One mechanism, the `act`, makes the kinds simpler
   and the validator one rule.
8. **People and third-party data were absent.** No envelope field, no GDPR consideration.
   That was fine for a decision register; it is not fine for "who did I talk to".
9. **The confirmation design assumed few acts.** Interactive confirmation per accept (04 §6) is
   right against accidents and wrong at proposal volume (N8). Batch acts over named revs,
   recorded as batches, are needed.
10. **The presence key was deferred until something ran unattended** (04 §8.5). That deferral
   assumed few, known processes running as the owner. Cheap, unreviewed tools running as the
   owner make a forgeable `act` the central risk, so proof of presence is a precondition of
   the trust rule from day one, not a later upgrade (§4.6).

**Still right, and more so:**

- Files in git, one store, the owner owns it.
- ULID for identity, sha256 for revisions, "one of each".
- The trust rule: human acts over exact hashes, agents only propose. It is now *the* reason
  cheap tools are safe.
- No runtime kernel, no scheduler, no canvas in the standard.
- Projections are regenerated and never read back.
- `origin` on the way in, sinks with verifiers on the way out, credentials in the edge module,
  no two-way sync (04 §6b). Integrations as edge modules fit the premise exactly: an
  integration is one more cheap tool, and the envelope is what makes it composable.
- "Type thin, text thick, coerce explicitly".
- Not building D's model gateway yet (spend metering). Grants with bounds (§4.2) are the
  same idea in record form, and spend can be enforced loosely first. The presence key is the
  exception: see item 10 above.
