# 01 — Inventory: the owner's projects as candidate modules

Track: what exists today, what each project's interface actually is, and which recurring shapes hint at a shared kernel. Read-only survey, 2026-10-07. Lens: Sonic's patch bay (`~/www/sonic/docs/product/patch-bay.md`): jack kinds and `canConnect`, the patch as plain data, parked modules that cost nothing, and feedback that is legal at the price of one quantum of delay.

Headline: none of the five projects is a writing tool, a knowledge base or a research tool. The candidates are **swarm** (delivery), **sonic** (audio patching, which also supplies the lens), **printer** (parametric CAD) and **square** (a kids' physics toy). **swtest** is a fixture, not a project. The seeds of a knowledge base and a research tool exist *inside* swarm and in the `docs/` convention, not as projects of their own.

---

## 1. swarm — agent-first product delivery (`~/www/swarm`)

### What it is
Swarm is a local tool, CLI first, that takes an idea and delivers it in sandboxed Claude agent rounds on a git branch per feature. A person judges each round. It is dogfooded: it builds itself (`swarm/.swarm/simple`) and sonic (`sonic/.swarm/simple`). The stack is Node 22, TypeScript run directly, Hono, zod, the Claude Agent SDK and nono for the sandbox (`package.json`).

There are two models in the tree:
- **Classic board** (`src/board/*`, `src/orchestrator/*`, `src/cli/index.ts` at 2.7k lines, `src/mcp/*`). It has lanes, a plan→build→review stage machine, a feature lifecycle, a queue, parking and a human agent. It is about 6.5k lines and **slated for deletion** (D-033).
- **Simple model** (`src/loop/*`, about 2k lines). It is the model in force (D-032 and D-033, accepted 2026-10-05; `docs/product/simple-model.md`). **Treat this as swarm's real interface.**

### Domain objects (simple model, `src/loop/model.ts`)
- **Feature** `f-xxxxxx`, stored at `.swarm/simple/features/<id>.json`. Fields: `id, title, idea, state (working|waiting|done), kind (result|question|problem|blocked), outcome (merged|dropped), branch swarm/<id>-<slug>, worktree, target, capUsd, costUsd, dependsOn[], rounds[]`. It is written atomically, and every write emits SSE.
- **Round**: `n, reply, basis[{decisionId,revision}], sessionId, resumes (≤3), budgetUsd, costUsd, snapshotSha, handback, problem, mergeConflict`. Rounds are append-only.
- **Hand-back**: the run's structured output, which the core checks.
  - A `result` carries `{built, decisions[{choice, rejected, relation: follows|new|conflicts|supersedes}], tryIt[], checks{tests, openFindings}, risks[], scopeChanged?}`.
  - A `question` carries `{question, why, options[], recommended}`.
- **Decision** (simple model): appended on approve to `.swarm/simple/decisions.jsonl` as `{at, feature, title, choice, rejected, relation}`. swarm has 29 lines and sonic has 21.
- **Agent roles**: one *loop agent* plus four subagents, `planner`, `builder`, `reviewer` (fresh context on purpose) and `product-critic`. They are defined in code (`src/loop/prompt.ts`). The builder and the critic get a browser when `builderBrowser` is set.
- **Board config**: `.swarm/simple/board.json` (`LoopConfig`, `src/loop/store.ts`). It holds `targetRepo, target, port, roundBudgetUsd, featureCapUsd, maxReviewIterations, maxTurns, model, sandbox{profile, read[]}, preview{prepare, command, args, urlPattern}, builderBrowser, stack (free-text stack profile), access/publicDomain`. Sonic's copy is a good example (`~/www/sonic/.swarm/simple/board.json`).

### Interface today
- **CLI**, from `LOOP_USAGE` in `src/loop/cli.ts`:
  - human: `init --model simple`, `serve`, `add "<idea>" [--budget] [--depends-on id]…`, `reply <id> "<text>" [--budget]`, `approve`, `drop`, `ls|show [--json]`, `preview [<id>]`, `link`, `talk <id>`, `auth`;
  - agent: `show <id>`, read-only.
- **Files**: reads go straight to the feature JSON files, so they need no server and work from inside the sandbox.
- **HTTP** (`src/loop/server.ts`, Hono):
  - reads: `GET /api/features`, `GET /api/features/:id` and `GET /api/events` (SSE);
  - writes, only on the `human` sub-router with the human token from `~/.config/swarm/human-token`: `POST /features`, `/features/:id/{reply,approve,drop,preview,preview/stop,preview/external}`.
- **MCP**: *the simple model has none.* `src/mcp/index.ts` serves the classic board only (`list_board, create_task(s), move_task, update_task, submit_work, adopt_ownership, park_task, unpark_task, raise_decision_conflict, list_features, manage_feature, hand_off_design, add_comment, list_decisions, record_decision, decision_docs, plan_to_board`), and it goes away with D-033.
- **Git as output**:
  - one commit per round, `f-xxxxxx round N: result` (the core's snapshot);
  - one per approve, `Merge f-xxxxxx: <title>` (`--no-ff`, no push).
- **Hard trust rule** (Settled #1 in `simple-model.md`): **agents read, only a person writes.** A round has a read-write worktree, a read-only `.git`, no human token and its own nono profile. Any patch that lets one module's output *trigger* swarm's approve breaks this, so approve is a jack that cannot be cabled.

### Swarm as one module in a patch
- **Inputs (jacks in)**:
  - `repo` (a workspace) and `target` branch;
  - `idea` (text) and `reply` (text, the feedback edge);
  - `budget`/cap;
  - `stack` profile (text);
  - **decision basis** (pinned accepted decisions; today empty);
  - `dependsOn` (other features' `done·merged` events);
  - optionally the preview command.
- **Outputs (jacks out)**:
  - `handback` JSON, which is `result` or `question`;
  - `decisions[]`, new or superseding, which become accepted on approve;
  - branch + `snapshotSha` per round, and a merge commit on approve;
  - preview URL;
  - SSE state events (`working → waiting(kind) → done(outcome)`);
  - cost.
- **Human-only control jack**: `approve` (and `drop`). This is like a param with `modulatable: false` in Sonic: it is visible and settable by a person, but no cable may drive it.

## 2. sonic — voice-driven effect unit (`~/www/sonic`)

**What it is.** SvelteKit + TS, browser as lab, the Pi as target engine (D-002, D-016). Voice → notes/MIDI, plus a modular effect unit patched with virtual cables (D-018). Routes: `/`, `/record`, `/midi`, `/synth`, `/patch`, `/dev/{tempo,transposer,vocoder,fixtures}`.

**Domain objects.**
- `Patch {version:1, name, modules[{id,type,x,y,params}], cables[]}` (`src/lib/patch/types.ts`).
- `Plugin` = descriptor + `create()`. The descriptor holds jacks with `PortKind audio|control|note`, params with range, curve and `modulatable` flags, a `latency` sentence and a `cost` sentence.
- `canConnect(from,to) = (from==='note') === (to==='note')` (`src/lib/patch/runtime.ts:501`).
- Registry plus a contract test (`registry.ts`, `registry.test.ts`) that holds every plugin to the same invariants.
- Presets are starting patches (`presets.ts`).
- Fixtures/recordings feed the bench, which has a baseline and a latest run (`bench/baseline.json`, `bench/latest.json`, `bench/compare.ts`).

**Interface today.**
- Web UI only, plus `.mid` export and MIDI out.
- Patches are saved in browser storage; devices are kept apart under `sonic.audio-devices.v1`.
- `npm run bench*` is a CLI that measures DSP against recordings, kept in a gitignored `recordings/` folder (D-006). A dev-only vite route writes them (`vite-plugin-recordings.ts`).
- No MCP and no HTTP API.

**Process artefacts.**
- `docs/product/{principles,decisions,<feature>.md}`. `decisions.md` is the **generated register projection** from swarm's classic register (D-001…D-018). D-001 is still *proposed*, so not everything there is in force.
- `.swarm/simple` board: 21 decisions in jsonl, `f-` commits.
- `AGENTS.md` (generated by swarm, classic flavour).

**As a module.** It is a domain app built *by* swarm, not a tool to chain with writing or KB tools. Its value here is the **kernel shape** it already proves: typed jacks, a pure runtime, a registry with a contract test, a patch as versioned plain data, parked modules, and one-quantum feedback.

## 3. printer — agent-first parametric 3D modelling (`~/www/printer`)

**What it is.** Node core (manifold-3d) + Express/WebSocket server + Svelte/three.js editor + CLI + MCP, all over one document model (`README.md`, `AGENTS.md`).

**Domain objects.**
- Document `{format:"printer/1", name, meta.bed, vars, nextId, nodes[] (tree: id,type,name,params,position,rotation,scale,hole,…), joints[]}`, in `core/doc.js` and stored at `projects/<name>.json` with `<name>.history.json` beside it.
- Node-type **registry**, `core/registry.js`: params schema + build function. This is the single source of truth.
- **Ops** with one mutation path, `applyOps(doc, ops)`: atomic batches, `$refs`, `--dry-run`, one undo step per batch.
- An expression language (`core/expr.js`).
- Printability checks that return *fix ops*.
- Mechanics: joints, sweep, click/jump analysis.

**Interface today.**
- **CLI** `printer` (`cli/printer.js`), about 50 verbs: `status tree get add set move rotate hole group apply check measure describe watch vars undo redo export snapshot joints sweep pose mesh test plate select activity projects new open save-as …`.
  - `--json` everywhere.
  - Exit codes 0/1/2.
  - Unknown flags are refused with a suggestion.
- **MCP** (`mcp/server.js`): `status, tree, get_node, schema, apply_ops, stats, check, measure, describe, snapshot, sweep_frames, export, vars, undo, redo, selection, mechanics, joint_ratio, sweep, pose, …`.
- **HTTP + WebSocket** live sync. The server is the single writer while it runs.
- `cli/backend.js` chooses **live server or offline file** (`PRINTER_OFFLINE`, `--project`, `PRINTER_URL`).
- Outputs: STL/3MF/OBJ, PNG snapshots with a `rendered_rev`.

**Process.** It is not run by swarm. It uses `/loop` with round briefs (`.claude/improve-round.md`, `.claude/mechanics-round.md`): 4 parallel track agents, each owning files, a 3-round cap, and an append-only log (`IMPROVEMENTS.md`, `MECHANICS.md`). Commits read "Mechanics round N: …".

**As a module.** It is the cleanest **tool-module template** in the set: one core, three adapters, a dry-run plus atomic ops interface, `describe` as an agent-readable summary, and `check` returning fix ops. A patch could cable `swarm.handback.tryIt` → nothing useful. A more natural cable is "research/writing → spec → printer ops", or "printer check findings → swarm reply".

## 4. square — "Magnet Lab" kids' physics sandbox (`~/www/square`)

**What it is.** Vite + Three.js + Rapier (WASM). Kids build with magnetic blocks and press Play. The physics is headless (`src/physics/*`, runnable under Vitest), with the renderer in `src/render`, the UI in `src/ui` and data in `src/scenes/{presets,missions}.js`.

**Interface today.**
- Browser only.
- localStorage for saves, missions and onboarding (`src/ui/{saves,missions,coach}.js`).
- `src/ui/testHooks.js` for Playwright.
- `scripts/shoot.mjs` takes screenshots per scene and viewport into `shots/`.
- No CLI, MCP or HTTP. There are no product docs or decisions in the repo.

**Process.** "Round N: …" commits (R1–R4), with a `.claude/` loop like printer's. `shots/r2…ux-r4` are per-round visual evidence.

**As a module.** Weak. It is an end-user app. It is useful only as evidence of the *round + screenshot evidence* pattern, and of "headless core + thin renderer".

## Recurring patterns (kernel hints)

1. **One core, many adapters, a single writer.**
   - Printer: core → CLI, MCP and HTTP/WS; `backend.js` is live-or-offline.
   - Swarm classic: `BoardClient` is HTTP-or-store; D-025 is literally "one core, three adapters".
   - Swarm simple: reads go to files, writes go through the server.

   The rule is the same everywhere: there is one mutation path, and the adapters hold no rules (swarm D-013, printer's `applyOps`).
2. **State as versioned plain-data files.** `printer/1` docs, Sonic's `Patch.version: 1`, swarm's `kind: 'simple'` and its feature JSON, `decisions.jsonl`, and `.swarm/decisions/<id>.json`. Writes are atomic and history is append-only (rounds, decision revisions and events, printer's `.history.json`).
3. **A registry of typed things + a contract test.** Sonic's `PLUGINS` + `registry.test.ts`; printer's `core/registry.js` (params schema); swarm's agent types (`agents/*.md`) and the hand-back schema.
4. **Structured, checked outcomes over prose.**
   - swarm hand-back checked by the core;
   - printer `--dry-run` + "Nothing was changed";
   - sonic descriptors that state `latency` and `cost`;
   - `--json` everywhere.
5. **Rounds as the unit of agent work.** There are three independent implementations:
   - swarm (`f-xxxxxx round N: result` + `Merge f-xxxxxx: <title>`);
   - printer/square `/loop` with `.claude/*-round.md`, parallel tracks, a round cap and an append-only round log;
   - this research loop (`compose-research/STATE.md` iterations).

   **The shared primitive is "round" (bounded run → structured outcome → human or next round), not swarm.**
6. **Decision registers with stable ids.** `D-NNN`, proposed ≠ accepted, supersession, generated projection into `docs/product/decisions.md`. They appear in swarm and sonic, and the files also hold handwritten decisions above the generated region.
7. **The `docs/product/` layout.** `principles.md` (standing judgements), `decisions.md` (projection), and one `<feature>.md` per settled design with a "Status: settled … as D-NNN" header (sonic `patch-bay.md`, swarm `simple-model.md`). There is also `docs/research/` (dated, "not canonical"). This *is* the proto knowledge base.
8. **Id schemes.** `f-xxxxxx` (simple features), `t-xxxxxx` (classic cards), `D-NNN` (decisions), node ids `cut1`/`uni1` (printer). Sonic module ids sit inside a patch.
9. **The person approves and the agent proposes.** Swarm approve is human-token-only. Swarm `record_decision` proposes and only a person accepts. Printer's web app lets the person edit anything the agent made. Sonic: "the owner judges whether it sounds good".
10. **Evidence artefacts per round.** Preview URLs and `tryIt` (swarm), PNG snapshots with a revision (printer), `shots/<round>` (square), bench `latest` vs `baseline` (sonic).

## Gaps
- **Knowledge base.** No standalone tool exists. The seeds are the decision register (pure core, unplugged), `docs/product/principles.md` and the generated-projection mechanism. Principle 6 ("product knowledge accumulates… relevant context retrieved, not dumped") and roadmap step 7 describe it but have not built it.
- **Research tool.** Nothing is built. The seeds are `docs/research/*.md` and this compose-research loop.
- **Writing tool.** Nothing exists.
- **Drift.** Sonic's `AGENTS.md` and `decisions.md` come from swarm's classic era while sonic runs a simple board. This is a symptom of swarm acting as host, writing into other repos, rather than being a module.

## What is the cable/jack/patch here

| Patch-bay concept | Equivalent across these projects |
|---|---|
| **Module** | A tool with one core: swarm round engine, decision register, printer doc, sonic patch runtime. A future KB, writer or researcher. |
| **Descriptor** | Jacks + params + `latency`/`cost` sentences. For tools: input/output kinds, config schema, **cost in $ and time** (swarm already has `budgetUsd`/`costUsd`) and **who may drive it** (agent / human-only). |
| **Jack kind** | Typed artefacts rather than samples: `text` (idea, reply, note), `spec/brief`, `decision[]` (with a revision pin), `handback` (result/question), `git ref` (branch@sha), `url` (preview), `file` (STL/.mid/PNG), `event` (state change). `canConnect` = schema compatibility: `decision[]` → a basis input, `question` → a human or a research module, never `result` → `approve`. |
| **Non-modulatable param / device param** | **Human-only jacks**: swarm `approve`/`drop`, register `accept`. They are visible in the patch, but no cable may drive them, and the kernel enforces this (swarm's human token) rather than trusting the module. |
| **Cable** | A declared flow of typed artefacts between modules, persisted as data. Fan-in sums in sonic; for artefacts it is more like a "list of inputs" (several decisions → one basis). |
| **Quantum** | **One round**: a bounded run that ends in a persisted, checked hand-back. Discrete like a render quantum, but variable in length. |
| **Feedback with one quantum of delay** | `reply → next round` is already this: the loop reads the *previous* round's hand-back. The patch-bay rule generalises it: a cycle is legal when every edge in the loop reads the source's last *completed* round, never a live one. So swarm ↔ reviewer-module ↔ swarm loops cannot deadlock, and each turn is bounded by budget. |
| **Parked module** | A `waiting` feature or an idle module: its state is kept on disk, it costs $0 until a cable (a reply or a dependency becoming `merged`) wakes it. Swarm's `blocked` kind + auto-start on dependencies is literally "parked until a cable brings it back". |
| **Patch as plain data** | A versioned JSON: modules (type, id, config) + cables. Swarm's `board.json` is a degenerate one-module patch. `dependsOn` between features is an in-module cable that could become a kernel-level one. |
| **Edits keep state** | Changing the patch must not discard a module's state (a feature's rounds, the register's history). This is Sonic's "diff and keep modules whose id+type survive". |
| **Registry + contract test** | Any module that claims a jack kind must pass the kind's contract: it emits valid schema, it is idempotent on replay (swarm D-011: "restart never duplicates a round"), and it is append-only. |

## Implications for the kernel

1. **The kernel is not swarm. It is what swarm, printer and sonic each rebuilt.** That is: a typed-artefact store (versioned JSON, atomic writes, append-only history), one mutation path per module, adapters generated per module (CLI with `--json`, HTTP/SSE, MCP), and a single writer with read-from-file fallback.
2. **Make "round" a kernel primitive.** It is a bounded, budgeted run that returns a schema-checked outcome, is persisted before being applied, resumes at most N times, and never re-runs once applied. Swarm's engine, printer's `/loop` and this research loop are three instances. Feedback edges are legal because each one reads the last *completed* round, which is the one-quantum rule.
3. **Split the decision register out first.** It is already pure, already has a projection format, is already hosted by two repos, and is currently unplugged from swarm's simple model, which is the test case. As a module it has inputs `propose(decision)` and `accept` (human-only), and outputs `basis@revisions` and a markdown projection. It is the obvious nucleus of the knowledge-base module, and the first real cable is register → swarm basis.
4. **Trust is a jack property enforced by the kernel**, not a module convention. Some inputs are human-only (`approve`, `accept`) and need a credential the sandboxed agents cannot read (swarm's human-token pattern). `canConnect` must refuse agent→human-only cables statically.
5. **Sandbox, agent runner and workspace are kernel services, not swarm internals.** Every agent module (researcher, writer, KB curator) needs nono profiles, an output schema per run, budget, and a worktree or read-only grants. Today these sit in `src/orchestrator/{agentRunner,sandbox}.ts` and `src/loop/{claudeHome,git}.ts`.
6. **Descriptors must state cost and latency in plain words**, as sonic's do. For agent modules this means dollars per round, typical wall time and the scope of side effects (read-only, worktree, merges to main).
7. **Modules must stop writing into each other's repos.** Swarm's `AGENTS.md` generator and the `.swarm/` dirs in target repos are host behaviour. In a patch, a project repo is a *workspace artefact* that modules receive through a cable, and per-repo config (stack profile, preview command) belongs to the workspace or the patch, not to one module's `board.json`.
8. **Keep the `docs/product/` convention as a projection target**: principles, decisions (generated region) and settled designs with D-ids. The KB module should own it the way the register owns its region, so it stays human-readable and diffable in git. Do not make it a second source of truth.
9. **Plan for weak modules.** Square and sonic have no machine interface, so a patch can only reach them through a generic "repo + preview + screenshot" workspace jack, which is exactly how swarm already treats them.
