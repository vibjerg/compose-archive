# 01 — Why composable products fail: a critic's evidence base

Track: the critic. Lens: Sonic's patch bay (`/Users/svenven/www/sonic/docs/product/patch-bay.md`):
modules, typed jacks, cables carrying one block format, a one-file plugin contract, and a contract
test every plugin is held to.

The question is not "is composition good" (Unix, Excel and Eurorack answer that) but **which
specific decisions killed the composable systems that died, and what the survivors did instead**.
Each pattern below has a concrete failure, the evidence for it, and the counter-move a winner made.

Sources are cited inline. Where a claim comes from a secondary summary rather than a primary page,
it says so.

---

## The cases in one table

| System | Outcome | The decisive failure (or success) mechanism |
| --- | --- | --- |
| Apple OpenDoc (1992–97) | Killed by Jobs on his return | Document-centric paradigm users didn't ask for; heavy runtime; no killer part; the platform vendor was losing money while Microsoft pushed OLE |
| Microsoft OLE / ActiveX | OLE survives as plumbing; ActiveX deprecated | ActiveX: native code, full machine access, trust by click-through dialog → drive-by malware |
| Yahoo Pipes (2007–15) | Shut down | Brilliant editor, no owner investment, depended on an RSS/open-API web that closed around it |
| Microsoft Popfly, Google Mashup Editor | Shut down in beta | Mashup tools with no sustaining use; Popfly cut for budget (built on Silverlight, itself later abandoned) |
| IFTTT | Alive, capped | One trigger → one action: easy, but a structural ceiling |
| Zapier | Large business | Same idea, but multi-step + filters + an integration catalogue as distribution |
| Google Wave (2009–10) | Shut down in a year | Platform-before-product: federation, robots, gadgets, live typing — no single job done better than email |
| Smalltalk images | Niche | Composition lives in an opaque, unreproducible image, cut off from files, VCS and other tools |
| Eclipse / OSGi | Survives, notorious | Rich module system, version-range resolution, singleton bundles → "unsatisfied constraint" hell |
| Firefox XUL → WebExtensions | Power traded for stability | Extensions could touch everything, so the host could not change (e10s) |
| Microservices (Segment) | Went back to a monolith | 50+ per-destination services, shared-library version drift, per-service ops cost grew linearly |
| LangChain | Widely abandoned in production | Abstractions over a thin, fast-moving core; hid the prompt and the control flow |
| Low-code / CASE | Recurring ceiling | Generated artefact drifts from the model; complexity beyond the palette has no exit |
| VS Code + LSP | Dominant | Out-of-process extensions, lazy activation, narrow API; LSP turns M×N into M+N |
| Obsidian | Thriving | Plain Markdown files as the bus; plugins optional on top of a great single-player app |
| Figma plugins | Thriving | Sandboxed document API, no browser access; UI in a separate iframe |
| Excel | The most successful end-user programming system | Two concepts (cells, formulas), instant visible feedback, useful on day one |
| Unix | Fifty years | Everything is a byte stream; tiny tools each useful alone |
| Eurorack | 15,000+ modules, 1,000+ makers | An open, physical, one-page spec: 3.5 mm jacks, voltages, 1 V/oct, HP widths |

## The recurring failure patterns

### 1. Platform before product (no killer single-module use)

**Failure.** Google Wave launched as a protocol, a federation story, an extension model (robots and
gadgets) and an app at once. Users got in and asked "now what?": Gina Trapani wrote a 195-page
guide to using it, and early testers "simply didn't know what to do with it"
([InfoWorld, "Why Google Wave failed: too complicated, no fun"](https://www.infoworld.com/article/2625908/why-google-wave-failed--too-complicated--no-fun.html);
[eWeek, 10 reasons](https://www.eweek.com/de/cloud/google-waves-failure-10-reasons-why/)). Secondary
retrospectives say Lars Rasmussen later named underestimating how hard the product was to explain,
and the cost of the federation/open-protocol ambitions, as mistakes (paraphrase via
[Gigazine](https://gigazine.net/gsc_news/en/20200411-why-google-wave-failed) and
[Taskade](https://taskade.com/blog/google-wave-history); not his words verbatim). OpenDoc had the
same shape: a framework for "parts" with several hundred developers signed up, but no part anyone
needed, and a paradigm (documents first, applications second) users had not asked for
([Cyberdog/OpenDoc, Wikipedia](https://en.wikipedia.org/wiki/Cyberdog);
[Dr. Drang, "The Cyberdog that didn't bark"](https://leancrew.com/all-this/2011/06/the-cyberdog-that-didnt-bark-in-the-night/)).
Jobs, asked "What about OpenDoc?" at WWDC 1997, answered that "focusing is about saying no"
([Gruber](https://daringfireball.net/2014/02/working_backwards)).
Martin Fowler sees the same thing in services: "almost all the successful microservice stories have
started with a monolith that got too big and was broken up"
([MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html)).

**What winners did.** Obsidian is a good Markdown editor with *no* plugins enabled; new vaults start
in Restricted Mode ([Obsidian plugin security](https://obsidian.md/help/plugin-security)). Excel is
useful with one cell and one formula. Each Unix tool (`sort`, `grep`) is a whole product on its own.
Eurorack grew out of Doepfer's A-100, which was a complete synth before it was a standard
([Wikipedia: Doepfer A-100](https://en.wikipedia.org/wiki/Doepfer_A-100)). **The modules were
products first; the composition came later and for free.** Fowler's rule is the same: find the
boundaries by building the thing, then cut.

### 2. The composition tax on users (the blank canvas)

**Failure.** Any system whose value only shows up *after* the user wires something together charges
a setup tax before it pays out. Yahoo Pipes was an excellent visual editor that "never got as many
users as the company would have liked"
([VentureBeat](https://venturebeat.com/2015/06/21/6-reasons-killing-off-yahoo-pipes-was-a-bad-idea)).
Microsoft Popfly never left beta, and Google Mashup Editor never left private beta
([TechCrunch](https://techcrunch.com/2009/07/17/microsoft-popfly-gets-squashed/)). The mashup era made
the user be the integrator.

**What winners did.** Zapier turned every pair of apps into a pre-built, findable starting point. It
published a page per app, per app pair and per *workflow*, so the user starts from "add Gmail email
to a Trello card", not from an empty canvas
([Reforge on Zapier's SEO growth](https://www.reforge.com/blog/brief-the-seo-driven-user-acquisition-behind-zapier-s-growth-to-35m-arr);
[Sacra](https://sacra.com/research/zapier)). Nardi's study of spreadsheets: users need early success,
and the "twinkling lightbulb" of instant recalculation gives it
([Nardi & Miller, "Twinkling lights and nested loops"](https://www.lri.fr/~mbl/Stanford/CS477/papers/Nardi-Twinkling-IJMMS.pdf)).
**Ship compositions, not just modules: templates and presets that work on first press.**

### 3. Lowest-common-denominator interface, and when it is not a failure

This is the subtle one, because the counterexamples contradict the naive version.

**Failure.** IFTTT's applet is one trigger → one action. Even Pro multi-action applets fire
unconditionally, with no branching, routing or field-based logic. The ceiling is structural, so no
price tier lifts it (paraphrase)
([Latenode comparison](https://latenode.com/blog/zapier-vs-ifttt-which-is-the-best-in-2025);
[Process Street](https://www.process.st/zapier-vs-ifttt/)). Low-code makes the same bargain: stay
inside the platform's boundaries and everything is easy, but real problems don't (paraphrase)
([webaligo, "Low code no code and why it has not conquered the world"](https://webaligo.bearblog.dev/low-code-no-code-and-why-it-has-not-conquered-the-world/)).

**But Unix text and Eurorack voltage are also lowest-common-denominator interfaces, and they won.**
The difference:

- **An LCD that is native to the domain wins.** Text *is* what Unix tools process. A voltage *is* what
  an analogue module processes; pitch is a voltage (1 V/oct), a gate is a voltage. Nothing is lost by
  crossing the cable.
- **An LCD that erases what the domain needs loses.** IFTTT's single event-to-action contract erases
  conditions and multi-step state, which is what automation is made of. OpenDoc's "part" erased what
  made each application good.

Even the native LCD has a price. The Unix-Haters Handbook's long complaint is that untyped text
streams make every pipe a parser
([UNIX-HATERS Handbook PDF](http://web.mit.edu/~simsong/www/ugh.pdf)). The PowerShell camp's version:
in Unix, text output is effectively a programming contract, so changing a command's output breaks
scripts downstream (paraphrase, as summarised in comparisons such as
[John D. Cook's](https://www.johndcook.com/blog/2009/06/09/comparing-the-unix-and-powershell-pipelines/);
the wording may originate with Jeffrey Snover).
PowerShell's answer is typed objects on the pipe. Gabriel's "Worse is Better" explains why the simple,
untyped thing spread anyway: simplicity of *implementation* beats correctness at adoption time
([dreamsongs](https://dreamsongs.com/RiseOfWorseIsBetter.html)).

**What winners did.** They chose *one* payload native to the domain, and added *just enough* typing
to stop the dangerous mistakes, not to model everything. Eurorack documents its signal levels and
doesn't enforce them. LSP has a rich typed schema, but only for one narrow domain (language features).
Zapier added filters and branching on top of a payload that stays simple (field maps).

### 4. Version skew and dependency hell

**Failure.** Eclipse/OSGi resolves bundle version ranges, allows singletons, and makes the user live
with "Unsatisfied version constraint". Eclipse developers on the lists describe optimal resolution as possibly
NP-hard and package-level versioning as barely manageable without tooling (paraphrase)
([eclipse-dev](https://www.eclipse.org/lists/eclipse-dev/msg12557.html);
[e4-dev](https://www.eclipse.org/lists/e4-dev/msg00571.html)). COM/ActiveX had "DLL hell". Segment's
per-destination services (50+ and growing by about three a month) drifted onto different versions of shared libraries, so a fix to the shared
code had to be rolled out N times, and three full-time engineers ended up spending most of their time
keeping the system alive (paraphrase)
([Segment/Twilio, "Goodbye Microservices"](https://twilio.com/en-us/blog/developers/best-practices/goodbye-microservices)).
LangChain users cite "frequent breaking changes to APIs" and dependency bloat
([Thoughtworks Radar](https://www.thoughtworks.com/radar/languages-and-frameworks/langchain)).

**What winners did.** Segment's fix was a rule: **one version of the shared code for all destinations**,
in one repo. Eurorack's spec has barely changed in decades. Its one big addition (+5 V on a 16-pin
header) is backward compatible with 10-pin modules. LSP negotiates *capabilities* at initialise
time instead of pinning versions ([LSP specification](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)). **Few, stable contracts that are versioned as a whole; capabilities
negotiated at runtime, not resolved as a version graph.**

### 5. Unbounded power → the host can't evolve (power vs stability)

**Failure.** Firefox XUL/XPCOM extensions could reach any internal of the browser. That was their
power and the reason Firefox could not ship multi-process (Electrolysis) or change its own internals
without breaking them. In August 2015 Mozilla announced the deprecation of XUL/XPCOM add-ons for
WebExtensions, with mandatory signing
([Mozilla Add-ons Blog, "The Future of Developing Firefox Add-ons"](https://blog.mozilla.org/addons/2015/08/21/the-future-of-developing-firefox-add-ons/)).
Many popular add-ons could not be rebuilt on the narrower API, and some users went to forks (Pale
Moon, Waterfox) ([gHacks](https://www.ghacks.net/?p=115533)). Smalltalk is the same thing turned
inward: every object is visible to every other through globals, with no process isolation, a problem
the thread compares to DOS (paraphrase)
([squeak-dev](https://lists.squeak.org/archives/list/squeak-dev@lists.squeakfoundation.org/thread/DC4AXX4EANODCDH3PLQTB26IFA76JL2E/)).

**What winners did.** VS Code chose the narrow API on day one. Extensions run in a separate extension
host process and cannot impact startup, slow UI operations or modify the UI. They load lazily through
declared activation events
([VS Code: Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host);
[Our approach to extensibility](https://vscode-docs1.readthedocs.io/en/stable/extensions/our-approach/)).
They pay for it in power (no DOM access) and get a host that can keep changing. **Choose the narrow
contract before there is an ecosystem to break; widening later is cheap, narrowing later is a schism.**

### 6. Security and permissions bolted on after

**Failure.** ActiveX downloaded and ran native code with full machine access, and the only gate was a
user clicking "yes". The result was a long run of drive-by-download exploits, and CERT/CC warnings
that the model was flawed at its root
([The Register on ActiveX bugs](https://www.theregister.com/2008/03/12/realplayer_bug/);
[SC World, "Hot or not: ActiveX vulnerabilities"](https://www.scworld.com/perspective/hot-or-not-activex-vulnerabilities);
[Virus Bulletin](https://virusbulletin.com/blog/2006/09/vulnerability-reported-ie)). Figma's *first*
sandbox (the Realms shim) was escaped by security researchers within weeks of launch
([Figma, "An update on plugin security"](https://www.figma.com/blog/an-update-on-plugin-security/)).
Obsidian is candid that it still has none: "there is no sandbox", and plugins inherit the app's full
access to files and network ([Obsidian plugin security](https://obsidian.md/help/plugin-security)).
It manages the risk socially (opt-in Restricted Mode, scanning, review) instead.

**What winners did.** Figma moved plugin logic into QuickJS compiled to WebAssembly: a sandbox with
the document API but no browser APIs. The UI runs in a separate iframe with browser APIs but no
document access, and the two talk by message passing
([Figma, "How to build a plugin system on the web and also sleep well at night"](https://www.figma.com/blog/how-we-built-the-figma-plugin-system/)).
WebExtensions declare permissions in a manifest. **Capability is granted per channel, declared up
front, enforced by the host.** It is not a property of being installed.

### 7. Glue-code explosion (M×N)

**Failure.** Before LSP, every editor implemented every language: M×N integrations
([freeCodeCamp on LSP](https://www.freecodecamp.org/news/what-is-the-language-server-protocol-easier-code-editing-across-languages)).
Segment's per-destination services each had their own queue, deploy and scaling, so the ops load
grew linearly per destination
([InfoQ](https://www.infoq.com/news/2018/07/segment-microservices)). The mashup era was N bespoke
API adapters, each broken by its upstream on its own schedule.

**What winners did.** LSP and Eurorack are both **M+N standards**. Each side implements the protocol
once. Zapier absorbs the N adapters *centrally* (and gets partners to maintain them), so the user
never writes glue. **Adapters are either eliminated by a shared contract, or concentrated in one
owned place. They are never left to the user.**

### 8. Debugging across boundaries (opacity)

**Failure.** Octomind dropped LangChain once the team spent about as much time understanding and
debugging LangChain as building features. Its high-level abstractions hid what was actually sent
to the model, and when they didn't fit, dropping to lower-level code was often hard or impossible
(paraphrase of their post)
([Octomind, "Why we no longer use LangChain"](https://octomind.dev/blog/why-we-no-longer-use-langchain-for-building-our-ai-agents)).
Smalltalk images hand on whatever state the developer ended up with, frozen, with no record of how
it got that way (paraphrase)
([Cuis-dev](https://lists.cuis.st/mailman/archives/cuis-dev/2023-August/007894.html)). CASE and
low-code generated code that drifted from the model the moment someone edited it, so the model became
unusable (paraphrase, from search results surveying CASE history; see also [arXiv 2112.14073](https://arxiv.org/pdf/2112.14073)). In microservices, a failure
becomes a distributed trace.

**What winners did.** Unix pipelines can be cut at any `|` and inspected with `tee`/`less`. Excel
shows every intermediate value in a cell. Eurorack lets you pull any cable into a scope or a speaker.
Obsidian's state is files you can open in another editor. **Every cable is observable; every
composition is plain data a human can read and diff; there is always an escape hatch to the raw
layer.**

### 9. Owner dependency and ecosystem closure

**Failure.** Yahoo Pipes "stagnated, it didn't change, it didn't grow"
([VentureBeat](https://venturebeat.com/2015/06/21/6-reasons-killing-off-yahoo-pipes-was-a-bad-idea)).
It was also built on an open-RSS, open-API web that closed around it, and it died with its owner's
reorganisation ([Neowin](https://www.neowin.net/news/yahoo-pipes-is-shutting-down/)). Popfly was cut
in a 2009 budget round (it was built on Silverlight, which was itself later abandoned). OpenDoc died with Apple's finances, while Microsoft used its OS
leverage to make OLE effectively mandatory ([Wikipedia, Cyberdog/OpenDoc](https://en.wikipedia.org/wiki/Cyberdog)).
A composition stored on someone else's platform dies with that platform.

**What winners did.** Eurorack's spec is published and free; "a whole cottage industry flourished
around Doepfer's specifications" and no manufacturer owns the aesthetic
([Wikipedia: Eurorack](https://wikipedia.com/wiki/Eurorack);
[Perfect Circuit](https://www.perfectcircuit.com/signal/doepfer-a100-eurorack-overview)). Obsidian's
data is Markdown on your disk, so it outlives Obsidian. **The composition format must outlive the
kernel that runs it.**

### 10. Unprotected physical/structural edges in the standard itself

**Failure, even in a winner.** Eurorack's power header can be inserted backwards. On 16-pin
connectors that shorts +5 V and +12 V through the module's ground pins and can damage the supply and
other modules. Protection was left to each maker, and some deviate from the standard to survive it
([Rossum Electro-Music, "Circuit protection"](https://www.rossum-electro.com/pages/daves-lab-circuit-protection)).

**Lesson.** The one thing every module must do right (power, the cable's own framing) should be
impossible to do wrong, or be enforced by a test. Don't leave it to the care of each author.

## Pattern summary

| # | Failure pattern | Archetype failure | What the winner did |
| --- | --- | --- | --- |
| 1 | Platform before product | Wave, OpenDoc, greenfield microservices | Each module a product alone (Obsidian, Unix, A-100); monolith first |
| 2 | Composition tax / blank canvas | Yahoo Pipes, Popfly | Templates and presets as the front door (Zapier pages, Excel's instant feedback) |
| 3 | LCD interface that erases the domain | IFTTT, low-code | A domain-native payload plus minimal typing (text, voltage, LSP schema) |
| 4 | Version skew | OSGi, DLL hell, Segment's shared libs | One version of the shared contract; capability negotiation (LSP) |
| 5 | Unbounded power freezes the host | XUL, Smalltalk image | Narrow API, out-of-process, lazy activation (VS Code) |
| 6 | Security bolted on | ActiveX, Figma's Realms, Obsidian | Sandbox plus declared capabilities (Figma QuickJS, WebExtension manifests) |
| 7 | Glue explosion (M×N) | Mashups, Segment ops | M+N protocols (LSP, Eurorack) or centrally owned adapters (Zapier) |
| 8 | Opaque boundaries | LangChain, Smalltalk image, CASE drift | Inspectable cables, plain-data compositions, escape hatch |
| 9 | Owner dependency | Pipes, Popfly, OpenDoc | Open spec, data on the user's disk (Eurorack, Obsidian) |
| 10 | Unprotected edges in the standard | Eurorack power header | Make the must-do-right thing impossible to get wrong |

## What is the cable/jack/patch here

The patch bay is a working miniature of a composable system. Mapping the patterns onto its own
mechanisms:

**What it already avoids**

- **Pattern 3 (LCD), done the Eurorack way.** Every cable carries "one mono block of 128 samples", a
  payload native to the domain, exactly like voltage. Jacks have three *kinds* (`audio`, `control`,
  `note`). Audio and control mix freely "on purpose" because modulating with audio is the domain's
  pleasure, and `canConnect` gates only the one dangerous mismatch (note). That is minimal typing:
  enough to stop nonsense, not enough to model everything.
- **Defined semantics for the hard cases.** Several cables into one input are *summed*. Feedback loops
  are *legal*, at a stated cost of one quantum (2.7 ms). The running order is derived, not configured.
  Many composable systems fail at exactly these edges (merge, cycles, ordering), leaving them undefined
  or as runtime errors.
- **Pattern 10 and pattern 4, via the contract test.** `registry.test.ts` holds every plugin, "whoever
  wrote it", to the same conformance suite: unique ids, defaults in range, every output sample
  written, finite output for 400 quanta of noise at every param extreme. That is the Eurorack spec
  plus a reverse-polarity diode, made executable.
- **Version skew.** `type` is "never renamed once shipped". Patches saved before channels existed
  "open on In 1 and Out 1–2, sounding exactly as before". Edits diff the running patch and keep state.
  The contract is one file (`types.ts`) and is versioned as a whole, the Segment rule.
- **Pattern 7 (M×N).** A module "knows or cares" nothing about its neighbours. Adding a plugin is
  "one file, one line and its tests", and it is "playable everywhere at once". That is M+N.
- **Pattern 5, partly: lazy activation.** Modules that don't reach an output are *parked*: they keep
  their state, cost nothing and read as silence. That is VS Code's activation events in DSP form.
- **Pattern 2 (blank canvas).** Presets are "starting patches", each "complete and playable: pick it,
  press Start, sing". These are Zapier's workflow pages.
- **Pattern 8, partly.** A patch is "plain data", saved, restorable, with undo. It is the opposite of
  a Smalltalk image. `PatchRuntime` is pure and tested outside the browser.
- **Pattern 9.** The patch format is the same for the browser and the future Pi engine. The patch names
  channels, never devices, so "a patch made on one desk opens unchanged on another".
- **Pattern 1.** Sonic had a fixed chain with presets (D-016) and a working vocoder/transposer *before*
  the patch bay (D-018). It went monolith-first and then cut.

**What it does not yet avoid**

- **No isolation (pattern 5/6).** The whole patch runs in one `sonic-patch` worklet. One plugin that
  allocates, loops, or takes 2 ms stalls every other module and the audio itself. The contract test
  catches non-finite output, not a time-budget overrun. There is no per-module deadline or kill.
- **Permissions are avoided by being closed (pattern 6).** All plugins are first-party, from the
  registry. The ActiveX/Obsidian question ("what can a third-party module touch?") arrives with the
  first plugin the owner didn't write. Today a module could, in principle, do anything the worklet can.
- **Debugging across boundaries is open (pattern 8).** "Latency per route" is listed as not built.
  There is no cable probe either: you cannot put a scope on an arbitrary cable the way a Eurorack
  player would, and modules report only their own `report()` readouts.
- **Cost is per module, not per composition.** The Pi budget for a whole patch is unmeasured. That is
  the composability version of "each part fine, the whole too slow" (OpenDoc's memory footprint).
- **Contract upgrades are untested.** `type` stability covers renames. There is no stated rule for a
  plugin that changes a param's range or removes a jack after patches using it exist.

**Translating to the broader platform** (writing tool, knowledge base, swarm, research tool): the
"cable" is the hardest question. Sonic's cable works because audio is domain-native and uniform. For
documents, tasks, findings and agent runs there is no single native payload like voltage. That is
exactly where IFTTT (too thin) and OpenDoc/LangChain (too abstract) failed. The kernel needs a
payload as obvious to its modules as a 128-sample block is to a DSP module: probably *files/records
with a small typed envelope*, Obsidian-style, rather than an object model.

## Implications for the kernel

A pass/fail checklist. Any proposed kernel should be argued against each line, with the evidence
written down.

1. **Single-module test.** Each first module (writing tool, KB, swarm, research) is worth using with
   no other module present. *Fail if* the pitch for any module starts with "once it's connected to…".
   (Wave, OpenDoc)
2. **Monolith-first test.** At least two modules have run in production *before* the kernel boundary
   between them was drawn, and the boundary was drawn from what actually crossed it. (Fowler, Segment)
3. **One-page spec test.** The kernel's contract (payload, port kinds, lifecycle, permissions) fits on
   one page, like Eurorack's and like `types.ts`. *Fail if* it needs a framework to read.
4. **Native-payload test.** The cable's payload is something every module already handles natively
   (text/files/records), with typing only where a mismatch would be harmful. *Fail if* modules must
   convert into a kernel-specific object model to participate. (OpenDoc, LangChain vs Unix, Eurorack)
5. **Ceiling test.** A composition can branch, filter, merge and loop, with defined semantics for
   each (Sonic: sum, one-quantum feedback). *Fail if* the model is trigger→action only. (IFTTT)
6. **M+N test.** Adding module N+1 touches its own files plus one registry line. It never touches
   existing modules. Adapters, where unavoidable, are modules on the table, not code hidden in the
   kernel. (LSP, Sonic's registry)
7. **Conformance test.** An executable contract suite that every module, whoever wrote it, must pass
   to be loadable. It covers the "reverse power" cases: malformed output, timeouts, oversized payloads.
   (Sonic `registry.test.ts`, Eurorack power)
8. **Isolation test.** A module that hangs, crashes or leaks cannot stall the kernel or its neighbours.
   Its failure is visible on its own card. (VS Code extension host, XUL)
9. **Capability test.** A module declares what it may touch (files, network, other modules' data, the
   ability to spend money/tokens or run agents). The kernel enforces it per cable/capability, and it
   is shown before enabling. *Fail if* trust is a property of "installed". (ActiveX, Figma, Obsidian)
10. **Skew test.** A saved composition from the previous release opens and runs after one module is
    upgraded. Contracts are versioned as a whole; capabilities are negotiated, not resolved as a
    version graph. (OSGi, Segment, LSP)
11. **Plain-data test.** A composition is a human-readable, diffable file that lives in version control
    and can be edited by hand or by an agent. *Fail if* state exists only inside a running kernel.
    (Smalltalk image, CASE drift)
12. **Probe test.** Any cable can be inspected live (last payload, rate, latency/cost along a route),
    with no code changes. (Unix `tee`, Eurorack scope, Sonic's open "latency per route")
13. **Escape-hatch test.** For every abstraction the kernel offers, a module can drop to the raw layer
    (the actual prompt, the actual file, the actual API call) without forking the kernel. (LangChain)
14. **Front-door test.** The kernel ships with presets: whole compositions that do something useful on
    first run. A new user never meets an empty table. (Zapier, Sonic presets, Excel)
15. **Outlives-the-kernel test.** If the kernel disappeared tomorrow, the user's data and compositions
    would still be readable and mostly usable with other tools. (Pipes, Popfly vs Obsidian, Eurorack)
16. **Whole-composition budget test.** Cost (tokens, time, money, CPU) can be summed along a
