# 03 — Product critique: what is being built, for whom, and the smallest thing that proves it

Iteration 3, product half. The technical critique (`03-critique-technical.md`) is written in
parallel; this document stays on the product side. It asks what the product is, who uses it for
what on day 1 and at month 6, and what slice would prove or kill the idea in weeks.

Sources:
- `01-inventory.md` (INV), `01-failure-modes.md` (FM), `01-ai-landscape.md` (AI),
  `01-data-model.md` (DM), `01-prior-art.md` (PA);
- the three kernels, `02-kernel-a-patchbay.md` (A), `02-kernel-b-ledger.md` (B) and
  `02-kernel-c-namespace.md` (C);
- swarm's `docs/product/{principles,simple-model,decisions}.md`;
- sonic's `docs/product/{principles,patch-bay}.md`;
- printer's `.claude/improve-round.md`.

**The verdict in five sentences.**
1. The product is a **personal product-development toolchain for one builder working across
   several projects**: research → decide → specify → build → learn. It is not a general
   composable-tools platform, and not yet something anyone else uses.
2. Today the owner already composes these steps by hand. Claude Code sessions, round briefs in
   Markdown, `STATE.md` files and the decision register carry the work, and the platform must
   beat that "null kernel", not an empty field.
3. The first slice is the composition the owner is performing right now in this folder:
   a research loop whose output is decisions for the owner, which, once accepted, become the
   pinned basis of swarm features.
4. The kernel for that product is **C's files-in-git substrate, with A's descriptor and
   `canConnect` vocabulary and no scheduler**. B's ledger is the right destination only if the
   product later becomes multi-user or highly automated.
5. People see and shape a composition **in conversation with an agent that writes a plain-text
   patch as a diff**, starting from presets. The patch has a read-only rendered view. It does
   not get a graph editor.

**Three stages. Every later section says which one it describes.**

| Stage | What exists | When |
|---|---|---|
| **S0, the slice** (§2) | Two standalone CLIs, `decide` and `research`, plus swarm's `--basis`, composed by a skill or a two-line recipe. This is a null kernel on purpose: no patch format, no `run` verb, no scheduler. | Weeks 0–6 |
| **S1, the v1 kernel** (§5) | C's verbs `run`, `put`, `approve` and `check`, the envelope, the protected path, and A's descriptor fields. Recipes compose the modules. | Only if S0's evidence advances, and drawn from the friction S0 recorded |
| **S2, the end state** (§3) | The patch file in git becomes the authority. It is authored through conversation, with presets and a read-only view. B's ledger is added only if the toolchain becomes multi-user or runs unattended. | Once compositions are reused often enough to need a format |

## 1. What is the product?

### Three readings, and what each would demand of the kernel

| Reading | Who uses it | What it must be good at | Kernel it implies |
|---|---|---|---|
| **Personal toolkit** | The owner, across swarm, sonic, printer, square and whatever comes next | Low ceremony, plain files the owner and Claude Code already read, cross-project memory, human gates, cost visibility | C (files in git) with A's vocabulary; no daemon |
| **Developer platform** | Other developers write modules for it | A stable published spec, conformance tests, version-skew rules, a registry, docs | A or B: the contract must be strict and versioned as a whole (FM tests 3, 7, 10) |
| **Product others buy** | Non-developer knowledge workers | A front door: UI, onboarding, presets, hosted models, sync, accounts | None of the three. All three score only *partial* on FM test 14 (front door). A, B and C all assume a terminal. |

**Recommendation: a personal toolkit for the next six months, built with a platform's
discipline in its *formats* only.** The reasons:

1. **The only user is known.** There is one user with an observable practice: four projects, two
   swarm boards, 50 decision lines in `decisions.jsonl` files, 33 handwritten `D-` entries in
   swarm's `decisions.md`, three independent "round" implementations (INV pattern 5), and this
   research loop. Designing for a hypothetical developer or buyer means guessing the job. The
   owner's own principle is "Earn complexity" (swarm principle 10), and sonic's principle 9 says
   "Small and usable beats large and nearly working".
2. **The other two readings fail the first FM tests.** A developer platform with zero
   third-party developers is OpenDoc (FM pattern 1). A product for others with no front door is
   Yahoo Pipes (FM pattern 2).
3. **What is expensive to change later is the formats.** The record envelope, the patch file
   and the human-only rule are what a later platform would inherit. Getting those right costs
   little. The runtime can be thrown away (FM test 15: "the composition format must outlive the
   kernel that runs it").

What "Unix spirit" should mean here is **a property of the format**: plain files, small tools
each usable alone, text a person can read. It should not be the pitch. "A composable platform
for writing, KB, research and delivery" is the sentence FM test 1 fails on ("Fail if the pitch
for any module starts with 'once it's connected to…'").

### What the owner actually does repeatedly (the real jobs)

Iteration 2 picked C1–C3 to *stress the kernel*. Checked against the owner's files, only one of
them is a job the owner does:

| Composition | Evidence it is a real, repeated job |
|---|---|
| C1, a sourced article | **None found.** No blog, essays or articles exist in `~/www`. The owner's "writing" is product docs: `principles.md`, settled feature specs (`patch-bay.md`, `simple-model.md`), decision entries and research reports. |
| C2, swarm ⇄ decision register | **Strong.** Two boards, D-016 "decisions govern context", and the documented gap that `basis` is always `[]` (`simple-model.md` "Not built yet"). |
| C3, a draft through a critic loop | **Partial.** Swarm already has a `product-critic` subagent, and this folder runs a critique iteration. The draft being criticised, though, is a spec or a research synthesis, not prose for readers. |

The jobs the owner *demonstrably* repeats:
1. **Research a design question** with parallel tracks, numbered documents, a critique pass and
   a synthesis that ends in decisions for the owner. Examples: this folder,
   `swarm/docs/research/2026-09-agent-first-product-development.md`, and the iteration-2
   kernels.
2. **Settle a design in conversation** and write it down as a spec with a "Status: settled …
   as D-NNN" header. Example: `patch-bay.md` was settled "in conversation in Claude Code" when
   the owner chose "Accepter den", which became sonic D-018.
3. **Deliver features in rounds against settled decisions**: swarm, plus printer's and square's
   `/loop` round briefs.
4. **Keep principles and decisions current across projects**, and notice when they drift.
   Sonic's `AGENTS.md` and `decisions.md` still come from swarm's classic era (INV §2, Gaps).

So the four named modules map onto the owner's own loop (swarm principle 8: build → use →
evaluate → learn → change):

| Named module | What it is *for this owner* | Exists today as |
|---|---|---|
| Research tool | Answer a design question with sources and end in decisions to make | A practice: this loop, `docs/research/`, `STATE.md` |
| Knowledge base | Accepted decisions, principles, settled specs and research, across projects, with relevant context retrieved rather than dumped (swarm principle 6) | `docs/product/` + the register (`src/board/decisions.ts`, unplugged) |
| Writing tool | Turn a conversation plus decisions into a settled spec, a principles revision or a feature idea | Claude Code conversations, with the result committed by hand |
| Swarm | Deliver a settled idea in judged rounds | Built and dogfooded |

### Day 1 versus month 6

- **Day 1.** The owner asks a design question and gets a research run that ends in proposed
  decisions. They accept some, reject others, then run `swarm add` on a feature, and the round
  is built against the accepted decisions, pinned by revision. Nothing is copied by hand, and
  every hop is a file they can open.
- **Month 6.** One place answers "what have I decided, where, and why?" across all projects.
  New projects (square has no product docs at all) start with a principles file and a register
  from day one. A spec is drafted from the decisions it rests on, and a critic checks it against
  the principles. Three or four presets cover the recurring flows. Starting one is a sentence to
  an agent, not a graph to draw.
- **What month 6 is not.** It does not include a marketplace, third-party modules, a canvas or
  sync between people. If any of those appears on the plan before month 6, treat it as the
  platform-before-product signal.

## 2. Platform before product: which module first, which second, and the slice

### Three of the four named modules do not exist, and that is the main risk

FM test 2, monolith-first, asks for two modules that have *run in production before the
boundary between them is drawn*. Today one exists (swarm), plus a register that is built but
unplugged. Kernel A scores this test as a **fail**. B and C score it as partial *by design, not
proven*. Any kernel built now would be drawn around three imagined modules, and their jacks
would be guesses. This is the exact shape of Wave and OpenDoc.

There is a second, quieter risk. **The owner already has a composition medium, and it is good.**
Claude Code with skills, subagents, `/loop`, round briefs in Markdown and `STATE.md` files is
how printer, square and this research get orchestrated. It is flexible, conversational and
costs nothing to change. The platform must beat **the null kernel**: "a skill that reads
`docs/product/decisions.md` and then runs `swarm add`". If the null kernel is good enough, the
right outcome is conventions, not a kernel. That is a legitimate result, and §2 ("Evidence that would advance or kill the idea") makes it one
of the measured outcomes.

### The answer in one line

**The first new module that must be worth using alone is `research`. The first composition is
research → `decide` → swarm basis, and the typed meeting point is `decision`.** `decide` (the
register) is an enabling extraction that has to land first. It is not the proof.

### Module 1: swarm (already worth using alone), plus the register as the first extraction

Swarm passes FM test 1 today. The question is which **second** module makes the **first**
composition obviously valuable. Candidates:

| Second module | Alone-value | Composition with swarm | Verdict |
|---|---|---|---|
| **Decision register** (`decide`) | Moderate. It is one place for D-ids, proposed ≠ accepted, supersession, and a projection into each project's `decisions.md`. The owner already maintains this by hand and by projection. | C2: the accepted basis is pinned into every round, conflicts are flagged, and approve proposes new entries. **It closes a documented gap.** | **Extract first.** It is cheap and pure, and the seam already exists. But C2 alone proves *extraction*, not *composition*: it could all be done inside swarm. |
| **Research loop** (`research`) | **High, and demonstrated.** The owner chose to run one for this very question, and earlier ones exist. | Research ends in proposed decisions → the register → swarm's basis. That is two independent tools meeting at one typed artefact (`decision`). | **Build second. This is the composition that proves the idea.** |
| Knowledge base (beyond decisions) | Unclear until there is content beyond decisions and principles | Retrieval for basis and research | After the slice. It grows out of the register plus research outputs. |
| Writing tool | Low as a separate tool. Claude Code already writes the owner's specs well. | Spec drafted from decisions → a swarm idea | Later. It is the most "Claude Code already does this" of the four. |

**Why research before KB or writing.** It is the only new module whose standalone use is
*already observed*, and its natural output (decisions the owner must make) is exactly the typed
input the register needs. The "KB" is then no longer a vague store. It begins as the register
plus the research archive, and it grows only when a retrieval need shows up.

**Watch the noise in the register.** Of swarm's 29 `decisions.jsonl` lines, six come from one
feature (`f-54e88f`, adopting a CSS component library). They record things like "Capped
--pico-font-size at a flat 100%". Agent hand-backs produce implementation choices at volume.
The decisions the owner and agents actually cite are the 33 `D-` entries in swarm's
`decisions.md`, all handwritten above the generated region. A register fed raw from hand-backs becomes noise that dilutes
the basis. So **proposed must stay proposed until a person promotes it**, and "accept all on
approve" (today's simple-model behaviour, D-015 superseded) deserves a second look. That is a
product judgement, so it appears in §6.

### The first slice (about four weeks), deliberately kernel-light

Build the formats and the two CLIs. Do not build the runtime.

**Week 0: precondition.** Carve the register out before D-033 deletes the classic tree.
- The register's pure core is `src/board/decisions.ts` (420 lines), plus `decisionBasis.ts`
  (199) and `decisionDoc.ts` (443).
- All three sit in `src/board/`. Appendix A of `simple-model.md` schedules "about 6.5k lines in
  `src/board/*`" for removal, while Appendix B marks D-023/D-025 (register and surface) as
  "kept".
- The deletion and the extraction collide. Do the extraction first, or carve it out of the
  deletion explicitly.

**Week 1: `decide`, the register as its own CLI.**
- Verbs: `propose`, `accept` (human-only, outside every sandbox), `supersede`, `show`,
  `basis --json` and `project`.
- Import what exists. **There are no live register records anywhere.**
  - Swarm's generated region says "No decisions have been taken into the register yet".
  - Neither repo has a `.swarm/decisions/` directory.
  - Sonic's 18 `D-` entries survive only as a generated Markdown projection.

  So the import means parsing Markdown: swarm's 33 handwritten entries and sonic's
  projection. It also takes in the two `decisions.jsonl` files. Each entry is reviewed once by
  the owner as it comes in. Budget about two days for this, not an afternoon.
- One per-user workspace with a space per project. The projection into each project's
  `docs/product/decisions.md` stays exactly where it is.
- **Swarm changes, and nothing else:**
  - `swarm add --basis <file>`;
  - write the hand-back's decisions as `decide propose` records.

  This is C2. `decide` must be worth using without swarm, by the owner at the terminal and by
  Claude Code in any repo.

**Weeks 2–3: `research`, the loop in this folder made a tool.**
- `research start "<question>"` makes a folder with `STATE.md`. Iterations run parallel tracks
  as sandboxed agent runs and write numbered documents.
- A critique pass follows, then a synthesis whose last section is **proposed decisions**,
  written as `decide propose` records with `derivedFrom` links to the research documents.
- Reuse swarm's agent runner and sandbox through the seam that already exists (INV §1, "Shared
  seam already"). Do not extract a generic round engine yet.

**Week 4: use it on real work.**
- Two or three real *design* questions that sources and argument can settle, such as this
  folder's question or "how should square store saves and missions". Avoid questions gated on
  a measurement, such as sonic's Pi budget or lab runtime. Those are settled on the Zynthian,
  not by research, and a run on them would fail for reasons that say nothing about the tool.
- At least five swarm features whose basis comes from `decide`.

**What is deliberately not in the slice:**
- a patch file format;
- a scheduler;
- `canConnect` beyond the one rule "only a person writes `accepted`";
- MCP;
- a KB beyond decisions;
- the writing tool.

The composition is a two-line shell sequence or a skill. **This is the null kernel, built on
purpose, so its friction can be measured.**

### Evidence that would advance or kill the idea

Every item below can be read from files that already exist, or will exist in the slice. None
depends on how it felt to use.

| Signal | Where to read it | Advances if | Kills, or demotes to conventions, if |
|---|---|---|---|
| **The basis changes outcomes** | The hand-back's `decisions[].relation` and the round's pinned `basis` | Rounds cite basis entries (`follows`/`conflicts`/`supersedes` referencing pinned D-ids), and reviewer findings reference them | After five or more features, no hand-back references a pinned decision. The basis is then context nobody reads. |
| **Research ends in action** | `decide` records with `derivedFrom` → `research/…` | At least one research run per question yields accepted decisions that a later swarm basis pins | Research outputs are read and then re-typed by hand into `swarm add` or a conversation |
| **Hand-copying stops** | `swarm add` ideas compared with research or decision text, and the owner's shell history | Ideas reference decision ids and research paths | The owner keeps pasting prose between tools; the typed hand-off is bypassed |
| **The null kernel hurts** | A friction log kept in the slice's own `STATE.md` | Concrete failures that a kernel would prevent: a stale basis, a forgotten accept, runaway spend, "why did this run?" | **The skill plus two CLIs is enough. Stop there: keep `decide` and `research` as tools and write the conventions down.** |
| **Cross-project pull** | `decide show --space` usage, and sonic boards pinning swarm-wide decisions | The owner asks cross-project questions | Every query is single-project. In that case the per-project register is enough, and so is the per-project `docs/product/`. |

**Time box: four weeks of build plus two weeks of use.** At the end, the owner decides between
three outcomes:
1. extract a kernel from the friction actually observed;
2. keep tools plus conventions (null kernel wins);
3. stop.

All three are successes of the slice. Only "keep building the kernel without that evidence"
is a failure.

## 3. How does a human see and shape a composition?

### The variable that decides it is feedback latency and cost per try

Sonic's patch table works, and the owner built it, so "graph editors fail" is the wrong lesson.
The difference that matters:

| | Sonic patch bay | This toolchain |
|---|---|---|
| Time from cable to result | One render quantum, 2.7 ms. You hear it immediately. | One round: minutes to hours |
| Cost of a try | $0 | $0.50 to $25 per composition run (A's C1 estimate is $6.50; C3 is up to $18) |
| What tells you it worked | Your ear, instantly (sonic principle 12: "experimenting is frictionless") | Reading documents, later |
| Number of distinct patches | Many, played with | Few, reused (presets) |

Nardi's spreadsheet point (FM pattern 2) is that the "twinkling lightbulb" of instant
recalculation makes direct manipulation pay. Knowledge-work compositions do not twinkle: you
cannot wiggle a cable and hear the research change. The evidence on canvases for slow, costly
flows is bad:
- Yahoo Pipes and Popfly died (FM pattern 2).
- OpenAI is reported to be shutting down Agent Builder, the only major-vendor visual agent
  graph. **This is secondary-sourced only**: openai.com returned 403 (AI §1.4, open items). Its
  migration path is toward code (the Agents SDK) and natural-language workspace agents.

### How the owner actually shapes things today

- **Sonic's patch bay was settled in conversation.** The owner wrote one sentence ("Effekterne
  skal kunne kombineres på kryds og tværs via virtuelle ledninger"), an agent proposed the
  design, and the owner chose "Accepter den" (`patch-bay.md` header, D-018).
- **Swarm principle 2: "Product design is conversational and human-led"**, and the human
  "react[s] to concrete proposals" rather than authoring formal documents.
- **Swarm principle 4: "the board is a projection"**, not the authority.
- **Printer's and square's loops are prose briefs** (`improve-round.md`) that an agent executes.
  The owner composes *in Markdown, through an agent*, already.

### Recommendation (stage S2; S0 and S1 use a skill and recipes)

1. **The authority is a plain-text patch file in git.** It is YAML or a recipe, and the owner can
   read and diff it. This keeps FM test 11 and test 15.
2. **The patch is authored mostly through conversation.** The owner says what they want ("after
   research, propose the decisions to sonic's register, and start nothing"). An agent writes or
   edits the patch, and the owner **approves the diff**. This is the same gate A already requires
   for edits that widen an agent's inputs (A §7.10), turned into the main interaction rather than
   a tax.
3. **Presets are the front door.** Ship three, drawn from the real jobs in §1: research → decide;
   decide → swarm basis; spec → critic → owner. Each is complete and runs on first use, as sonic's
   presets do ("pick it, press Start, sing").
4. **A read-only rendered view replaces the editor.** It shows the graph with costs and
   human gates marked, generated from the file, in the style of swarm's board page and B's
   `compose show`. It is for *seeing*, not editing. Build an editor only if the owner keeps
   wanting to drag something there.
5. **Never only a conversation.** A composition that exists only in a chat transcript breaks
   swarm principle 7 ("Conversation is not product state"). The conversation writes the file. It
   does not replace it.

## 5. Which kernel, and what to cut for v1

*This section describes stage S1, the v1 kernel. It is built only if S0's evidence advances.*

### Reweighting the iteration-2 scores from the product side

The self-scores were A 11/4/1, B 12/4/0 and C 7/9/0, and B and C each offered to sit under A.
For a personal toolkit at the slice stage, the tests do not weigh the same:

| Weighs more for this product | Why | A | B | C |
|---|---|---|---|---|
| 1 Single-module | Each tool must stand alone (§2) | Partial | Pass | **Pass** |
| 2 Monolith-first | Three modules are unbuilt | **Fail** | Partial | Partial (cheapest to satisfy) |
| 11 Plain data | The owner and Claude Code read files | Pass | **Partial**: the topology is derived, not written | Pass |
| 13 Escape hatch | The owner debugs by reading files | Pass | Pass | **Pass**: the raw layer is the interface |
| 15 Outlives the kernel | The slice may end in "conventions win" | Pass | Pass | **Pass**, strongest |

| Weighs less for now | Why |
|---|---|
| 5 Ceiling, 12 Probe, 16 Whole-composition budget | These matter once compositions run unattended. In the slice every paid run is started by the owner, and each run has a hard cap. |
| 9 Capability as a full model | One rule carries the slice: only a person writes `accepted`. Everything else is nono profiles, which swarm already has. |
| 10 Skew | One user, first-party modules, both versioned in the owner's repos |

On those weights, **C wins as the substrate**. The weaknesses that leave C partial are all about
time: events, live loops, mid-run human input (C §7). They are exactly the things the slice
deliberately does without.

**The pick: a hybrid of C's substrate and A's vocabulary, with no runtime from A or B.**
- **From C:** the workspace is a git repo of plain records (Markdown or JSON with an envelope).
  `run` stamps provenance and sandboxes the run. `decisions/accepted/` is a protected path
  written only by a signed human command. Every module is a plain CLI that works without the
  kernel.
- **From A:** the descriptor fields that carry meaning for the owner:
  - `kind` per input and output;
  - `cost` and `latency` in words;
  - `agent: true|false`;
  - `drivenBy: human`.

  Also take A's `canConnect` rule that refuses agent → human-only. Keep the *patch file* as the
  future composition format (§3), even if v1 compositions are recipes.
- **From B, later and not now:** the per-record envelope with `prov.reads` (the reads-set),
  refusals as records, and the ledger as an index *over* the files. Adopt B if and when the
  product becomes multi-device, multi-user or mostly automated. B's own recommendation (B §7) is
  that the store underneath should probably be the ledger "either way". From the product side
  that is premature: B's invisible, derived topology needs `compose show`, `why` and graph diffs
  before it is usable (B §7.1–7.2). That porcelain is a second product for a solo builder to
  build.

### Cut for v1, as concrete spec elements

From A's one-page contract (A §1), cut:
- **SCHEDULE** (`reach ∧ dirty ∧ budget`), **hot/cold inputs** and the terminal `done` status.
  Runs are started by the owner or a recipe.
- **POLY** (voices).
- **`relays`** and the `swarm.rounds`/`swarm.merge` split. Swarm keeps its own approve, and
  `decide accept` is a separate human act.
- **Service jacks and the MCP proxy.**
- **The model gateway.** Spend is capped by each module's own budget flag, as swarm does today.
- **Back cables with `{max, then}` / `{gated}`.** v1 has no automatic loops. The one loop,
  spec ↔ critic, uses C's `ns loop --max N` porcelain with the bound written in the recipe.
- **Kinds `signal` and `claim`.** Keep `doc`, `decision` and `artifact`. `claim` returns when
  research emits checkable claims and something checks them, which is A's and C's C1, deferred
  with the article job.
- **CONFORM**, reduced to `ns check` on envelopes and protected paths.

From C, cut:
- **The `server` mode with `owns:`/`ctl/`.** Swarm stays an ordinary CLI that `decide` and
  `research` call or are called by; it is not moved into the workspace.
- **`ns serve --mcp`.**
- **`ns watch`.**

Keep: the envelope (`kind`, `type`, `links` as `path@sha`, `run`), `run` with
sandbox + budget + stamp + content-keyed cache, `put`, `approve` (signed, human-only), `check`,
and the protected path for accepted decisions.

## 6. Five decisions only the owner can make

Each turns on scope, taste or risk appetite. No further research settles them.

1. **Who is this for in its first six months?**
   - *Why it matters:* it decides the kernel (§1). A platform for others needs a strict,
     versioned spec and a front door. A personal toolkit needs neither, and is harmed by both.
   - *Default:* **personal toolkit**, with a deliberate review at month 6 asking whether a second
     person should use it. Formats are kept clean enough that the answer can be yes.

2. **Which new module comes first: research, a broader KB, or writing?**
   - *Why it matters:* the first new module decides which composition proves the idea and which
     boundary is drawn from real crossings.
   - *Default:* **research**, because it is the only one already practised (this folder) and its
     output, decisions to make, is the typed input the register needs. The KB grows from the
     register; writing comes last.

3. **One workspace per person, or registers per project?**
   - *Why it matters:* cross-project memory is the main promise of the KB ("what have I decided,
     and where?"). But it moves decisions out of each project's repo, where swarm and the agents
     read them today.
   - *Default:* **one per-user workspace with a space per project.** The projection into each
     project's `docs/product/decisions.md` stays, so every project still reads as it does now.

4. **What may happen without the owner pressing a button?**
   - *Why it matters:* this decides whether a scheduler (A or B) is in scope at all. It sets the
     spending risk. It also decides whether "approve accepts every decision on the hand-back"
     stays, given the register-noise evidence in §2.
   - *Default:* **in v1 nothing paid runs unattended.** Only deterministic, $0 steps
     (projection, `check`) run automatically. Approve merges, but decisions stay proposed until
     the owner promotes them, individually or in a batch. Revisit once a composition has been run
     ten times the same way.

5. **What is the time box, and what counts as a kill?**
   - *Why it matters:* "the right solution, not the easiest" can turn into an open-ended platform
     build that competes with sonic and swarm for the owner's attention. The slice is only
     useful if its failure is allowed to end something.
   - *Default:* **four weeks of build plus two of use**, judged on the signals in §2 ("Evidence that would advance or kill the idea"). "Two CLIs
     and a skill are enough" is accepted as a valid outcome, not a defeat.

One sequencing point is not a decision but needs the owner's word: **finish D-033's classic
deletion with the register carved out**, so the extraction is not done twice or lost.

## What is the cable/jack/patch here

| Patch-bay concept | Product-side reading |
|---|---|
| **Module** | A tool the owner would use with no other present: `swarm`, `decide`, `research`. Its jacks are discovered from real crossings, not designed up front. |
| **Jack kind** | Three for v1: `doc`, `decision`, `artifact`. `decision` is the one that pays: it is the artefact research produces, the owner judges and swarm consumes. |
| **Non-modulatable param** | `accept` and `approve`. The product's spine is that these stay human, and the owner is the only principal. |
| **Cable** | A recipe line or skill step that passes a pinned `path@sha` from one tool to the next. In v1 it is written in text, and agents propose it in conversation. |
| **Patch** | A plain-text file in git, authored through conversation and approved as a diff, with presets as the front door and a read-only rendered view. It is never a canvas first. |
| **Quantum** | One round: minutes to hours and dollars, not 2.7 ms. That latency is why a canvas does not pay here as it does in sonic. |
| **Parked module** | A tool nobody invoked. In v1 this is trivially true because nothing runs on its own. |
| **Preset** | The three real jobs: research → decide, decide → swarm basis, and spec → critic → owner. |

## Implications for the kernel

1. **Product first: a personal product-development toolchain for one builder across projects.**
   Generality is a property of the formats, never the pitch.
2. **Draw no kernel boundary before two tools have crossed it in use.** The slice builds `decide`
   and `research` with a null kernel and measures the friction (§2, "Evidence that would advance or kill the idea").
3. **The formats are the kernel's durable part.** Fix them now:
   - the envelope;
   - the `decision` lifecycle with human-only `accepted`;
   - `path@sha` pinning;
   - the patch-as-text file.

   The runtime is the disposable part, so defer it.
4. **Substrate: C. Vocabulary: A's descriptor and `canConnect`.** No scheduler, poly, relays,
   service jacks or gateway in v1. B's ledger is the upgrade path if the product becomes
   multi-user or unattended.
5. **The UI is conversation → patch diff → human approval**, with presets and a read-only view.
   The graph-editor evidence (Pipes, Popfly, and Agent Builder, secondary-sourced) applies here
   because rounds are slow and paid. It does not apply to sonic, where tries are instant and
   free.
6. **The register is extracted before the classic tree is deleted**, and it gains a curation
   gate. Agent hand-backs propose; only the owner promotes, or the KB fills with
   implementation trivia.
7. **The benchmark is the null kernel:** Claude Code with skills plus the owner's CLIs and file
   conventions. A kernel is justified only by failures it would have prevented, recorded during
   the slice.
