# 02 — Kernel A: "Patch bay". The explicit graph is primary

Iteration 2, candidate A of three (see `STATE.md`: A "patch bay", B "ledger", C "namespace").
Brief: push the patch-bay idea to its strongest honest form, show C1–C3 as real patch data,
score it against the 16 tests in `01-failure-modes.md`, and name what it makes hard.

**The stance that separates A from B and C.** In A, **the patch is the authority.** A module
reads only what a cable brings it, writes only to its own outlets, and runs only when the graph
says so. **No cable means no read, no flow and no run.** Like B, A has an immutable,
content-addressed record store with provenance stamped by the kernel (`01-data-model.md` §3.3).
In A, though, the store sits *under* the patch as a kernel service. It is not a place modules
query. B lets modules react to anything in the log. C lets modules see whatever is bound into
their namespace. A makes the **user-visible topology** the single answer to three questions:
who may see what (grant), what runs (schedule) and what it costs (budget).

---

## 1. The core idea

> A **patch** is a plain-data graph (modules, cables, params) that the user owns, reads and
> versions. Every module declares typed **jacks** in a descriptor. The kernel is the only
> broker between modules, so a module receives exactly what is cabled into it and nothing else:
> **a cable is a capability grant.** A module runs only when three things hold: it reaches a
> **sink** (a person's inbox, a publish, a merge); one of its inputs has a newer revision than
> the one its last run used; and its budget allows it. Otherwise it is **parked**, with its state
> kept, and it costs nothing. A cable that closes a loop reads the source's *previous completed*
> revision, the one-quantum rule of Sonic (`patch-bay.md`, "Order and feedback"), and must carry
> a bound. Some inputs can be driven only by a person, and `canConnect` refuses any cable that
> lets an agent drive them.

### The one-page spec (test 3)

The whole kernel contract, in the spirit of Sonic's `types.ts` as "the whole contract":

```text
KERNEL A — PATCH BAY. Contract v1.

PATCH      {version, name, modules[{id, type@major, params, budget?, poly?}],
            cables[{from: id.jack, to: id.jack | id.param,
                    back?: {max, then} | {gated: human}}]}
           Plain YAML in the project's git. Edits are diffed; modules whose id+type
           survive keep their state and in-flight runs.

DESCRIPTOR type (namespaced, never renamed), major, name, blurb,
           jacks[{id, dir: in|out, kind, type?, many?, mode: value|service,
                  hot: bool (default true), drivenBy: any|human, relays?: <in-jack>}],
           params[{id, schema, default, cable: bool}],
           run{via: mcp|process, entry}, agent: bool, sink: bool,
           effects[{workspace|network:<host>|spend}], cost: words+usd est,
           latency: words, failure{retries, then: park|escalate}.

KINDS      doc · claim · decision · artifact · signal.
RECORD     {id=hash(body+links), kind, type, body, links{derivedFrom[], about[],
           answers?, supersedes?}, by{module, type@ver, run, actor, inputs[], cost}, at}
           Immutable. `by` is stamped by the kernel, never supplied by the module.
           claim needs >=1 derivedFrom link to a doc|artifact.
           decision.status=accepted needs a human-rooted signal in derivedFrom.
OUTLET     (module, out-jack) -> list of record ids, newest last. The cable reads it.

canConnect(out, in):
  same kind                                   ok (type must match if both narrow)
  any kind -> doc input                       ok (kernel renders deterministically)
  doc -> structured input                     refused: put an adapter module between
  any -> in.drivenBy=human                    ok only from the human module, or from an
                                              out declaring `relays` of a human-only in
                                              on a module with agent=false
  fan-in: claim/decision/artifact = union; signal = merge; doc = one cable
          unless the input is `many` (then a list). Docs never sum.

RUN        A run pins its input revisions, gets them materialised (files, or a
           scoped MCP proxy for service jacks), runs in its own sandbox with no route
           to other modules and a run token for the model gateway, and returns
           records per out-jack and a status: complete | input_required | done |
           failed. One run = one quantum. input_required is a signal to the inbox;
           done parks the module for good (until its patch entry is reset).
SCHEDULE   run(m) iff reaches(m, sink) and dirty(m) and budget(m) > estimate(m)
           and m is not done.
           dirty = some HOT input's outlet has a revision m's last run did not use.
           Cold inputs (Pd's cold inlet) are read at the next run, never start one.
           Order: from the sinks back, depth-first. A back cable reads the previous
           completed revision. Reachability follows back cables too.
LOOPS      Every cycle must hold a `back` cable, which reads the previous completed
           revision and is either counted {max: N, then} or gated: it carries only
           human-rooted records (accepted decisions, human signals), checked per
           record. After N passes a counted cable closes and feeds `then`. Any
           human-rooted input to a module on the cycle resets the count.
GRANT      No cable, no data. Service-jack calls go only to cabled providers and are
           recorded as run inputs. Patch edits that add a cable into an agent
           module need a human's approval.
BUDGET     estimate(patch) = sum over reachable modules of cost; a counted loop's
           modules x (max+1); poly modules x voices. Shown before the first run.
HUMAN      One built-in module per person: out {say.<name>: doc, approve/drop/accept:
           signal}, in {inbox: any, many}. Its signals are signed with a key no
           sandbox can read.
POLY       poly: {key: <in-jack>} = one voice per record on that jack, each with its
           own state and runs; outputs carry the key; fan-in to a mono input = union.
CONFORM    A module loads only if it passes the kind contract suite.
```

**Measured:** the fenced block is 556 words and 62 lines (`wc -w`, `wc -l`). It started at
446 words. Review then forced three additions, and each one was needed to make C2 and C3 behave:
- hot and cold inputs;
- a terminal `done` status;
- gated back cables.

`poly` added about 30 more words. At around 560 words it still fits one dense printed page,
next to Eurorack's voltage sheet and Sonic's commented `types.ts`. The growth is itself the
finding: **the patch bay's spec grows with every scheduling subtlety that knowledge work adds to
Sonic's.** Test 3 is a pass today and the margin is gone.

## 2. Kernel primitives (complete, minimal)

| # | Primitive | Why it must be in the kernel | Lineage |
|---|---|---|---|
| 1 | **Descriptor** | It is the contract every module is checked against. Without it there is no `canConnect`, budget or grant. | Sonic `Plugin` descriptor; swarm `agents/*.md` frontmatter (`01-inventory.md` §1, §5) |
| 2 | **Patch** `{modules, cables, params}` | It is the authority. It is plain data, diffed on edit, and stored as YAML in git. | Sonic `Patch`, VCV/Zoia, k8s manifests (`01-prior-art.md` §6, §10) |
| 3 | **Kind + `canConnect`** | Legality must be checked when the cable is drawn, not discovered when a model calls something. | Sonic `runtime.ts:501`; the missing check named in `01-ai-landscape.md` §3 gap 2 |
| 4 | **Record + outlet** | Something must be the "128-sample block": an immutable record, stamped by the kernel, with an outlet as a mutable ref to its latest revision. | git objects+refs, Datomic, `01-data-model.md` §3.1 |
| 5 | **Run** (the quantum) | It is bounded, pins its inputs, returns a checked outcome, and is persisted before anything is applied. | swarm round (`01-inventory.md` pattern 5), MCP tasks / `input_required` |
| 6 | **Scheduler rule** `reach ∧ dirty ∧ budget`, with back cables and loop bounds | When running costs tokens, "parked costs nothing" is only true if the kernel owns this rule. | Sonic parking; k8s level-triggering; LangGraph super-steps (`01-prior-art.md` §10, `01-ai-landscape.md` §1.5) |
| 7 | **Broker** (materialise inputs, proxy service calls, sandbox, model gateway) | A cable is only a grant if modules cannot reach each other any other way. | swarm nono profile + human token (`01-inventory.md` §1), Figma/VS Code isolation (`01-failure-modes.md` patterns 5–6) |
| 8 | **Human module** | It is the one source of authority, so it holds a signing key that sandboxes cannot read. It is a module so that a person is a visible node in the patch. | swarm "agents read, only a person writes" (Settled #1) |
| 9 | **Poly** (one voice per keyed input record) | *Contested.* Without it A cannot express "one swarm feature per idea" or "one research run per sub-question" (§7.1). | VCV polyphonic cables (`01-prior-art.md` §6) |

**Explicitly NOT in the kernel**

| Concern | Where it lives instead |
|---|---|
| Body schemas of `type`s (`swarm.handback`, `kb.note`) | The module that owns the type publishes them, and the kernel validates against them. Evolution follows atproto's additive rules (`01-data-model.md` §3.4). |
| LLM coercion (doc → claim, lenses V1 → V2) | **Adapter modules** that show up in the patch with their own cost. Never an implicit cast. |
| Search, retrieval, relevance | The KB module, offered as a `service` jack. The kernel has **no ambient query**, and this is the line between A and B. |
| Prompts, agent loops, subagents | Inside modules. The kernel never templates a prompt (test 13). |
| Git, worktrees, previews, merge | Swarm's own machinery (`src/loop/git.ts`, `preview.ts`). |
| Decision semantics (supersession, D-ids, projection to `decisions.md`) | The register module (`src/board/decisions.ts` lifted out). |
| UI, patch editor, inbox rendering, board views | Porcelain over the patch and outlets (`01-prior-art.md` principle 7). |
| Sync, sharing, multi-user | A later layer. Immutable records make it addable. |
| Durable-execution engine | An implementation detail under *run*, such as Restate/DBOS (`01-ai-landscape.md` §1.6). |

The model gateway (item 7) *is* in the kernel. That follows `01-ai-landscape.md` §5.5: Sampling is
deprecated. The gateway is also the only place that can enforce a per-run budget without trusting
the module, so a run's sandbox holds no provider key, only a run token.

## 3. Module contract

### Declaring a module

One file per module, `module.yaml`, beside its code. Swarm is the hardest case, and the
patch-bay answer is to cut it in two along its own trust line ("agents read, only a person
writes"; `01-inventory.md` §1). `swarm.rounds` runs agents. `swarm.merge` is swarm's core
doing the one human-authorised act. Both are adapters over the same swarm install.

```yaml
type: dk.svenven.swarm.rounds          # namespaced; never renamed once shipped
major: 1
name: Swarm rounds
blurb: Delivers one idea on a git branch in sandboxed agent rounds; a person judges each round.
agent: true                            # runs agents => may never feed a human-only jack
run: { via: process, entry: "swarm-module rounds" }
jacks:
  - { id: idea,      dir: in,  kind: doc }
  - { id: basis,     dir: in,  kind: decision, many: true, hot: false }  # cold: read at round start,
                                                                         # never starts a round
  - { id: reply,     dir: in,  kind: doc }                               # a person or another module
  - { id: drop,      dir: in,  kind: signal, type: drop, drivenBy: human }
  - { id: merged,    dir: in,  kind: signal, type: swarm.merged }        # ends the voice: status done
  - { id: summary,   dir: out, kind: doc,      type: swarm.handback }
  - { id: decisions, dir: out, kind: decision, many: true }        # status: proposed, always
  - { id: findings,  dir: out, kind: claim,    many: true }        # reviewer openFindings, risks
  - { id: snapshot,  dir: out, kind: artifact, type: git.commit }
  - { id: preview,   dir: out, kind: artifact, type: url }
  - { id: question,  dir: out, kind: signal,   type: needs-human }
params:
  - { id: workspace, schema: {repo: path, target: string}, cable: false }
  - { id: roundBudgetUsd, schema: number, default: 3, cable: false }   # money is never cable-driven
  - { id: stack, schema: string, cable: true }                          # e.g. from a KB doc
effects: [workspace, spend]
cost: "≈ $1–4 per round (roundBudgetUsd caps it); 3 subagents"
latency: "5–40 min per round; waits indefinitely for a person"
failure: { retries: 3, then: escalate }        # swarm's own resumes ≤3
---
type: dk.svenven.swarm.merge
major: 1
name: Swarm merge
blurb: Merges exactly the approved snapshot (--no-ff, no push); nothing else.
agent: false                           # swarm's core; no model, no sandboxed agent
sink: true                             # the merge is an effect outside the graph (Sonic's MIDI-out rule)
run: { via: process, entry: "swarm-module merge" }
jacks:
  - { id: candidate, dir: in,  kind: artifact, type: git.commit, hot: false }
  - { id: handback,  dir: in,  kind: doc, type: swarm.handback, hot: false }
  - { id: approve,   dir: in,  kind: signal, type: approve, drivenBy: human }
  - { id: merged,    dir: out, kind: signal, type: swarm.merged, relays: approve }
  - { id: refused,   dir: out, kind: signal, type: needs-human }        # approveRefused, conflicts
params:
  - { id: workspace, schema: {repo: path, target: string}, cable: false }
effects: [workspace]
cost: "$0"
latency: "seconds"
failure: { retries: 0, then: escalate }
```

`merged` with `relays: approve` is how a human-only effect passes through a module. `canConnect`
allows a relay into a human-only jack only from a module declared `agent: false`, and the
conformance suite checks that `merged` is emitted only in a run triggered by a human-signed
`approve` (§3, Conformance). `swarm.rounds` cannot relay anything, because it is `agent: true`.

### How a module runs

**Always out of process.** There are two transports, both behind the broker:

1. **`via: mcp`.** The module is an MCP server (spec 2026-07-28, stateless). Jack metadata
   travels in a vendor extension `dk.svenven/jacks` in `server/discover`. Hosts that ignore it
   still see an ordinary MCP server (`01-ai-landscape.md` §5.2). A run is one `tools/call` on
   `run` with input *record ids*. Long work returns a task handle (tasks extension), and a
   pause for a person returns `input_required`. This suits long-lived modules with private
   indexes (KB, research).
2. **`via: process`.** This is the Unix form. The broker writes inputs to `in/<jack>/<hash>.{md,json}`,
   starts `entry` in a fresh nono sandbox with read access to `in/` and write access to `out/`,
   and reads `out/<jack>/*` back as records. Exit 0 means complete. Exit code 3 plus
   `out/question` means `input_required`. Anything else counts as failed. This suits CLIs and
   per-run tools.

In-process modules exist only as kernel built-ins (`human`, `probe`). The reason is the isolation
test: a module that hangs must stall only its own card (`01-failure-modes.md` pattern 5,
VS Code's extension host).

**The broker is what makes "cable = grant" true.** A run's sandbox has three things:
- no network except the model gateway, plus hosts named in `effects`;
- no paths except `in/`, `out/` and declared workspaces;
- no addresses of other modules.

A `service` jack (for example the KB's `ask`) appears inside the run as a single MCP server: a
proxy the broker mounts. It forwards only to the cabled provider and journals every call and
result into the run's `by.inputs`. So an agent *can* look things up mid-run, but only along a
cable, and only on the record. Without the proxy, swarm's agent could open the KB's socket and
test 9 would fail.

### Turning existing tools into modules

**Swarm, via `swarm-module`** (about 300 lines, a sketch). Each kernel *run* of
`swarm.rounds` is one swarm *round*, so the quanta line up exactly.
- First run on a new `idea` revision: `swarm add "<idea>" --basis-file in/basis/`, then follow
  SSE until the feature is `waiting`.
- Split the hand-back across jacks:
  - `built`/`tryIt`/`checks` → `summary`;
  - `decisions[]` → `decisions` with status `proposed`;
  - `openFindings`/`risks` → `findings`;
  - `snapshotSha` → `snapshot`;
  - preview URL → `preview`;
  - a `question` hand-back → `question`.
- Later runs fire only on hot inputs:
  - `reply` → `swarm reply`;
  - `drop` → `swarm drop`, status `done`;
  - `merged` → status `done`, and the module parks for good.

  A new `basis` revision never starts a paid round.
- `swarm.merge` runs on a human `approve`: `swarm approve <id>` (the snapshot it merges is the
  one on `candidate`). On `done·merged` it emits `merged` with `answers: <handback hash>`. On
  `approveRefused` it emits `refused` to the inbox.

**What swarm itself must change.** No adapter alone can do this (`simple-model.md`, "Not built
yet"):
1. Accept a basis from outside. Today `basis` is always `[]` and the register is unplugged.
2. Write proposed decisions in the register's record shape instead of the flat
   `decisions.jsonl`. Two formats exist today (`01-inventory.md` §1).
3. Accept a *signed approve record* in place of the bearer human token. Otherwise the adapter
   must hold the token, and the trust rule moves from swarm into the adapter.
4. Stop writing into target repos (`AGENTS.md`, `.swarm/` in sonic; `01-inventory.md`
   implication 7). The workspace becomes a param of the module.

**Any CLI, via the built-in `exec` adapter type.** The params are `argv` (a template over input
paths), `stdin` (one doc jack) and `stdout` (a doc jack). This is `cat brief | pandoc` as a
module. It is `agent: false`, has no spend and costs about $0. Printer's CLI (`--json`, exit
codes 0/1/2) wraps the same way, with `check` → `claim` and `apply_ops` behind a human-only
jack if desired (`01-inventory.md` §3).

### Conformance (test 7)

A module loads only if it passes the kind suite. The checks:
- the descriptor parses, ids are unique and defaults are in range;
- every out record validates against its kind and type;
- a run with the same pinned inputs produces no duplicate records (swarm D-011);
- malformed, oversized (> limit) and timed-out runs are refused and land on the module's own card;
- `relays` jacks emit only in runs whose trigger was the relayed human signal.

This is `registry.test.ts`, translated (`patch-bay.md`, "Adding a plugin").

## 4. What flows on cables, and where state lives

### Position on the six candidate kinds (`01-data-model.md`, "Candidate jack kinds")

| Candidate | Verdict | One reason, tested on C1–C3 |
|---|---|---|
| `doc` | **Keep.** The "audio". | Every module reads it, and any record renders to it deterministically. It is the only kind every composition uses. |
| `claim` | **Keep.** Its only required structure is ≥1 `derivedFrom` link to a doc or artifact. | C1 is impossible to *check* without it: "every claim traces" becomes a deterministic graph walk instead of an LLM opinion. The body stays free text, which answers the RDF fear (`01-data-model.md` §2.4). C3 critiques are claims *about* a draft (`about: [draft]`). |
| `decision` | **Keep. Strict**, like `note`. | C2 is exactly this kind. `accepted` is a kernel-checked invariant: it needs a human-rooted signal in `derivedFrom`. |
| `task` | **Drop.** | In a patch-first kernel, *the module instance is the task*: requested work = a doc on its input + params + budget. "Admitted" = cabled and reached. A `task` record would be a second, invisible topology, which is B's model, not A's. The cost is that dynamic work needs `poly` (§7.1). |
| `artifact` | **Keep.** | Commit shas, preview URLs and fetched-source snapshots (C1's provenance roots) are bytes or refs by hash, and are never coerced. |
| `signal` | **Keep, narrowed.** | Only *discrete happenings that carry authority or need a person*: `approve`, `drop`, `accept`, `needs-human`, `budget-exhausted`, `swarm.merged`. "A new revision exists" is **not** a signal in A, because the scheduler sees outlet revisions directly. So `signal` is not "the event log". |

**Fan-in per kind:**
- `claim`, `decision` and `artifact` form a union (a set, ordered by `at`, deduplicated by hash).
- `signal` streams merge.
- **`doc` never sums.** An input takes one cable, unless it is declared `many`, in which case it
  gets an ordered list. Combining drafts is a `mixer` module with a visible cost
  (`01-ai-landscape.md` §4: "documents do not sum — they need a mixer module").

**Coercion is asymmetric** (`01-data-model.md` §3.2):
- structure → doc is free, done by the kernel's renderer;
- doc → claim or decision only through an adapter module, which can only ever emit `proposed`
  decisions.

### Where state lives

Per project, on disk, in open formats:

```text
<project>/patches/<name>.patch.yaml     # the authority. In git, human-diffable.
<project>/.compose/records/<hash>.json  # immutable records (envelope + body)
<project>/.compose/outlets/<module>/<jack>   # one line per revision: record hash (a ref log)
<project>/.compose/runs/<run-id>.json   # pinned inputs, outputs, status, cost, sandbox profile
<project>/.compose/text/…               # Markdown projection of docs/claims/decisions for grep/editors
<module's own dir>                      # module-private state: swarm's .swarm/simple, KB's index
```

The patch is git-tracked. The store is git-friendly (immutable files) but large, so whether it is
tracked is a project choice. **Module-private state is invisible to the kernel by design**: a
swarm feature's worktree and the KB's embeddings are the module's business. Only what crosses an
outlet is shared, probed and provenanced. That keeps the kernel small. It is also a hole in the
probe and outlives tests (§7.7).

## 5. Three worked compositions

Conventions: `human:owner` is the built-in human module. `back:` marks a cable that closes a loop.
Costs are author estimates in the style of Sonic's descriptors, not measurements.

### C1 — research → knowledge base → writing; every claim traces to a source

```yaml
version: 1
name: sourced-article
modules:
  - { id: owner,    type: human@1 }
  - { id: research, type: dk.svenven.research.web@1,
      params: { depth: 2, maxSources: 25 }, budget: { usd: 4 } }
  - { id: kb,       type: dk.svenven.kb.notes@1, params: { scope: "article/agent-kernels" } }
  - { id: writer,   type: dk.svenven.write.draft@1, params: { words: 1500 }, budget: { usd: 2 } }
  - { id: trace,    type: dk.svenven.verify.trace@1 }      # deterministic, agent: false, $0
  - { id: citejudge,type: dk.svenven.verify.citejudge@1, budget: { usd: 0.5 } }  # LLM, partial
  - { id: publish,  type: dk.svenven.export.markdown@1, params: { path: "out/article.md" } }  # sink
cables:
  - { from: owner.say,          to: research.brief }        # doc
  - { from: owner.say,          to: writer.brief }          # same brief, fan-out
  - { from: research.sources,   to: kb.sources }            # artifact (page snapshots by hash)
  - { from: research.claims,    to: kb.claims }             # claim, each derivedFrom a source
  - { from: kb.style,           to: writer.style }          # doc: house style held in the KB
  - { from: kb.claims,          to: writer.claims }         # claim (many): curated, deduped, in scope
  - { from: kb.ask,             to: writer.lookup }         # service jack: mid-run lookups, journaled
  - { from: writer.draft,       to: trace.draft }
  - { from: kb.claims,          to: trace.claims }
  - { from: writer.draft,       to: citejudge.draft }
  - { from: trace.report,       to: owner.inbox }           # claim(s): "ref c:9f… resolves; source s:41…"
  - { from: citejudge.report,   to: owner.inbox }           # claim(s): "sentence 14 asserts a fact, uncited"
  - { from: writer.draft,       to: owner.inbox }
  - { from: writer.draft,       to: publish.doc }           # cold: a new draft never publishes itself
  - { from: trace.pass,         to: publish.gate }          # cold signal: all refs resolve
  - { from: owner.approve,      to: publish.approve }       # human-only, hot: the only trigger
```

**Execution.**
1. *Sinks:* `owner.inbox` and `publish`. Walking back reaches every module, so nothing is
   parked. *Preflight:* the estimate is $4 + 0 + $2 + 0 + $0.5 = **$6.50**, shown before the
   first run (test 16).
2. The owner writes a brief, `owner.say` r1. `research` and `writer` both become dirty.
   - Depth-first from the sinks puts `research` → `kb` before `writer`.
   - The writer's `claims` input is cabled from `kb`, which has not run on this brief.
     Upstream-first ordering avoids a wasted writer run.
3. `research` runs in its sandbox with network access granted to the web (`effects: [network:*]`).
   - It emits `sources` (artifacts: the fetched page bytes, hashed) and `claims`.
   - The kernel **refuses** any claim record with no `derivedFrom` link to a doc or artifact.
     This is an envelope rule, not research's good manners.
4. `kb` runs.
   - It merges the claims (union), deduplicates by hash, and links near-duplicates with
     `supersedes` and `about`.
   - It emits the in-scope set on `kb.claims`.
5. `writer` runs. It sees the brief, the style doc and the claim set as files.
   - It may call `lookup` (the proxied `kb.ask`). Each call is journaled into the run's inputs.
   - It writes Markdown with inline refs `[^c:9f3a…]` to claim hashes.
6. `trace` (deterministic, $0) checks three things:
   - every `c:` ref resolves to a claim in its *cabled* input set;
   - every such claim has a `derivedFrom` chain ending in an artifact;
   - the artifact still exists.

   It emits `pass` only if all three hold. `citejudge` (LLM) flags factual sentences that carry
   no ref.
7. The owner sees the draft and both reports in the inbox. On `approve`, with `trace.pass`
   present, `publish` writes `out/article.md` plus a sources appendix rendered from the chain.

**Re-runs.** If the owner edits the brief (r2), everything downstream becomes dirty. If the owner
only replies to the writer, `research` and `kb` stay clean and do **not** re-run. That is
level-triggering paying for itself.

**Honest limit.** "Every claim traces" is **guaranteed only for sentences that carry a ref.** A
deterministic checker can prove the *refs* are sound. Whether an uncited sentence asserts a fact
is a judgement, so `citejudge` is a partial check with an LLM's error rate. A does not make
hallucination impossible. It makes the *cited* part machine-checkable and the uncited part
visible.

### C2 — swarm reads the decision register; accepted decisions flow back through a human gate

```yaml
version: 1
name: delivery-with-register
modules:
  - { id: owner,    type: human@1 }
  - { id: register, type: dk.svenven.kb.decisions@1,       # src/board/decisions.ts, lifted out
      params: { project: swarm, projectTo: "docs/product/decisions.md" } }   # projection = sink
  - { id: rounds,   type: dk.svenven.swarm.rounds@1,
      params: { workspace: { repo: ~/www/swarm, target: main }, roundBudgetUsd: 3 },
      budget: { usd: 25 } }
  - { id: merge,    type: dk.svenven.swarm.merge@1,
      params: { workspace: { repo: ~/www/swarm, target: main } } }
cables:
  - { from: owner.say.idea,      to: rounds.idea }
  - { from: owner.say.reply,     to: rounds.reply }
  - { from: owner.drop,          to: rounds.drop }            # human-only
  - { from: register.accepted,   to: rounds.basis,            # cold; pinned at round start
      back: { gated: human } }                                # carries only human-rooted records
  - { from: rounds.summary,      to: owner.inbox }
  - { from: rounds.preview,      to: owner.inbox }
  - { from: rounds.findings,     to: owner.inbox }
  - { from: rounds.question,     to: owner.inbox }            # signal needs-human
  - { from: rounds.snapshot,     to: merge.candidate }        # cold
  - { from: rounds.summary,      to: merge.handback }         # cold
  - { from: owner.approve,       to: merge.approve }          # human-only; hot: the only trigger
  - { from: merge.refused,       to: owner.inbox }
  - { from: merge.merged,        to: rounds.merged,           # ends the feature (status done)
      back: { gated: human } }
  - { from: rounds.decisions,    to: register.proposed }      # decision(proposed), always
  - { from: merge.merged,        to: register.accept }        # human-only jack, fed by a relay
```

**Why it is legal.**
- `merge.merged → register.accept` feeds a human-only jack from `merge`, which is
  `agent: false` and declares `merged` as `relays: approve`. `canConnect` accepts it. A cable
  from any `rounds` output into `register.accept` would be refused, because `rounds` is
  `agent: true`.
- There are two cycles. Both close on a `back` cable marked `gated: human`:
  - `register → rounds → register`, through `basis`;
  - `rounds → merge → rounds`, through `merged`.
- The kernel checks every record on a gated cable. Records on `register.accepted` are accepted
  decisions, which the RECORD invariant makes human-rooted. Records on `merge.merged` are relays
  of a signed `approve`. So agents cannot turn either loop: proposed decisions pile up in the
  register but never reach `accepted`, and `rounds.basis` never changes without a person.

**One approve, or two?** In swarm today one `approve` both merges and accepts the hand-back's
`new` decisions (D-015 superseded, `simple-model.md`). A keeps the coupling but splits the
mechanism:
- `owner.approve` drives only `merge.approve`.
- Only when the merge **succeeds** does `merge` emit `merged`, carrying `answers: <handback hash>`.
- The register accepts exactly the proposed decisions whose `derivedFrom` is that hand-back.

A merge refused for a conflict (`approveRefused`) emits `refused` and accepts nothing. Under a
naive "fan the approve out to both" cable, the register would accept the decisions of a feature
that never merged. Decisions raised outside any feature, for example in KB curation, can be
accepted with a direct `owner.accept → register.accept` cable.

**Execution.**
1. *Sinks:* the inbox, `merge` (`sink: true`) and the register's projection. All four modules
   are reached.
2. The owner writes an idea. `rounds.idea` is hot, so `rounds` is dirty.
   - The broker materialises `in/basis/` from the register outlet's *current* revision, say 29
     accepted decisions.
   - Pinning them is the "basis@revisions" swarm already models (`Round.basis`).
3. Round 1 runs. Its outputs land: summary, preview, findings, a snapshot and 2 proposed
   decisions.
   - `register` is dirty on `proposed` and runs. It records the two as `proposed` (D-034, D-035;
     D-033 is the latest in force) and emits nothing on `accepted`.
   - `merge` is **not** dirty. `candidate` and `handback` are cold, so a fresh snapshot alone
     never merges.
   - `rounds` is not re-triggered. None of its hot inputs changed.
4. The owner replies. `rounds.reply` is hot → round 2, with the **same** pinned basis → a new
   hand-back. The proposals are re-emitted with `supersedes: <round-1 proposal>`.
5. The owner approves with a signed `approve`. `merge` runs, reading the latest cold
   `candidate` (round 2's snapshot), and calls swarm's approve. The merge succeeds.
   - `merged` is emitted (it relays approve, answers hand-back r2).
   - `register.accept` fires and the round-2 decisions become `accepted`. The projection
     rewrites the generated region of `docs/product/decisions.md`.
   - `rounds.merged` fires. `rounds` returns status `done` and parks for good.
6. `register.accepted` has a new revision. `basis` is cold, so a finished or waiting feature
   does not start a paid round. Under `poly`, every *other* live feature voice picks up the new
   basis **at its next round start**, which is the one-quantum rule: a running round never sees
   a mid-round change.

**The catch, said plainly.** The whole guarantee rests on `merge` really being agent-free and
really emitting `merged` only after a human-signed approve. The kernel enforces the static half
(`agent: false`, `relays` declared, and the signed trigger is present in the run's inputs). The
conformance suite tests the behavioural half. Neither can prove that swarm's merge binary does
nothing else. It is the same trust swarm places in its own core today, moved to a smaller,
visible module. The user also sees four nodes where they used to see one board.

**Many features.** This patch is one feature. A board of features puts `poly: {key: idea}` on
`rounds` and `merge`: one voice per idea record, each with its own state, all sharing `basis`.
`dependsOn` between voices stays inside swarm. See §7.1 for why that is a crack in A.

### C3 — a draft cycles through a critic at most N rounds, then waits for the human

```yaml
version: 1
name: critic-loop
modules:
  - { id: owner,  type: human@1 }
  - { id: writer, type: dk.svenven.write.draft@1, budget: { usd: 3 } }
  - { id: critic, type: dk.svenven.critic.prose@1,
      params: { rubric: "argument, evidence, plain words" }, budget: { usd: 1.5 } }
cables:
  - { from: owner.say,       to: writer.brief }
  - { from: writer.draft,    to: critic.draft }
  - { from: critic.notes,    to: writer.feedback,                # claim(many), about: [draft rev]
      back: { max: 3, then: owner.inbox } }                      # the bound
  - { from: owner.say,       to: writer.reply }                  # doc: the human's own feedback
  - { from: writer.draft,    to: owner.inbox }
  - { from: critic.notes,    to: owner.inbox }
```

**Execution.**
1. *Sink:* `owner.inbox`. `critic` is reachable through the back cable into `writer`, which
   reaches the inbox, so it is not parked. *Preflight:* the loop body (writer $3 + critic $1.5)
   runs at most `max + 1` = 4 times, so **$18 worst case** before the human (test 16).
2. Brief r1 → `writer` → draft **d1**. `critic` is dirty → notes **n1** (`about: d1`).
3. The `back` cable delivers **n1** to `writer.feedback` as the previous completed revision →
   **d2** (pass 1) → `critic` → **n2** → **d3** (pass 2) → **n3** → **d4** (pass 3).
4. The pass counter hits `max: 3`. The back cable **closes**. The kernel stops delivering
   `critic.notes` on it and emits `signal: loop-bound-reached{cable, passes: 3}` to
   `owner.inbox` (`then`). The critic still produces **n4** for d4, because `critic` is dirty and
   reached via the inbox, so the owner sees the last critique as well. The writer does not
   react to n4.
5. *Early exit for free:* if the critic returns **no** notes, its outlet gets no new revision, so
   `writer` is not dirty and the loop quiesces before `max`. Convergence falls out of
   level-triggering and needs no special signal (`01-prior-art.md` §10).
6. The owner replies through `owner.say → writer.reply`. That is a human-rooted input to a
   module on the cycle, so it **resets the counter** (LOOPS rule). The writer runs on the reply
   (`reply` is hot), and up to three more critic passes follow.

**A design choice C3 exposes.** The owner's feedback is prose (`doc`) and the critic's is
`claim`, so they cannot share one input: `canConnect` refuses doc → claim without an adapter.
The writer therefore declares two jacks, `feedback: claim, many` and `reply: doc`. That is the
right answer, because a person's reply and a critic's findings are different things with
different authority. It is also the kind of friction a module author will meet on every jack.

## 7. Weaknesses, and what this design makes hard

1. **Dynamic topology is the crack.** Swarm creates features at runtime with `dependsOn`
   between them, research fans out into sub-questions, and a KB grows a note per source.
   - A static graph does not say "one per idea". `poly` (one voice per keyed record) patches
     this, but the *real* graph is then partly hidden in voice keys, and `dependsOn` between
     voices lives inside swarm, outside the patch.
   - The more a composition is *generated* rather than *wired*, the less the graph is primary.
     B handles this natively, since every new record is just an event.
2. **The graph-editor evidence is against a user-facing canvas.** Pipes and Popfly died, and
   Agent Builder is being retired (`01-ai-landscape.md` §1.4). A can survive this only by
   separating *the graph as authority* from *the graph as UI*: the user mostly picks presets and
   approves agent-proposed patch diffs, and rarely draws cables. If nobody ever looks at the
   graph, though, much of A's advantage over B (a visible grant, visible cost) is theoretical.
3. **Ad-hoc use is heavy.** "Ask the KB one question" or "run the critic on this paragraph once"
   needs a patch. The answer is ephemeral patches (a shell-like `compose run 'kb.ask <
   question.md'` that builds a two-node patch, runs it and discards it). That is a second mode
   to design, and Unix's actual strength.
4. **Pinned inputs fight how agents work.** Agents want to look things up mid-run. Service jacks
   (proxied, journaled) fix this, but they break the clean "a run is a function of its pinned
   inputs" story. A re-run of the same inputs may make different service calls, so replay is an
   audit, not a recomputation.
5. **Authority relays are the most delicate rule** (C2). A pays for a checkable rule by
   splitting modules along their trust line: swarm becomes `rounds` plus `merge`, and every
   future tool with a human-authorised act needs the same cut. Even then, the trust boundary of
   the whole platform runs through `agent: false` and `relays`, fields a module author fills
   in, backed only by a conformance test.
6. **Hot and cold inputs are a necessary, unloved concept.** Without cold inputs, every new
   accepted decision would start a paid round in every waiting feature, and a fresh snapshot
   would trigger a merge. With them, a module author must decide which inputs start work, and
   Pd shows that hot/cold is where patch semantics become folklore (`01-prior-art.md` §7).
7. **Module-private state escapes the graph.** Swarm's worktrees, the KB's index and a research
   tool's crawl cache are invisible to probes, to grants (a module's state can carry data from
   one patch to another) and to the outlives test. A only governs what crosses outlets. C
   (namespace) would make the KB's tree itself the visible thing.
8. **Level-triggering spends money on trivial edits.** A typo fix in the brief dirties C1's whole
   chain (≈ $6.50). The scheduler needs a `hold` param per cable or module (a human-set hold,
   never cable-driven), or a "material change" check, which is an LLM judgement again. Parking
   stops *unreached* work, not *unwanted* work.
9. **Concurrent human and agent edits of one doc** have no kernel answer. An editor is a module
   that emits doc revisions. If the writer emits d3 while the owner edits d2, the kernel has two
   revisions and no merge, because docs never sum. Patchwork-style CRDT docs (`01-data-model.md`
   §2.1) could live inside a `doc` type, but the kernel does not provide them.
10. **The topology is a social contract with agents.** An agent that proposes a patch edit adding
   `kb.ask → research` is asking for a capability. Every patch diff that widens an agent
   module's inputs must go through a human, which makes patch editing itself a gated flow. It is
   correct, and it means more approvals.
11. **No streaming across cables.** The quantum is a completed run, so a writer cannot start on
    a partial research result. That is fine for these modules. It rules out a live
    "co-writing" feel without a second, streaming kind.

**What A makes easy:** seeing why something ran and what it cost; refusing a dangerous wiring
before it runs; bounding every loop; zero spend for anything nobody reads; and proving the
*cited* part of an article is sourced.

**What A makes hard:** anything whose shape is not known in advance (many features, recursive
research); quick one-off use; a module that wants to browse everything; and any authority that
must pass *through* a module that also runs agents.

**Shared with B:** the record envelope, kernel-stamped provenance and content addressing.
**Different from B:** in A, topology decides grant, schedule and cost; in B, subscriptions are
implicit and reactors decide. **Different from C:** C binds trees into views. A cables typed
records, and every flow is an edge a person can point at.
