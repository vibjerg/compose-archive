# 01 — Prior art: what makes composition systems compose

Track: the uniform interface behind composable systems. Lens: Sonic's patch bay
(`~/www/sonic/docs/product/patch-bay.md`). It has jack kinds with a `canConnect` rule, a patch
that is plain data, parked modules that cost nothing, and feedback that is legal at the cost of
one quantum of delay.

The question for each system is the same. **What is the primitive? What contract does every
part honour, so that parts which have never met still fit? How are configuration and composition
written down? Where does it break?**

---

## At a glance

| System | Primitive | Uniform contract | Composition is expressed as | Main limit |
|---|---|---|---|---|
| Unix pipes | process | stdin/stdout/stderr byte streams + exit code | shell text (`a \| b \| c`) | untyped: every boundary pays a parsing tax; linear only |
| Plan 9 | file server | 9P (about a dozen messages: walk/open/read/write/clunk/stat…) | per-process namespace built by `bind`/`mount` | a file's *content* is still untyped; semantics hide in conventions per server |
| PowerShell / nushell | cmdlet / command | typed objects/tables flow through the pipe | pipeline text | types are host-runtime-bound (.NET); crossing to the outside world falls back to text |
| Erlang/OTP | process (actor) | async messages + links/monitors; OTP behaviours | supervision tree (child specs as data) | messages are untyped at the protocol level; topology is code, not a visible graph |
| Smalltalk / Emacs | object / buffer + function | message send / buffers, hooks, advice | live image / init file | everything can touch everything; no isolation, no declared interfaces |
| Eurorack / VCV / Zoia | module | voltage on a 3.5 mm cable (±5 V audio, 1 V/oct, 10 V gates) / 0..1 in Zoia | physical or virtual cables; the patch *is* the program | untyped by design: a nonsensical patch is legal; hard to save/version in hardware |
| Pure Data / Max | object box | inlets/outlets; messages + signal (`~`) connections | the visual patch file | message order depends on hot/cold inlets and right-to-left firing |
| Node-RED / n8n | node | `msg` object (`payload`, `topic`) / array of `{json, binary}` items | flow JSON | message shape is convention, not contract; nodes silently disagree |
| Spreadsheets | cell | value or formula over references | the grid itself; dependency graph is implicit | no modules, hidden logic, references by position; cycles are an error |
| Git | object (blob/tree/commit) + ref | content-addressed objects; plumbing commands with stable output | scripts over plumbing; porcelain on top | the stable contract is low level; porcelain is not meant to be scripted |
| Kubernetes | resource (spec/status) | declarative API object + controller reconcile loop | YAML manifests; controllers watch kinds | eventual consistency; controllers can fight; debugging *why* is hard |
| Datomic / event sourcing | fact / event | append-only, immutable, time-stamped | queries and projections over the log | schema evolution and projection rebuilds; the log is not a UI |

## 1. Unix pipes and "everything is a file"

**Primitive.** A process with three file descriptors and an exit status.

**Uniform contract.** A byte stream in and a byte stream out. McIlroy's rule (1978): *"Expect
the output of every program to become the input to another, as yet unknown, program."*
([Wikipedia: Unix philosophy](https://en.wikipedia.org/wiki/Unix_philosophy)). "Everything is a
file" extends the same `open/read/write/close` vocabulary to devices, terminals and pipes. A
program written for files therefore works on all of them without knowing which it has.

**Configuration and composition.** Configuration is argv, env and dotfiles. Composition is shell
text, linear and ephemeral. A pipeline lives only as long as its command line, unless someone
saves it as a script.

**Main limit.** The stream is untyped. Every boundary is a parsing contract that no one wrote
down: column 3 of `ls -l` output, tab or space separators, locale-dependent dates. Composition
is easy to start and brittle to keep. Pipes are also linear (fan-out needs `tee`, fan-in
needs named pipes), one-shot (no long-lived graph) and one-way (no feedback without
`mkfifo` contortions).

**Lesson.** One uniform interface beats many good ones. But a byte stream makes *every* pair of
modules connectable, so `canConnect` is always true and the type check moves into each
program's parser, where it fails late and silently.

## 2. Plan 9: everything is a file server

**Primitive.** A file server: any process that speaks 9P.

**Uniform contract.** 9P2000, a small request/response protocol: `version, auth, attach, walk,
open, create, read, write, clunk, remove, stat, wstat, flush`
([Linux 9p.h listing of 9P2000 message types](https://lkml.indiana.edu/0506.0/1569.html)). The
window system, the network stack, `/proc` and remote machines are all file servers. Because the
protocol works over any byte channel, local and remote resources look the same.

**Configuration and composition.** *Per-process namespaces.* Each process assembles its own tree
with `bind` and `mount`. Composition is therefore not wiring components to each other. It is
deciding what each process sees at which name. *"The foundations of Plan 9 are built on two
ideas: a per-process name space and a simple message-oriented file system protocol"*
([Pike et al., The Use of Name Spaces in Plan 9](https://src.rcs.uwaterloo.ca/source/xref/plan9/sys/doc/names.ms)).
Union directories let several servers stack at one name. `rio` runs a program inside a window by
binding a fresh `/dev/cons` into its namespace, and the program never knows.

**Main limit.** 9P makes *access* uniform, not *meaning*. A ctl file takes text commands
whose grammar belongs to each server. The structure lives in the tree layout, the content is
still bytes, and conventions do the rest. Plan 9 also never reached mass adoption.

**Lesson.** Composition by *naming* rather than by *wiring* is a strong alternative to cables.
A module declares what it serves and what it expects to find at a path. The patch then becomes
a namespace: "the research tool's `/sources` is the knowledge base's `/notes/project-x`".
Per-process (per-module) namespaces also give isolation and capability scoping for free, since
a module can touch only what was bound into its view.

## 3. PowerShell and nushell: typed pipelines

**Primitive.** A command (a PowerShell cmdlet or a nushell command) that consumes and produces
structured values.

**Uniform contract.** The pipe carries objects (.NET objects in PowerShell) or values (tables,
records and lists in nushell). Snover's 2002 Monad Manifesto set the thesis: keep Unix
composition, drop the text parsing ([Monad Manifesto summary](https://www.techtarget.com/it-infrastructure/definition/Monad-Manifesto);
[annotated edition](https://leanpub.com/themonadmanifestoannotated)). Nushell restates it as
"everything is data" ([Nushell design philosophy](https://www.nushell.sh/contributor-book/philosophy_0_80.html)).
Generic verbs (`where`, `sort-by`, `select`, `Format-Table`) work on *any* command's output,
because they operate on fields and not on bytes.

**Configuration and composition.** Still pipeline text, but parameters are typed and
discoverable (`Get-Command`, `help`), and pipeline binding can map fields onto parameters by
name (`ValueFromPipelineByPropertyName`).

**Main limit.** Types stop at the runtime's edge. External programs and the network still speak
text or JSON, so a boundary that converts is needed (`from json`, `ConvertFrom-Csv`). Rich
objects with methods (PowerShell) are hard to serialise and replay. Nushell's plain-data values
travel better than PowerShell's live objects.

**Lesson.** Typing the cable makes *generic modules* possible: filter, sort and render work for
every producer. Typing is a spectrum, not a switch. Unix and Eurorack sit at the untyped end,
PowerShell at the fully typed end. **Sonic sits deliberately in between**: audio and control
interchange freely ("half the fun of a modular"), and `note` is the one hard boundary. That
middle position is a design choice the kernel will face directly. Type the few distinctions
that would produce nonsense, and leave the rest permissive.

## 4. Erlang/OTP: processes and supervision

**Primitive.** A lightweight isolated process with a mailbox. It shares no memory with other
processes.

**Uniform contract.** Asynchronous message send, plus links and monitors that turn another
process's death into a message. OTP *behaviours* (`gen_server`, `gen_statem`, `supervisor`) are
the standard shapes a process takes: a fixed set of callbacks (`init`, `handle_call`,
`handle_cast`, `terminate`) that the framework drives.

**Configuration and composition.** The supervision tree. A supervisor's child specs and restart
strategy are *data*: `one_for_one` restarts only the failed child, `one_for_all` restarts every
child, and `rest_for_one` restarts the failed child and those started after it. Restart
intensity is bounded: if more than MaxR restarts happen within MaxT seconds, the supervisor
gives up and fails upward
([erlang.org supervisor(3)](https://www.erlang.org/docs/19/man/supervisor.html)). "Let it crash"
works because recovery is someone else's declared job
([Armstrong's thesis](https://erlang.org/download/armstrong_thesis_2003.pdf)).

**Main limit.** Message contents are untyped at the protocol level. The dataflow topology who
sends to whom lives in code (pids and registered names), not in a visible, editable graph. You
can see the supervision tree, but not the dataflow.

**Lesson.** A composition system whose modules **fail mid-run** needs failure in the contract,
not bolted on. Agent modules (swarm, research) *will* fail: timeouts, bad output, exhausted
budgets. OTP shows that the composition layer should declare *what happens when a module dies*
(restart it, restart its dependents, or escalate), with a bounded retry budget, so that one
module's crash loop cannot run unbounded. This is a second graph next to the dataflow graph: the
**supervision graph**.

## 5. Smalltalk and Emacs: live, malleable environments

**Primitive.** Smalltalk: an object that receives messages, living in a persistent *image*.
Emacs: a buffer (text with properties) plus Lisp functions and variables.

**Uniform contract.** In Smalltalk, everything is a message send, including the IDE, the
compiler and the UI ([Ingalls, Design Principles Behind Smalltalk](https://www.cs.virginia.edu/~evans/cs655/readings/smalltalk.html)).
In Emacs the buffer is the universal data structure: mail, shells, directories, git status and
compilation output are all buffers, so every editing command works on all of them. Hooks are the
universal extension point: *"A hook is a variable where you can store a function or functions to
be called on a particular occasion by an existing program"*
([GNU Emacs Lisp manual: Hooks](https://www.gnu.org/s/emacs/manual/html_node/elisp/Hooks.html)).
Advice can wrap any function.

**Configuration and composition.** Configuration *is* code: `init.el` and the image. You compose
by redefining things live. Nothing restarts, and state survives an edit.

**Main limit.** Total malleability means no isolation. Any package can break any other, interfaces
are implicit, and load order matters. "It works in my image" is the Smalltalk version of "it
works on my machine". Composition happens by mutation, so no artefact says what was composed.

**Lesson.** Two things are worth taking. (a) **A universal substrate type makes all tools apply
to all content**: the buffer for Emacs, the document or artefact for us. (b) **Live edits keep
state.** Sonic's diff-on-load ("keeps every module whose id and type survive") is the same
idea, and it depends on **stable identity across edits**. The thing to avoid is composition by
side effect. Hooks should be declared edges in the patch, not ambient mutation.

## 6. Modular synths: Eurorack, VCV Rack, Empress Zoia

**Primitive.** A module: a box with jacks and knobs.

**Uniform contract.** *Voltage.* In Eurorack (Doepfer A-100 lineage) every jack carries a
voltage on a 3.5 mm cable. The conventions are 1 V/octave pitch, positive gates and triggers,
and ±12 V rails ([Doepfer A-100](https://en.wikipedia.org/wiki/Doepfer_A-100);
[Doepfer technical details](https://doepfer.de/a100_man/a100t_e.htm)). VCV Rack writes the
standard down: audio ±5 V, unipolar CV 0..10 V, bipolar ±5 V, gates 10 V, triggers 10 V for
1 ms, and polyphonic cables of up to 16 channels
([VCV Voltage Standards](https://vcvrack.com/manual/VoltageStandards);
[VCV Polyphony](https://vcvrack.com/manual/Polyphony)). Zoia normalises CV to 0..1 inside the
box, and its Euroburo maps external −5..5 / 0..5 / 0..10 V onto that range
([ZEBU manual](https://empresseffects.com/cdn/shop/files/ZEBU_Manual_2_dot_30.pdf)).

**Configuration and composition.** The patch *is* the program. In hardware it is cables and
knob positions, which are hard to save. VCV and Zoia make the patch a saved file of modules,
params and cables, which is the Sonic model. **Feedback:** *"Each cable in Rack induces a
1-sample delay of its carried signal from the output port to the input port"*
([VCV Voltage Standards](https://vcvrack.com/manual/VoltageStandards)). Any loop is therefore
well-defined. Sonic makes the same choice per loop (one 128-sample quantum) rather than per
cable.

**Main limit.** Untyped on purpose. A pitch CV into an audio input is legal and might even sound
interesting. The cost is that the system cannot tell a meaningful patch from a nonsensical one.
Ranges are conventions, not checks, and modules disagree about them.

**Lesson.** (a) A **single physical quantity with documented ranges** is enough to build an
ecosystem of thousands of modules from hundreds of independent makers. The contract is tiny and
public. (b) **Feedback is made legal by an explicit time step on the cable**, not by forbidding
cycles. (c) Normalised ranges inside the box (Zoia's 0..1, Sonic's 0..1 knob-space modulation)
let modulation mean the same thing on every target.

## 7. Dataflow tools: Max/MSP, Pure Data, Node-RED, n8n

**Max/MSP and Pure Data.**
*Primitive:* the object box with inlets and outlets.
*Contract:* two kinds of connection. Messages are discrete, event-driven and typed by selector
(`bang`, `float`, `list`, `symbol`). Signals (`~` objects) are continuous audio-rate blocks.
Message connections follow *hot/cold* semantics: *"The leftmost inlet of any object is always a
hot inlet… All other inlets are cold inlets"*. The cold inlets only store a value, and outlets
fire right to left ([FLOSS Manuals, Pd: Order of Operations](https://archive.flossmanuals.net/pure-data/ch039_order-of-operations.html);
[Max tutorial 6](https://docs.cycling74.com/api/latest/max8/tutorials/basicchapter06)).
*Composition:* the patch file. Abstractions (a patch used as an object) give recursion of
composition.
*Limit:* in the message domain, **evaluation order is an invisible property of the graph**. It
depends on which inlet is hot and on spatial right-to-left order, so `[trigger]` exists to make
it explicit. Signal-domain loops need explicit `send~`/`receive~` or delay objects. The kind
split (message vs signal) is the right idea, and Sonic's `audio/control/note` split descends
from it.

**Node-RED.**
*Primitive:* the node.
*Contract:* one `msg` JavaScript object passed along wires. By convention it has `payload`,
optionally `topic`, and an auto-added `_msgid`
([Node-RED: Working with messages](https://nodered.org/docs/user-guide/messages)).
*Composition:* the flow, saved as JSON. Subflows provide reuse.
*Limit:* the message is a bag of conventions, not a contract. Node A puts the thing in
`msg.payload.data`, node B reads `msg.payload`, and nothing checks the mismatch. Nodes mutate
the shared object, so anything downstream can depend on any upstream side effect.

**n8n.**
*Contract:* *"all data passed between nodes is an array of objects"*, each item shaped
`{json, binary}` ([n8n: data structure](https://docs.n8n.io/build/work-with-data/understand-n8ns-data-structure)).
Nodes implicitly run once per item.
*Limit:* the same untyped-JSON problem. Implicit per-item iteration is convenient until a node
needs the whole set, and then it needs special modes. Workflows also blur control flow and data
flow.

**Lesson.** The *envelope* (msg, items) is what makes these tools compose: every node agrees on
the outer shape, and the inner shape is left free. That is the minimum. Without declared kinds
at the jack, the editor cannot draw a `canConnect` and errors appear at runtime. Pd/Max's split
between event messages and continuous streams maps directly onto our domain's split between
*events* ("a revision landed", "a job finished") and *state/artefacts* ("the current draft").

## 8. Spreadsheets as composition

**Primitive.** A cell holding a value or a formula.

**Uniform contract.** Every formula is a pure function of the cells it references. The engine
derives the dependency graph and recomputes incrementally. Excel's dynamic arrays and data types
(2019) let cells hold arrays and records. LAMBDA (2020) made formulas reusable named functions,
and Turing-complete
([Microsoft Research: LAMBDA](https://www.microsoft.com/en-us/research/blog/lambda-the-ultimatae-excel-worksheet-function/)).

**Configuration and composition.** The grid itself. You compose by *referencing*, not by wiring:
a formula names its inputs, and the edges follow. Data and program sit in the same surface, so
end users compose without ever "programming".

**Main limit.** Cycles are errors (or need opt-in iterative calculation). References by position
(`B7`) are brittle. Logic hides in cells, there are no modules or encapsulation before LAMBDA,
and no review or versioning culture.

**Lesson.** **Pull-based, reference-by-name composition with automatic incremental recompute** is
the most successful end-user composition model ever shipped. A module input that is "a
reference to another module's named output" plus "recompute when it changes" is a spreadsheet.
It is also how the parking rule should feel: a cell nobody references costs nothing to keep.

## 9. Git: plumbing and porcelain

**Primitive.** Content-addressed objects (blob, tree, commit, tag) plus refs: mutable names
pointing at immutable objects.

**Uniform contract.** The object store and a set of *plumbing* commands (`hash-object`,
`cat-file`, `update-index`, `write-tree`, `commit-tree`, `update-ref`) whose behaviour and output
are stable and meant for scripts: *"designed to be chained together UNIX-style or called from
scripts"* ([Pro Git 10.1: Plumbing and Porcelain](https://git-scm.com/book/en/v2/Git-Internals-Plumbing-and-Porcelain)).
*Porcelain* (`commit`, `merge`, `rebase`) is the human layer built from those.

**Configuration and composition.** Hooks at defined points, config layered as
system → global → repo, and new porcelain written as scripts over plumbing. Many tools (GitHub,
CI, IDE integrations) are other porcelains over the same plumbing.

**Main limit.** The stable contract is low level. People script the porcelain anyway and break
when it changes (hence `--porcelain` flags with *stable* output, a confusing name). Merging is
the hard part, and it lives above the data model.

**Lesson.** **Split the kernel into plumbing with a frozen contract and porcelain that may change
freely.** Sonic already does this: `PatchRuntime` is pure, tested and portable, and the patch
UI is a layer over it. Immutable content plus mutable named pointers is also the right shape for
artefacts that agents revise. Every revision is kept, and "the current draft" is just a ref.

## 10. Kubernetes: declarative resources and reconciliation

**Primitive.** The resource: a typed API object with `spec` (desired) and `status` (observed).

**Uniform contract.** Every resource, built-in or custom (CRD), has the same envelope:
`apiVersion, kind, metadata, spec, status`. Every controller follows the same loop: *"Controllers
are control loops that watch the state of your cluster, then make or request changes where
needed. Each controller tries to move the current cluster state closer to the desired state"*
([kubernetes.io: Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)).
Controllers are designed to be *level-based*. They react to the current state, not to a
remembered delta, so a missed or duplicated event is harmless
([Kubernetes API conventions](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md);
[Red Hat: operator best practices](https://www.redhat.com/en/blog/kubernetes-operators-best-practices)).

**Configuration and composition.** YAML manifests, applied declaratively (`kubectl apply`).
Composition is *indirect*: controllers coordinate only through the API server. A Deployment
controller writes ReplicaSets, a ReplicaSet controller writes Pods, and a scheduler fills
`pod.spec.nodeName`. No controller calls another. Labels and selectors are the "cables": a
Service finds its Pods by label match, not by an explicit wire. Owner references and finalizers
give lifecycle and garbage collection.

**Main limit.** Eventual consistency. Debugging *why* the system is in a given state means
reading many controllers' logs. Two controllers that disagree about the same field fight
forever. Implicit selector-based wiring is powerful but invisible.

**Lesson.** This is the closest prior art to an *agent-driven* system. Agents are controllers:
long-running, fallible, slow, and acting toward a declared goal. Four things carry over.
(a) **Desired state as plain data, observed state reported back** onto the same object.
(b) **Level-triggered reconciliation makes cycles safe.** A loop between two modules converges,
or visibly oscillates, instead of exploding. This is the domain's version of Sonic's
one-quantum delay. (c) **Coordination through a shared store, not direct calls.** (d) **A
uniform envelope that lets generic tools (kubectl, dashboards, GC) work on kinds they have never
seen.**

## 11. Datomic and event sourcing

**Primitive.** The fact (datom) or the event.

**Uniform contract.** *"A datom is an immutable atomic fact that represents the addition or
retraction of a relation between an entity, an attribute, a value, and a transaction"*
([Datomic data model](https://docs.datomic.com/whatis/data-model.html)). Transactions only add
datoms, and the database can be queried *as of* any point in time. Event sourcing keeps the
same idea in application form: state is a left fold over an append-only event log
([Fowler: Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)).

**Configuration and composition.** Readers compose by *query* or *projection* over the shared
log. A new consumer can be added later and replay all history. Producers do not know their
consumers.

**Main limit.** Schema evolution of old events. Projection rebuild cost grows with history.
"Delete" is hard (privacy). The log is an excellent substrate and a poor user interface.

**Lesson.** Facts in a shared append-only log give **provenance, replay and late-bound
consumers** for free. Every artefact can say which inputs and which revision produced it. When
an agent produces a bad result, you can see *why* and re-run from that point. Datomic's
"database as a value" also means a module reads a *consistent snapshot*, which is the analogue
of Sonic reading the previous quantum's output on a feedback edge.

## Cross-cutting principles for a simple kernel that composes

Each principle is stated so that a kernel design could visibly break it.

1. **One envelope, few kinds, and a `canConnect` over kinds.** Every successful system has a
   single outer shape that everything honours: bytes, voltage, 9P, `msg`, k8s object, datom.
   The ones that age well add a *small* set of kinds at the jack: Pd's message/signal, Sonic's
   audio/control/note, PowerShell's types. Untyped (Unix, Eurorack, Node-RED) pushes errors to
   runtime. Fully typed (PowerShell) builds walls at the edge. *Violation:* a per-module bespoke
   schema on every cable, or no kinds at all.

2. **The composition is plain data, separate from the modules.** VCV/Zoia/Sonic patches,
   Node-RED flows, k8s manifests and OTP child specs can be saved, diffed, versioned, templated
   (presets) and generated by an agent. Emacs and Erlang's dataflow, where composition is
   code or mutation, cannot. *Violation:* any wiring that exists only inside a module's code or
   config.

3. **Modules know only their own jacks.** A module never names its neighbours. Unix programs
   don't know the next program, k8s controllers don't call each other, Sonic modules "neither
   know nor care what is on either side". *Violation:* the writing tool importing swarm's API
   directly.

4. **Cycles are legal and need an explicit time step.** VCV gives every cable a 1-sample delay,
   Sonic gives every loop a 1-quantum delay, and Kubernetes reconciles level-triggered against a
   store. Pd, which has no such rule, needs `[trigger]` and folklore, and spreadsheets forbid
   cycles outright. A kernel for agents needs feedback (critic → writer → critic), so it must
   define the step, for example "a back-edge reads the previous revision", and bound it with
   budgets (OTP's MaxR/MaxT). *Violation:* cycles forbidden, or cycles that recurse in the same
   step.

5. **Unreached modules cost nothing, and demand is pulled from the outputs.** Sonic runs a
   module only if it reaches an output. Spreadsheets recompute only what is referenced, and
   lazy namespaces mount on walk. In a world where a module run means agent invocations and
   tokens, *parked* must mean **no agent invoked, no tokens spent**, while state is kept.
   *Violation:* every module polls or runs on a timer whether anyone reads it or not.

6. **Stable identity, so live edits keep state.** Sonic diffs patches and keeps modules whose
   id and type survive. `kubectl apply` and Emacs live redefinition work the same way. Module
   ids, port ids and `type` names are never renamed once shipped. *Violation:* re-instantiating
   the world on every edit, which loses a long-running research job because a cable moved.

7. **Plumbing with a frozen contract, porcelain on top.** This is Git's split and Sonic's split
   (the pure `PatchRuntime` vs the UI). The kernel is small, pure, tested and stable. Editors,
   presets and the CLI are replaceable. *Violation:* kernel behaviour that is only reachable
   through a UI.

8. **Failure, provenance and time are in the contract, not bolted on.** OTP builds failure into
   the topology, Datomic builds time and provenance into the data, and k8s builds observed
   status into every object. For fallible, slow, costly agent modules this is not optional.
   Every output carries the revision, the inputs that produced it and its status; every module
   has a declared failure policy. *Violation:* a module that can only report "done" or throw.

## What is the cable/jack/patch here

Sonic's answers are fixed by the medium: a cable carries a 128-sample mono block per quantum,
a jack has one of three kinds, and a patch is `{modules, cables}` data. The target modules (a
writing tool, a knowledge base, swarm, a research tool) are **not audio-rate streams**. They
deal in **artefacts** (drafts, notes, sources, specs, features), **revisions** of those
artefacts, **long-running fallible jobs** (agent runs) and **costly computation** (tokens,
minutes). The prior art offers five candidate cable semantics. This is the choice iteration 2
has to make, so it is framed here rather than decided.

| Cable semantics | Prior art | What the cable carries | Makes easy | Makes hard |
|---|---|---|---|---|
| **Stream** | Unix, Pd signal, Sonic | a continuous flow of chunks | linear pipelines; streaming LLM output into the next stage | artefacts that are revised rather than appended; random access; "what is the current value?" |
| **Mounted namespace** | Plan 9 | a *view*: module A sees module B's tree at a path | read/write sharing of artefact collections (KB notes as the research tool's `/sources`); scoping, since a module sees only what is bound | change notification; events ("job finished"); typing what lives at a path |
| **Declared desired state + reconcile** | Kubernetes | a spec object; controllers converge `status` toward it | long-running agents, retries, idempotence, cycles that converge; humans and agents edit the same spec | latency and eventual consistency; invisible coupling via selectors; controllers fighting over a field |
| **Append-only fact log** | Datomic, event sourcing | facts/events; consumers project | provenance, replay, audit, late consumers, "re-run from here"; snapshot reads make back-edges well-defined | the "current draft" needs a projection; schema evolution; deletion |
| **Message bag** | Node-RED, n8n, Erlang | a loose JSON envelope per event | fastest start; agents produce JSON naturally | no `canConnect`; errors at runtime; shared-mutable-object bugs |

What each Sonic idea likely becomes, whichever row wins:

- **Jack kind.** A small set of artefact/event kinds, for example `doc` (a revisable artefact),
  `collection` (a set of artefacts), `event`/`signal` (something happened), and `spec` (a
  desired state). `canConnect` over kinds, with *permissive* pairs in the Sonic spirit (any
  `doc` can feed anything that reads text, just as audio and control interchange) and *hard*
  boundaries only where nonsense would follow (Sonic's `note`).
- **Cable.** A reference from an input to another module's named output. In spreadsheet terms
  it is "this input = that output", and in Plan 9 terms "bind that output here". Several cables
  into one input need a defined merge, the analogue of Sonic's summing. For collections the
  merge is union; for docs it needs a rule.
- **Patch.** Plain data `{modules: [{id, type, config}], cables: [{from, to, kind}]}`, saved,
  versioned and diffable. Presets are starting patches. An agent can propose a patch as a diff.
- **Quantum.** Not 128 samples. Most likely **one revision of an output** or **one reconcile
  pass**. A feedback edge reads the source's *previous revision*, the analogue of "reads what
  its source wrote in the previous quantum", and a budget bounds the number of passes.
- **Parked.** Not reachable from anything the user reads (a sink, a view, an export), so it is
  not run: **no agent invoked, no tokens spent**, state and history kept, revived by a cable.
- **Modulation cable into a param.** Configuration that comes from another module's output, for
  example the research tool's "topic" param driven by the writing tool's current heading. Like
  Sonic's choice params (`channel`, `pair`), some config must be marked *not cable-movable*:
  budgets, credentials, model choice.

## Implications for the kernel

1. **The kernel is a runtime of three things only: module descriptors, a patch
   (`{modules, cables}` as plain data) and a scheduler.** Everything else is a module or
   porcelain, *including swarm*. This mirrors `types.ts` as "the whole contract" and a registry
   where adding a module is one file and one line.
2. **The descriptor is the contract, as in Sonic.** It holds a stable `type`, input and output
   jacks with kinds, config params (range, default, whether a cable may move it), and two
   declared costs in words: **latency** (how long a run takes) and **cost** (tokens or money per
   run), the analogues of Sonic's `latency` and `cost` fields. Add a **failure policy** (OTP:
   restart, restart dependents, escalate; bounded by MaxR/MaxT). A contract test holds every
   module to it, as `registry.test.ts` does.
3. **Choose the cable semantics deliberately, and consider a two-layer answer.** The strongest
   combination from the prior art is an **append-only revision log as the substrate** (Datomic,
   Git: provenance, replay, snapshot reads) with **artefact references as the cable**
   (spreadsheet or namespace: "this input reads that output's latest revision") and
   **level-triggered reconciliation as the scheduler** (Kubernetes: a module re-runs when its
   inputs' revisions differ from those its last output was built from). That is one candidate,
   not a verdict. Iteration 2 should pit it against at least a stream-first kernel and a
   namespace-first kernel on the same three compositions.
4. **Evaluation is pull-from-sinks and incremental.** A module runs only if a sink reaches it
   and its inputs changed since its last revision, which is Sonic's depth-first order from the
   outputs plus spreadsheet recompute. That is what makes "parked costs nothing" true when
   running means spending tokens.
5. **Feedback is legal, delayed by one revision and budgeted.** Back-edges read the previous
   revision, and loops carry an explicit max-passes or convergence check. This makes
   writer↔critic, swarm's build↔review and research↔KB refinement first-class rather than
   hacks.
6. **Every output is a revision with provenance:** `{module id, input revisions, config hash,
   status, cost spent}`. This is the kernel's version of `status` in Kubernetes, and it is what
   lets a human (or the "nobody here can judge" checklist in Sonic) see why something is the way
   it is.
7. **Live edits diff the patch, never rebuild it.** Modules whose `id` and `type` survive keep
   their state and in-flight jobs. Moving a cable does not kill a running research job, just as
   it does not cut a reverb tail.
8. **Keep plumbing and porcelain apart.** The kernel (patch types, `canConnect`, scheduler,
   revision store) is pure and tested without any UI or LLM. A patch editor, a CLI, presets and
   an "agent that proposes patches" are porcelain over it.
9. **Isolation by view (Plan 9).** A module can read and write only what is cabled or bound
   into it. That is the composition model, and it is also the security and capability model for
   agent modules that would otherwise roam the filesystem.
