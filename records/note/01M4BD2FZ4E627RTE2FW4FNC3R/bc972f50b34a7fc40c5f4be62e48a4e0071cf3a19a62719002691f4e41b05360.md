# 02 — Kernel C: NAMESPACE (the Unix/Plan 9 answer, updated for agents)

Iteration 2, candidate C (see `STATE.md`). Kernels A ("patch bay": the graph comes first) and B
("ledger": the log comes first) are written in parallel. This document pushes C as far as it
honestly goes. The claim being tested: **a directory of plain records, a handful of path
conventions and one small runner are enough for these modules, and they are the only answer whose
data and compositions still work when the kernel is gone.**

Obsidian, §2.7 atproto, §3, candidate jack kinds), `01-failure-modes.md` (the 16 tests),

## 1. The core idea (the one-page spec, in one paragraph)

The user's work is **one directory tree in a git repo they own** (the *workspace*), and every record in it is a plain file — Markdown with a YAML frontmatter envelope, or JSON — carrying a `kind`, an open namespaced `type`, `links` written as `path@blobsha`, and a `run` stamp; the file's **path is its name**, its git blob sha is its content address, and git history is its log. A **module** is any program plus a manifest, and it is a **filter** (records as JSONL on stdin, records as JSONL on stdout), a **job** (reads and writes the paths it is given) or a **server** (the sole writer of one subtree, taking requests through files dropped in its request directory). A module never sees the workspace: it sees a **namespace**, the views its manifest declares, each bound by the caller to a workspace path either read-only or as a staged output, and **that namespace is the module's whole capability set**, enforced by the OS sandbox. The central kernel verb, `ns run`, builds the namespace, runs the module, validates the records it emits, stamps each new record with a run id whose run file pins the exact input blobs, module version and cost, and commits the outputs atomically; it skips the run when the same module version has already run on the same input blobs. **Authority is write access to a path**: agents can never be bound writable to a protected path such as `decisions/accepted/`, which only `ns approve` writes — a human command, run outside every sandbox, whose commit is signed with a key no sandbox can read. **Composition is text a human can read** (a Makefile or a shell script whose steps are `ns run`), feedback means reading the *previous numbered version* of a file, and every loop carries its bound in the script that runs it.

## 2. Kernel primitives, and what is not in the kernel

### Position: there is a kernel, but it is a spec plus five verbs, not a runtime

There is no daemon, scheduler, database or graph engine. The kernel is:

- **the spec** (§1 plus the envelope in §4), versioned as a whole (`ns-spec: 1` in `NS.md` at the
  workspace root);
- **one binary, `ns`, with five verbs.** It holds every rule that must not be left to each module's
  care (the Eurorack power header, `01-failure-modes.md` §10).

Everything else is porcelain or a module. This is git's plumbing/porcelain split
(`01-prior-art.md` §9) taken as far as it goes. The test of the position is §6, test 15: delete
`ns`, and the tree, the manifests and the recipes still read as what they are.

### The primitives (complete list)

| # | Primitive | What it is | Prior art |
|---|---|---|---|
| P1 | **Workspace** | one directory, one git repo, user-owned. Paths are names, blob shas are content addresses, commits are the log. | Obsidian vault (`01-data-model.md` §2.6), git (§2.2) |
| P2 | **Record** | a file with the envelope (§4): `.md` + frontmatter, or `.json` with the same top-level fields. Bodies are free. Bytes too large for text are `artifact` records that point to a blob. | Notion block, atproto record minus the DID |
| P3 | **Module manifest** | `modules/<name>/MODULE.md`: frontmatter that declares mode, exec, views (jacks) with kinds, caps, cost and timeout, followed by prose. | sonic `Plugin` descriptor; swarm's classic agent `.md` role descriptor (`01-inventory.md` §1, §5); SKILL.md |
| P4 | **Namespace (bind)** | `--bind view=path[:ro\|:out]`. The module sees `$NS/<view>` and nothing else. `ro` binds are read grants. `out` binds are a fresh staging directory the module writes. | Plan 9 `bind`/`mount` (`01-prior-art.md` §2); swarm's `sandbox.read[]` |
| P5 | **Run** | one execution of one module in one namespace, ending in exit status `0` (done), `75` (`EX_TEMPFAIL`: waiting, with a question record emitted) or any other code (failed). It leaves `runs/<run-id>.json` and one commit. | swarm round + hand-back (`result \| question`) |
| P6 | **Protected path** | two lists in `NS.md`. `human_only:` paths (`decisions/accepted/`, `approvals/`) are written only by `ns approve`, with a signed commit. `requests:` paths (`ctl/`) are where paid work is requested: never bindable `:out`, written only by `ns put` from a process outside any sandbox, meaning the human or a recipe the human runs. | swarm's `approve` (human token only, `01-inventory.md` §1); sonic's non-modulatable params |

The five verbs:

```text
ns run <module> [--bind view=path[:ro|:out]]... [--budget USD] [--force] [-- args]
ns cat <path|glob>...            # records → JSONL on stdout (blob sha included)
ns put <dir>                     # JSONL on stdin → validated, stamped, committed records
ns approve <path> [--to <dir>]   # human-only: move/flip a record into a protected path, signed commit
ns check [module|workspace]      # conformance: manifests, envelopes, links resolve, protected-path audit
```

For a filter module, `ns run` *is* the pipe: it does `ns cat` on the `stdin` bind itself, so it
knows exactly which blobs went in, pipes them through the module, and `ns put`s stdout into the
`out` bind. A bare shell pipe `ns cat … | filter | ns put …` also works, but `ns put` cannot know
what the filter read, so it is **unstamped**: its records get `run: manual` with no `inputs`, and
`ns put` refuses `claim` and `decision` records arriving that way. There is one stamped mutation
path, `ns run`, which follows printer's `applyOps` rule and swarm's D-013 (`01-inventory.md`,
recurring pattern 1). `ns put` alone is for human-authored records: requests, replies and notes.

### Semantics the verbs pin down

- **Staleness is by content, never by mtime.** Before running, `ns run` computes a key from the
  module name, the manifest version, the exec digest, the args, the bind map and the blob sha of
  every file under every `ro` bind. A run file with that key and exit 0 already in `runs/` means
  the run is **skipped** and its outputs stand. So:
  - make's mtime problem after a `git checkout` goes away (make only orders steps; `ns` decides
    what is stale);
  - a nondeterministic LLM module's result is **the** result for those inputs until someone passes
    `--force` or changes an input. That is a feature: re-running a recipe after a human gate costs
    nothing up to the gate. It is the knowledge-work form of "parked costs nothing"
    (`01-prior-art.md`, principle 5).
- **Outputs are staged, then committed atomically.** A module writes only into its `out` staging
  directories. On exit 0 or 75, `ns` validates every record, stamps `run:`, moves the files into
  place and makes one commit with the trailers `Ns-Run:`, `Ns-Module:` and `Ns-Inputs:` (a hash of
  the input-blob list). On any other exit, nothing lands. The failure is the run file plus stderr
  in `runs/<id>.log`.
- **Concurrency.** Runs execute in parallel. Their *commits* are serialized by one lock
  (`.git/ns.lock`, held only for the move-and-commit, which takes milliseconds). Two runs that
  stage the same output path conflict, and the second fails loudly rather than merging. Code-
  editing modules (swarm) do not work in the workspace at all: they get **their own git worktree**,
  as swarm already does per feature (`src/loop/git.ts`, `01-inventory.md` §1). The workspace is
  for records, not for a product's source.
- **Isolation.** A run is a child process under nono (macOS) or bubblewrap (Linux), with:
  - read grants for the `ro` binds;
  - write grants for its staging directories;
  - network only if the manifest's `caps.net` allows it;
  - a wall-clock timeout from the manifest.

  macOS has no per-process mount namespaces. There, the "view" `$NS` is a scratch directory of
  symlinks to the bound paths, and the **sandbox grants are the enforcement**: following a symlink
  out of the view hits a denied path. This is exactly how swarm already confines rounds
  (`board.json.sandbox.read[]`, its own nono profile; `01-inventory.md` §1).
- **Servers are the exception, and are confined only after the fact.** A server is a long-lived
  process the human starts, such as `swarm serve`. It sandboxes its *own* agent runs, as swarm
  does per round, but `ns` does not sandbox the server itself, which needs the human's delegation
  (swarm merges with the human token). The kernel's only hold on it is `ns check`. That command
  fails any commit by `Ns-Module: swarm` that touches a path outside the server's `owns:` and
  `emits:` lists. Git can then revert the commit.

### Not in the kernel (deliberately)

| Left out | Where it lives instead | Why |
|---|---|---|
| Scheduler, daemon, event bus | make, shell, `cron`, and an optional `ns watch` porcelain (fswatch → re-run a recipe) | an event bus is the thing that does not outlive the kernel |
| Graph or patch object | the recipe file *is* the patch | §6 test 11: the composition is already plain text |
| Body schemas | modules publish them as records (`schemas/<type>.json`); `ns check` validates them if present | no global ontology (`01-data-model.md` §2.4) |
| LLM calls and model credentials | inside modules; `caps.model` and `--budget` are declared and metered by reading the module's reported cost | Sampling is deprecated in MCP (`01-ai-landscape.md` §0); the kernel lending models is a *possible* later verb, not v1 |
| Search, query, indexes | filter modules that *materialize* an index as records (`kb/index/*.json`) | Plan 9's synthetic files are its strength, and also where its semantics hid in per-server conventions (`01-prior-art.md` §2). We refuse them in the kernel. |
| UI, board, editor | porcelain that reads the tree (any editor, Obsidian, swarm's board page) | Obsidian's lesson: a great file editor *is* the UI |
| 9P, FUSE, MCP | adapters. `ns serve --mcp` exposes a namespace as MCP resources (below) | the protocol is a door, not the house |
| Sync and sharing | `git push` / `git pull` | already solved, already owned |

**The MCP adapter (porcelain, but it matters for agents in other hosts).** `ns serve --mcp
--bind ...` serves one namespace (never the whole workspace) under the 2026-07-28 spec:

- `server/discover` lists the views;
- records are resources `ns:///<view>/<path>` with `mimeType` taken from the extension, and a
  pinned form `ns:///<view>/<path>@<blobsha>`;
- change notifications go through `subscriptions/listen`, driven by commits to bound paths;
- there are no sessions, and directories are passed as resource URIs, not Roots, which are
  deprecated (`01-ai-landscape.md` §0);
- there is one tool, `put_records(records[])`, which writes only into `out` binds and is stamped
  as a run of the serving namespace (`module: mcp-host`, with the host's `clientInfo`). A host LLM therefore has exactly the capability the namespace grants
  (`01-ai-landscape.md` §3, gap 5: "no per-cable capability grant"). Here the bind *is* that grant.

## 3. Module contract

### How a module declares itself

```yaml
# modules/extract-claims/MODULE.md
---
name: extract-claims          # stable, never renamed (sonic's `type` rule)
version: 3                    # bumps invalidate the run cache
mode: filter                  # filter | job | server
exec: ["node", "bin/extract-claims.js"]   # relative to the module dir; digest goes in the run key
in:
  - { view: stdin, kind: doc }                         # filter: stdin is a JSONL record stream
out:
  - { view: stdout, kind: claim, type: research.claim, status: proposed }
caps: { net: false, model: "claude-sonnet", budget_usd: 0.50 }
cost: "≈ $0.02 per source page, 3–8 s each"          # words, like sonic's `cost`
timeout: 300s
adapter: true                 # doc → claim is a lossy LLM coercion; must be declared (§4 canConnect)
---
Reads source documents and emits one claim per checkable statement, each with a verbatim
`quote` and a `derivedFrom` link to the source at its blob sha. Never paraphrases inside `quote`.
```

A **job** names its views:

```yaml
in:  [ { view: q, kind: doc }, { view: kb, kind: doc, optional: true } ]
out: [ { view: sources, kind: doc, type: research.source } ]
```

A **server** declares what it owns and how it is driven:

```yaml
mode: server
owns: swarm/                  # sole writer; ns check fails any commit touching it without Ns-Module: swarm
ctl: ctl/swarm/               # request inbox, outside the owned subtree, under NS.md `requests:`
serve: ["swarm", "serve"]
emits: [ { path: decisions/proposed/, kind: decision, status: proposed } ]
```

### Inputs and outputs on the wire

A filter's JSONL line is one record:

```json
{"path":"claims/crdt-merge-cost.md","meta":{"kind":"claim","type":"research.claim","links":{"derivedFrom":["sources/automerge-3.md@3b18e2c"]}},"body":"Automerge 3 cut memory use by more than 10×…"}
```

`ns cat` adds `"sha"` to each line. `ns put` refuses any line that:

- lacks `kind`;
- names a path outside the target directory;
- names a `kind` the manifest did not declare;
- would land under a protected path.

An `artifact` travels as `{"path":…,"meta":{"kind":"artifact","blob":"<sha256>","size":…}}`. Bytes
never go on the pipe.

### How a module is run

- **Directly:** `ns run <name> --bind …`. This is the only way to get provenance, the cache and the
  sandbox.
- **Without `ns` at all:** every module is still a plain CLI. `extract-claims < sources.jsonl`
  works. You lose the stamp, the cache and the sandbox, not the function. This is §6 test 1 and
  test 15.

### How an existing tool becomes a module

1. **A CLI with `--json`** (printer, `01-inventory.md` §3): a manifest whose `exec` calls it. If it
   speaks JSON but not the envelope, a ten-line shim maps its output to records. Printer's
   `describe --json` becomes a `doc`, and `check --json` becomes `claim` records ("wall too thin at
   node cut1").
2. **A tool with its own state directory** (swarm): it becomes a **server** that owns a subtree.
   Its existing files *are* its interface. Swarm already reads its own state from files and writes
   it through one path (`01-inventory.md` §1, "reads go straight to the feature JSON files"). The
   adapter work is to:
   - move `.swarm/simple/` into the workspace as `swarm/` (or bind it there);
   - add a `ctl/swarm/` reader (a dropped `add-*.md` record runs the same code as `swarm add`);
   - emit decisions as records (C2).

   Swarm's board page, CLI and HTTP API stay as porcelain over the same files.
3. **An MCP server** (any third party): `ns-mcp-client` is a generic module that calls one tool and
   writes the `structuredContent` as a record. One adapter for all MCP servers, owned in one place
   (`01-failure-modes.md` §7, Zapier's "centrally owned adapters").
4. **A pure web service:** a job module with `caps.net: [host]`.

## 4. Record model

### The flip from the data-model track, argued

`01-data-model.md` (§3.1 and its kernel section) recommends an append-only, content-addressed
**record log as the source of truth**, with files as projections. Kernel C reverses that: **files
are the source of truth, and git is the log.**

What we get from git:

- content addressing: the blob sha;
- an immutable history: commits;
- tamper evidence: the sha chain, plus signatures on protected paths;
- "as of" reads: `git show <rev>:<path>`;
- free sync and backup.

What we lose against a real record log:

- **No per-record append event.** A commit is the event, and it is coarse: one per run. A consumer
  wanting "every new claim since offset N" computes `git diff --name-only <last-seen>..HEAD --
  claims/`. That works, and it is a poll, not a push.
- **No folds as first-class views.** "The current status of feature f-abc" is the current file
  content, a mutable materialization like swarm's feature JSON. The fold lives in the module that
  writes it, not in the kernel.
- **Identity of a "thing" across renames is weaker.** A path is a name and names change, so `id:`
  in the envelope carries identity across a `git mv`, and `links` should cite `path@sha` (exact)
  or `id:` (living).

The argument for paying that price is §6 test 15 and the ownership row of `01-data-model.md` §3.1:
files score "best" on longevity, on tool diversity (grep, editors, LLMs, Obsidian) and on fit for
agents, which read and write files natively. Every agent harness in `01-ai-landscape.md` §1.3–1.4
ships a filesystem. The log's advantages (events and folds) return as porcelain (`ns watch`, index
filters). The ownership and longevity advantages could not come back as porcelain over a log.

### The envelope

```yaml
---
kind: claim                     # doc | claim | decision | artifact   (closed set, ns-spec 1)
type: research.claim            # namespaced, open; atproto evolution rules
id: c-7f3a91                    # optional stable identity across renames
status: proposed                # only meaningful for decision (proposed|accepted|superseded) and claim (proposed|checked)
links:                          # typed refs; values are path@blobsha (exact) or id: (living)
  derivedFrom: [sources/automerge-3.md@3b18e2c]
  about: [questions/sync.md@a01f9d2]
run: r-20261007T1532-9ab4       # STAMPED BY ns; a module that writes it is rejected
---
Body: free Markdown. Types add optional frontmatter fields; never required ones (atproto, §2.7).
```

`runs/<run-id>.json` is itself a record (`kind: doc`, `type: ns.run`):

```json
{"module":"extract-claims","version":3,"exec_digest":"sha256:…","args":[],
 "binds":{"stdin":"sources/"},
 "inputs":{"sources/automerge-3.md":"3b18e2c","sources/patchwork.md":"9c0d…"},
 "outputs":["claims/crdt-merge-cost.md", "…"],
 "exit":0,"cost_usd":0.11,"wall_s":41,"model":"claude-sonnet-…",
 "by":"agent","on_behalf_of":"svib","started":"2026-10-07T15:32:04Z","commit":"<sha>"}
```

That is PROV-O's `wasGeneratedBy`, `used`, `wasAssociatedWith` and `actedOnBehalfOf`
(`01-data-model.md` §2.4), in plain JSON.

### Two kinds of provenance, kept apart on purpose

1. **Run provenance: stamped by the kernel, unforgeable by the module.** Which module and version,
   which input blobs, which cost, who triggered it. The module cannot write `run:`, and `ns`
   computes `inputs` itself from the binds. This is the Datomic rule, "the store stamps it, not the
   author" (`01-data-model.md` §3.3).
2. **Claim provenance: written by the module, checked by a deterministic filter, never trusted.**
   "This sentence came from that passage" is a judgement only the module can make, so the module
   writes `links.derivedFrom: [path@sha]` and a verbatim `quote:`. `ns check` and the `trace`
   module then verify, with no LLM:
   - the linked blob exists in git;
   - it was among the run's recorded `inputs` (a module cannot cite something it was never shown);
   - `quote` occurs in the blob's text after whitespace normalization.

   A claim that fails stays `status: proposed`. It never becomes `checked`.

### Kinds: a position on the six candidates (`01-data-model.md`, candidate jack kinds)

The namespace answer is **four kinds, and authority lives in paths rather than kinds.**

| Candidate | Verdict | Reason |
|---|---|---|
| `doc` | **Keep.** It is the universal input. | Any record renders to text deterministically (`ns cat --as-text`), so any kind binds into a `doc` view. This is the "control can be heard" direction. |
| `claim` | **Keep, as a doc with three required fields** (`derivedFrom`, `quote`, `run`). | It is the one kind whose required fields enable a deterministic check (above). Without the kind, "every claim traces to a source" in C1 is a convention nobody can enforce. The RDF risk (`01-data-model.md` §2.4) is answered by the body staying prose and the required fields being exactly three. |
| `decision` | **Keep.** It is the strict kind. | It carries authority. In this kernel `status: accepted` is legal **only** for a file under a protected path, so `ns put` rejects an accepted decision anywhere else. The kind supplies the shape and the path supplies the authority. |
| `artifact` | **Keep.** It is the bytes escape hatch. | A pointer record: `blob` (sha256), `size`, `media`, plus a `path` under `artifacts/` (git-lfs or plain git, by size). For a git ref it is `{repo, ref, sha}`, which is swarm's `snapshotSha` (`01-inventory.md` §1). |
| `task` | **Drop as a kind. A task is a *place*, not a type.** | A request is a `doc` dropped into a server's `ctl/` directory. Its state is the server's owned subtree (`swarm/features/f-abc.json`). The authority a task carries (it spends money) belongs to whoever may write to `ctl/`. `NS.md` lists `ctl/` under `requests:`, so no agent can enqueue paid work, which is a path permission again. This is Plan 9's ctl file. |
| `signal` | **Drop as a kind, and say plainly what that costs.** | A tree has no events. "Approved" is a file existing under `decisions/accepted/`. "A question was asked" is a record in `inbox/`. "Budget reached" is exit 75 plus a run file. "Something changed" is a commit. Most signals are therefore *representable as state*. **Edge-triggered** signals are not: "fire once when X happens", or a clock tick nobody writes down. They become polling (`ns watch`) or cron. This is the weakness in §7.1. |

**`canConnect` (checked by `ns run` before anything starts, and by `ns check` on a recipe's
literal `ns run` lines):**

- **Same kind binds.** If the view narrows `type`, the type must match, or the view leaves it open.
- **Any kind into a `doc` view binds.** It is rendered to text.
- **`doc` into a `claim` or `decision` view does not bind.** The conversion must go through a
  module whose manifest says `adapter: true`. That module's outputs are stamped and capped at
  `status: proposed`.
- **`artifact` binds only into `artifact` views.** Into `doc` views it binds as its description.
- **A view declared `authority: accepted`** (for example a swarm basis) binds **only** to a
  protected path. This is the kernel-level form of "no cable into approve" (`01-inventory.md` §1;
  sonic's `modulatable: false`).

Fan-in is **union**. Several `ro` binds to one view become one union directory (Plan 9's union
directories, `01-prior-art.md` §2). On a name clash the earlier bind wins, and the clash is
reported. Docs are never "summed". Merging two drafts is a module.

### Versioning

- **A record's versions are its git history.** "Previous revision" in a feedback edge is either
  `path@<earlier sha>` or, more legibly, a **numbered sibling** (`v1.md`, `v2.md`). C3 uses
  numbered siblings because they make the quantum visible in a plain `ls`.
- **Types follow atproto law** (`01-data-model.md` §2.7, §3.4): new fields are optional, nothing is
  renamed, a breaking change gets a new `type` (`research.claimV2`), and a lens is a module.
- **Modules:** `version` is in the run key, so upgrading a module invalidates only its own cached
  runs.
- **The spec:** `ns-spec: 1` in `NS.md`. A kernel that reads spec 1 must keep reading spec 1.

## 5. Three worked compositions

Workspace layout used throughout:

```text
~/work/                         # git repo, user-owned
  NS.md                         # ns-spec: 1; human_only: [decisions/accepted/, approvals/]; requests: [ctl/]
  ctl/<server>/                 # request inboxes (agents can never write here)
  modules/<name>/MODULE.md      # manifests (+ code, or exec pointing at an installed CLI)
  recipes/                      # Makefiles and scripts = the patches; presets live here
  questions/  sources/  claims/  kb/  drafts/  decisions/{proposed,accepted}/  inbox/  runs/
  swarm/                        # owned by the swarm server (features/, rounds)
```

### C1 — research → knowledge base → writing, with every claim traceable to a source

`recipes/article.mk`. All targets are phony: make only orders the steps, and `ns` decides what is
stale.

```make
.PHONY: article sources claims kb draft check
Q      = questions/local-first-2026.md
SLUG   = local-first-2026

article: check                                   # the sink; `make -f recipes/article.mk article`

sources:
	ns run research --bind q=$(Q):ro --bind sources=sources/$(SLUG)/:out --budget 2.00

claims: sources
	ns run extract-claims --bind stdin=sources/$(SLUG)/:ro --bind stdout=claims/$(SLUG)/:out

kb: claims
	ns run kb-file --bind claims=claims/$(SLUG)/:ro --bind notes=kb/notes/:ro \
	               --bind out=kb/notes/:out                      # new/updated notes, never deletes

draft: kb
	ns run write --bind brief=$(Q):ro --bind kb=kb/notes/:ro --bind claims=claims/$(SLUG)/:ro \
	             --bind out=drafts/$(SLUG)/:out --budget 1.00

check: draft
	ns run trace --bind doc=drafts/$(SLUG)/article.md:ro --bind out=drafts/$(SLUG)/:out
```

**Walk-through.**

1. **`research`** (a job, `caps.net: true`) reads the question and writes one `doc` per source:
   `type: research.source`, with `url`, `fetched` and the fetched text in the body. The text is the
   point: a URL changes, a blob sha does not. One commit, one run file.
2. **`extract-claims`** (a filter, `adapter: true`) receives the sources as JSONL with their shas.
   It emits claims with `derivedFrom: [sources/…@sha]` and a verbatim `quote`. `ns run` rejects any
   `derivedFrom` link to a blob that is not among the run's recorded `inputs`. That check is
   possible because `ns run` itself fed the stdin bind and recorded every blob.
3. **`kb-file`** is the knowledge base acting as a job. It merges new claims into topic notes
   (`kb/notes/crdt.md`), and each note's body cites claim ids (`[[c-7f3a91]]`). The KB is
   *useful alone*: an Obsidian-compatible vault of notes with backlinks (§6 test 1).
4. **`write`** drafts `article.md`. Every factual sentence carries a footnote `[^c-7f3a91]`, and
   the footnote section lists `claims/…@sha`. Its namespace contains the brief, the notes and the
   claims, and **not** the web. It has no `caps.net`, so it cannot cite anything it was not given.
5. **`trace`** is deterministic and costs nothing. For every footnote it checks that the claim
   exists at that sha and that the claim is `checked` (its quote occurs in its source blob). It
   writes `drafts/<slug>/trace.md`, a table `sentence → claim → source passage`, and exits 1 if any
   sentence lacks a chain.

**Where the human waits.** After `check`, the human reads `article.md` beside `trace.md`. Edits
are ordinary file edits followed by `git commit`. Rerunning `make article` re-runs only `trace`,
because `write`'s inputs have not changed. If the human edits a KB note, `write` is stale and runs
again. **Parking:** a `make sources` alone never runs `write`, which is pull from the sink.

**What C1 proves and what it does not.** The chain sentence → claim → quote → source blob is
checked by a program, not trusted. It cannot tell whether the sentence *faithfully represents* the
claim. That is a judgement, and it belongs in C3's critic loop or with the human.

### C2 — swarm reads the decision register, delivers, and accepted decisions flow back

**Decision format.** Today there are two:

- the flat `.swarm/simple/decisions.jsonl`;
- the classic `.swarm/decisions/<id>.json` with revisions, a `D-NNN` id and a projection
  (`01-inventory.md` §1).

C2 uses **one record per decision**, `decisions/{proposed,accepted}/D-NNN.md` (`kind: decision`),
because a per-file record has a blob sha that a basis can pin and a path that can be protected. A
one-time `migrate-decisions` filter turns both old formats into these files. Revisions become git
history and `supersedes:` links become `links.supersedes`. `docs/product/decisions.md` stays a
projection (`ns cat decisions/accepted/ | decisions-md > docs/product/decisions.md`).

**New in swarm** (none of these exist today; `basis` is always `[]`, `01-inventory.md` §1):

- the `ctl/swarm/` reader;
- an `--basis <dir>` flag;
- basis pinning from blob shas;
- decisions emitted as records.

Swarm's own `approve` of a *feature* (the merge) stays exactly as it is: a human-token route.

**The time axis.** This loop spans features and days, so it is not one recipe invocation:

```text
day 1  human    $ ns put ctl/swarm/ <<< '{"path":"add-sync.md","meta":{"kind":"doc","type":"swarm.add",
                     "basis":"decisions/accepted/","budget":8},"body":"Add offline sync to the board"}'
                (equivalently, new flag:  swarm add "Add offline sync…" --basis decisions/accepted/)
       swarm    reads ctl/swarm/add-sync.md → creates swarm/features/f-3c1e9a.json
                pins basis = [{decisionId:"D-012", revision:"<blobsha>"}, …] for every file in
                decisions/accepted/ at that moment            ← the one-quantum delay
       round 1  runs in its own worktree, sandboxed. Namespace: repo worktree (rw),
                decisions/accepted/ (ro), NO write grant to decisions/, NO human token.
                Hand-back: result, decisions[ {choice:"CRDT per board, not per card",
                relation:"conflicts", with:"D-012"} ]
       swarm    (server, sole writer of swarm/ and of decisions/proposed/) writes
                decisions/proposed/D-034.md  kind: decision, status: proposed,
                links: {conflicts:[decisions/accepted/D-012.md@<sha>], from:[swarm/features/f-3c1e9a.json@<sha>]}
                feature → waiting(result).  Commit trailer Ns-Module: swarm
day 2  human    reads the round, the preview and D-034
                $ swarm approve f-3c1e9a                   # existing, human-token only: merges snapshotSha
                $ ns approve decisions/proposed/D-034.md   # NEW: human-only, outside any sandbox
       ns       verifies D-034's `from` feature is done·merged, sets status: accepted and git-mvs it
                into decisions/accepted/. Because D-034's relation is `conflicts`, ns approve asks
                "supersede D-012? [y/N]" before marking D-012 status: superseded. One commit, signed
                with the human's key.
day 3  human    $ swarm add "Show sync conflicts in the UI" --basis decisions/accepted/
       swarm    pins basis — now includes D-034@sha, excludes superseded D-012      ← feedback closes
```

**What enforces "agents read, only humans approve":**

- **Before the fact.** A round's sandbox has no write grant on `decisions/`, and `ns run` refuses
  any `:out` bind under a `human_only` path. The swarm *server* writes only `decisions/proposed/`.
  This is enforced by its own manifest (`emits:`) and by `ns check`, which fails any commit
  touching `decisions/accepted/` that lacks an `Ns-Approve:` trailer.
- **After the fact.** Every commit under `decisions/accepted/` must be signed with a key listed in
  `NS.md` under `approvers:`. The key lives in the human's ssh-agent or keychain and is never
  inside a sandbox's read grants. Swarm keeps its human token at `~/.config/swarm/human-token`
  outside every round's profile for the same reason. Anyone with git can audit the log with
  `git log --show-signature -- decisions/accepted/`. This audit survives the kernel: it is plain
  git.
- **What does not stop it.** The human running an unsandboxed agent in their own shell with their
  own agent socket. The kernel cannot defend against the human delegating their key. The same is
  true of swarm today.

**What runs automatically.** Nothing, unless the human opts in with
`ns watch decisions/accepted/ -- make -f recipes/decisions.mk`, which regenerates the projection.
No watcher may call `ns approve`: it refuses to run without a TTY and the signing key.

### C3 — a draft goes through a critic for at most N rounds, then waits for the human

A Makefile cannot express a cycle, so the patch is a **shell script**, which is the honest form.
`recipes/critique.sh`:

```sh
#!/bin/sh
# usage: recipes/critique.sh drafts/essay [N=3] [BUDGET=3.00]
set -eu
D=$1; N=${2:-3}; export NS_BUDGET_USD=${3:-3.00}
export NS_LEDGER="$D"            # ns run sums cost_usd over every run file whose binds lie under $D,
                                 # across invocations, so a resume does not reset the budget
R="inbox/review-$(basename "$D").md"                 # the human's reply file (may not exist yet)
REPLY=""; [ -e "$R" ] && REPLY="--bind reply=$R:ro"  # an edited reply changes the writer's run key
i=1; while [ -e "$D/v$((i+1)).md" ]; do i=$((i+1)); done   # resume: start at the newest version
while [ "$i" -le "$N" ]; do
  ns run critic --bind draft="$D/v$i.md":ro --bind brief="$D/brief.md":ro \
                --bind out="$D/":out -- --name "crit-$i.md"
  grep -q '^verdict: pass' "$D/crit-$i.md" && break
  [ "$i" -eq "$N" ] && break
  ns run writer --bind prev="$D/v$i.md":ro --bind crit="$D/crit-$i.md":ro $REPLY \
                --bind brief="$D/brief.md":ro --bind out="$D/":out -- --name "v$((i+1)).md"
  i=$((i+1))
done
[ -e "$R" ] || ns put inbox/ <<EOF            # never overwrite a reply the human has written
{"path":"review-$(basename "$D").md","meta":{"kind":"doc","type":"ns.question",
 "links":{"about":["$D/v$i.md"],"evidence":["$D/crit-$i.md"]}},
 "body":"Draft v$i after $i critic round(s). Approve, reply with notes in this file, or drop."}
EOF
exit 75                                          # EX_TEMPFAIL: waiting for a human
```

**Walk-through.**

- **`v1.md`** is the human's or the writer's first draft.
- **`critic`** (a job, fresh context, read-only on the draft) writes `crit-1.md` (`kind: claim`,
  `type: writing.critique`). Its frontmatter carries `verdict: pass|revise`, and its findings each
  quote the draft passage they are about, so they are checkable the same way C1's claims are.
- **`writer`** reads **`v1` and `crit-1`**, the *previous* version and its critique, and writes
  `v2`. That is sonic's one-quantum rule (`patch-bay.md`, "Order and feedback"): a back-edge reads
  what its source wrote in the previous step. The numbered files make each step visible in `ls`
  and diffable (`git diff --no-index v1.md v2.md`).
- **The bound is threefold:**
  - `N` iterations, enforced by the script;
  - `NS_BUDGET_USD` for spend, enforced by `ns run`: before starting, it sums `cost_usd` over every
    run file in `runs/` whose binds lie under `NS_LEDGER` (this draft's directory), across all
    invocations, and refuses with exit 75 if the next run's declared ceiling would cross the budget.
    The budget therefore belongs to the draft and survives a resume. Raising it is a human edit to
    the invocation;
  - the final human sink.
- **Where the human waits.** `inbox/review-essay.md` is their mailbox. Any editor, Obsidian or the
  MCP adapter shows it. They either:
  - write notes into that file and rerun the script with a higher `N` (for example `N=5`). On
    resume the script starts at the newest `v$i`. The `ns` run cache skips the critic run already
    made on it. The script binds the existing reply file as the writer's `reply` view, so the
    writer's run key changes and it really runs, with the human's notes in its namespace. The
    question record is created only if absent, so the human's notes are never overwritten. (A
    `verdict: pass` on the newest version still ends the loop before the writer runs. A human who
    wants changes anyway runs the one `ns run writer … --bind reply=…` line by hand.)
  - or run `ns approve drafts/essay/v3.md --to approvals/` to mark it final.

**What the kernel cannot see here.** The loop and its bound live in an `sh` `while`. `ns check`
can lint a recipe's literal `ns run` lines for `canConnect`. It **cannot** prove that every cycle
in a shell script is bounded, which `01-data-model.md` kernel item 5 asks the kernel to guarantee.
The spend bound is enforced; the iteration bound is a convention. A partial fix: ship a
porcelain `ns loop --max N --until 'verdict: pass' -- <step>` whose bound *is* declared, and make
presets use it. It is still not a kernel check on arbitrary scripts.

## 7. Weaknesses, and what this design makes hard

1. **No events, so long-running loops are invisible to the composition.** The tree holds state
   well and happenings badly. C2's real loop runs across days and exists only as a sequence of
   human commands plus swarm's internal engine. Swarm's round loop (start, resume ≤3, hand back,
   wait) stays *inside* the swarm server, where no recipe can see it. Reactivity is polling or
   fswatch (`ns watch`), and there is no "wake me when X" contract. This is Kubernetes'
   level-triggered model (`01-prior-art.md` §10) without the API server that makes it cheap.
2. **Human gates are coarse.** "Waiting for a human" means exit 75, a file in `inbox/` and a re-run
   later. There is nothing like MCP's `input_required` or A2A's `INPUT_REQUIRED` mid-run
   (`01-ai-landscape.md` §4). A module that needs one yes/no halfway through must split into two
   runs. The run cache makes this cheap, but the module author has to design for it.
3. **Compositions are hard to discover and impossible to check fully.**
   - A Makefile can be drawn (`make -pn`). A shell script with conditionals cannot be drawn or
     statically checked.
   - `canConnect` is checked per `ns run` line at run time, and by lint only where binds are
     literal. A computed path (`$D/v$i.md`) escapes the lint.
   - Nobody sees "the patch" as a graph unless a porcelain reconstructs one from `runs/*.json`.
     That graph is *after* the fact: lineage, not a plan. This is the gap the landscape already has
     (`01-ai-landscape.md` §3, gap 1), only half closed.
4. **Paths are a contract nobody versions.** If `kb-file` starts writing `kb/topics/` instead of
   `kb/notes/`, every recipe that binds `kb/notes/` silently reads stale data. Atproto law covers
   record *fields*, not *directory layouts*. Mitigation: views are named in manifests and recipes
   bind views, not internal paths. But the workspace layout is still a shared, informal API, the
   Node-RED "bag of conventions" (`01-prior-art.md` §7) moved into the filesystem.
5. **Git as a database has a ceiling.**
   - Thousands of small records per run, one commit per run, `ns cat` over large directories, and
     a single commit lock are fine for one person and a few agents, and not for a team-scale event
     stream.
   - Large artifacts need git-lfs or out-of-tree storage, which breaks "everything is in the
     repo".
   - Concurrent human edits plus agent commits mean merge conflicts on records, which the
     immutable-record log of `01-data-model.md` avoids by construction.
6. **Queries are second-class.** "All accepted decisions that conflict with anything touching
   sync" is a grep over frontmatter or a materialized index that goes stale. Logseq left files
   for exactly this reason (`01-data-model.md` §2.6). A KB that grows large will want a derived
   SQLite index. It is allowed as a filter output, but then a second, non-authoritative store
   exists.
7. **Authority rests on the OS, on trusted servers and on the user's key hygiene.** A server such
   as swarm is a trusted delegate, checked only after the fact. Path protection is only as strong as
   the sandbox (nono and bubblewrap differ by platform; symlink views on macOS are a convention
   the sandbox happens to enforce) plus the signing key staying out of agent reach. The audit is
   excellent after the fact. Before the fact, it is exactly as strong as swarm's current design,
   and no stronger.
8. **Cost control is advisory at the model boundary.** With no kernel-lent model, a module that
   lies about or under-reports `cost_usd` overspends until the next run's check. Closing this
   needs `ns` to proxy model calls, which is a sixth verb and a much bigger kernel.
9. **Non-developers.** Everything above assumes a terminal, an editor and git. Obsidian shows a
   files-first design *can* have a humane front, but that front is a product someone has to build.
   The kernel gives it nothing beyond "read the tree".

### Where C is strongest, and what that suggests

C is the best answer on **ownership, longevity, debuggability and capability scoping** (tests 4,
11, 13 and 15, and the bind-as-grant model for 9). It is weakest on **time**: events, live loops,
mid-run human input and whole-run budgets. Those are exactly where B (the ledger) and A (the patch
bay with a scheduler) put their weight.

A plausible iteration-3 question is whether C is a *storage and capability layer* that A or B could
sit on, rather than a rival. The candidate split: a namespace of files in git as the durable,
user-owned truth, with a ledger or patch runtime for the time axis that keeps its own log of
events, whose payloads are `path@sha` references into the tree. This document does not decide
that. It records that every weakness above is about time, and that none of them is about the data.
